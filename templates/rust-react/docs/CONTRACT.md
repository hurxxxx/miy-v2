## Local development and data connections

`miy app dev` compiles and runs the native Rust backend, serves the built React preview on loopback, and connects to the server development database through an authenticated in-process WS/WSS tunnel. Rust, Node and the selected server are required; Docker Desktop, WSL and a local PostgreSQL installation are not required. The CLI owns the backend, gateway, tunnel and session heartbeat. The gateway signs the actual caller identity; platform credentials stay in the CLI. Stop with Ctrl-C or `miy app dev-stop`; development DB rows survive. Development deployment reuses that same DB. Use `--runtime docker` explicitly for a container backend, and `--runtime docker --database local` for a separate local container database. Native development never falls back to a separate DB.

Declare `platform:directory:read` in requestedPermissions and call `runtime.directory({kind:"users",q,limit:50,cursor}, {signal})`. Kinds are users, groups and memberships (only the current original user's memberships). Pages include subjectId, installationId, environment, users, groups and nextCursor. Users expose id/name/primaryGroup; groups expose id/name/source, never administrator or HR private fields. Limits are 1–100 (50 when omitted), optional ids resolve at most 100 stable references, and cursors bind to the current caller, installation/release and filters. Every page rechecks current access. The untyped `runtime.platformApi("directory")` called without a query reads one page and rejects with `directory_page_incomplete` when more entries exist, so a first page is never taken for the whole directory; search and follow `nextCursor` with `runtime.directory`. Declare `app:TARGET:read` or `app:TARGET:write` and use `runtime.appApi(TARGET,"/path",options)` to call another app in the same environment. The platform also requires the caller's access to that target; declarations do not grant user access. Target backend business authorization still applies. No cross-database credentials are exposed.

For typed backend directory reads use `identity.directory(&DirectoryQuery { kind: DirectoryKind::Memberships, ..Default::default() }).await`; the response is bound to the current identity and installation/environment. `identity.platform_api("directory").await` is the untyped first page only: it cannot pass a cursor and fails with `directory_page_incomplete` when the directory does not fit in that page, so page with `identity.directory` and `next_cursor`. Call another app with `identity.app_api("target-app", "/records", miy_app_sdk::Method::GET, None).await`. JSON writes pass `Some(&body)` with the intended method. The SDK sends the core-issued opaque proof only to the configured `MIY_CORE_ORIGIN`, with the receiving installation and current release; redirects and automatic retries are disabled. HTTPS is required unless the runtime explicitly sets `MIY_CORE_ALLOW_HTTP=1` for a configured HTTP development server. The core rechecks the original user's access, originating token restrictions, and the approvals of the entire caller chain. Permissions cannot expand at a later hop, environments cannot change, and at most eight caller hops are accepted. Manifest requests alone are not installation approval.

The proof is a sensitive short-lived bearer credential. `Identity` debugging redacts it, and the SDK removes the identity header before dispatching the business handler. Do not serialize, return, persist or log `identity.delegation_token()`. The installation's gateway signing key cannot mint a core delegation proof. SDK call errors expose a stable local code and optional HTTP status, never raw server bodies or credentials. Native and Docker preview use a separate process capability and private backend listener for directory/files only. Its identity uses the actual approved dev installation and a local release ID; it never claims local source is a deployed release. The browser never receives the capability or CLI credential. A deployed app needs the configured core origin to be reachable and trusted from its runtime; declaring permissions is not evidence of that connectivity.

## Resource ACL and sharing

Request and obtain installation approval for `platform:directory:read`, including for direct-user grants: ACL always checks the current actor. Apply `sdk/rust/src/acl.sql` as a new explicitly numbered application migration, then construct `miy_app_sdk::acl::Acl` with app-defined role/action mappings. Never execute migration SQL in a request handler. The app declares roles/actions in code and owns resources, grants, audit and result rows in its database; the platform owns identity, current groups and app Use. There is no implicit global workspace or platform-administrator bypass.

Create the business row and `create_resource_in` in the same transaction. `require_in` holds the resource share lock through a business write; use `require` for reads. `require`, `sharing` and `replacement_result` read the grants and return their pooled connection before the directory call, so a slow directory does not pin the app's connections; `require_in`, `replace_in` and `create_resource_in` call the directory inside the transaction you pass, so keep that transaction short. Group IDs in grants are stored in lowercase, as Core reports them. `list_resources` filters by current user/group permissions in SQL before pagination. Do not fetch private titles/counts before applying the predicate. Current group lookup fails closed and is bounded; never store expanded group members as permanent grants.

`sharing`, `replace_in(expected_revision, request_id, entries)` and `replacement_result` require current `acl.manage`. Replacements check the revision, protected creator, active new/changed recipients and at least one active direct-user manager, and commit audit/result with the grants. Reusing a request ID with another payload conflicts. A sharing snapshot lists `roles` in the order given to `Acl::new`, and that order grants nothing. `defaultRole` names a role only when exactly one role is the least: its actions are a subset of every other role's and it cannot manage sharing. `ShareEditor` preselects that role for a new subject and otherwise requires an explicit choice before saving. On a lost write response query the original request, without blindly resubmitting. App invitations/state rules remain app-owned; sharing never grants platform Use. No anonymous share URL or cross-app ACL inheritance is implied.

Common `DirectoryPicker` and `ShareEditor` accept app-provided services; selected values never grant authority. Memoize providers, reset drafts on user/installation/resource changes, and combine dirty states before reporting `setNavigationState`. Typed `ApiError` exposes status/code/requestId and sanitized network/abort/parse errors. App-generated 401 and uncertain write outcomes are never retried automatically. Only a Core-marked credential refusal before app delivery may renew the frame credential and resend once.

## Small attachments

Request and obtain installation approval for `platform:files:read` and `platform:files:write`. The app backend checks its own current resource ACL, then calls `Identity::files_create/by_request/get/upload/attach/detach/cancel/download`. The Core Storage API rejects ordinary browser and CLI access; possession of a file UUID is not authority. Preview allows only the current developer's approved dev installation.

Metadata uses opaque file id, version 1, name, mime, size, sha256 and status. Persist reservation intent with a UUID requestId in the app DB before reserving. File bytes stream via `runtime.fileApi('/path')` to the app's `/api/files/path`, then the backend's Core Storage client; ordinary JSON/apiBlob limits stay unchanged. Platform refusals keep their code for known storage and notification errors (`CallError.code`, for example `file_quota_exceeded`, `file_storage_low`, `file_part_offset`, `file_upload_expired`, `file_corrupt`); any other refusal is `core_call_rejected` with its HTTP status. A one-request upload is up to 10MiB, with four transfers per gateway stage and a 20-second transfer timeout. Each installation keeps up to 20GiB/100,000 files unless an administrator sets other limits, and the platform refuses new reservations when the file volume runs low (`file_storage_low`).

For larger files (up to 2GiB) reserve with `Identity::files_create_parts`, send ranges of up to 8MiB with `files_upload_part(&file, bytes)` (each starts at the metadata's `received`), then call `files_complete(file_id)`; Core hashes the bytes and marks the file ready. Send the browser's parts through `runtime.fileApi` like small files, one range per request; pass `onUploadProgress(sent, total)` in its options to show progress (it always ends with a final report when the upload completes). After an uncertain result call `files_get` and continue from its `received`; a range at another offset is refused with 409 `file_part_offset`. `files_complete` is safe to repeat. To let the person download a file of any size, declare `"platformEndpoints": {"fileAccess": "/v1/file-access"}` and serve it (POST, platform calls only): the body is `{"fileId", "reference"}` and you answer `{"allowed": true}` only if this person may still read that file through your ACL. Then, inside a request that came from your own frame and after your ACL check, call `Identity::files_download_link(file_id, reference)` (the reference given at attach, or `None` for an unattached file) and return its `url` to the UI, which calls `runtime.download(url)`. The link lives five minutes; every request for it (including resumed ranges) is checked again and asks your `fileAccess` endpoint before bytes are sent. `files_download` keeps its 10MiB limit and `runtime.download` is not available in local preview.

Incomplete pending uploads expire after 24 hours. An elapsed reservation reports `expired` and stops counting toward quota at once; the platform worker removes its bytes about once a minute, apart from any request. A failed or interrupted upload may be sent again for the same reservation until it expires. A state change that meets a running upload of the same file waits a few seconds and then answers 409 `file_upload_in_progress`. Ready bytes and attached bytes are retained; ready is not safe to garbage-collect because an app reference may already have committed. Commit the app reference before `files_attach(file_id, reference, request_id)`. A lost reserve/upload/attach response requires request/file lookup, never automatic compensation deletion. Explicit cancel only applies to unattached files. To release an attached file, remove the app reference in a committed transaction and then call `files_detach(file_id, reference)` with the reference given at attach: Core deletes the bytes, returns the quota and reports `cancelled`. Detach may be repeated after an uncertain result; until it succeeds the file stays attached and keeps its quota. A durable internal cancelling marker prevents attachment before byte removal; cleanup failures remain recoverable and keep their quota until removal. The app must refuse cancellation once its own reference exists even if Core still says ready. App removal preserves stored files. Back up and restore Core metadata, bytes and the owning app references together.

The file gateway copies only approved content/integrity headers and adds sandbox/nosniff. It drops cookies, redirects and Clear-Site-Data. Download authenticated bytes inside the frame, use a local Blob URL and revoke it after use. `FileTransferPanel` provides sequential transfer, explicit cancellation and result recovery; `FileImagePreview` accepts validated raster content only. HTML/SVG/PDF/Office are not embedded by the common image preview.

## Platform notifications

Request and obtain installation approval for `platform:notifications:write`. While handling a user request, the backend calls `Identity::notify(&Notification { request_id, recipients, kind, group_key, title, path, resource_id })`. Recipients are miy user IDs; the platform silently leaves out people who may not use this app in this environment, disabled accounts and people who turned that kind off, and answers only `accepted` (a count). `group_key` (for example a conversation ID) keeps one line per person: a newer notification replaces the older one. `title` is short display text without the message body (for example "Alice · 2 new messages"); `path` is an app-relative destination the portal opens in this app's frame. Use a new UUID per notification as `request_id`; after an uncertain result call `notification_by_request` instead of sending again, and never undo the business write because publishing failed. To reach people who have access through a platform group (for example a space shared with a group), call `Identity::notify_with_groups(&notification, &group_ids)` instead; the platform sends to the group's current members with the same filters, never adding the calling person through a group (needs `platform:directory:read` approved as well; up to 50 groups, recipients may then be empty). Call `retract_notifications(group_key, recipients)` when the source is edited or deleted or someone loses access, and `mark_notifications_read(group_key)` when the calling person reads it in the app. The frame cannot publish. Local preview checks the request and delivers nothing.

To let the platform recheck notifications when a person opens the notification panel, declare `"platformEndpoints": {"notificationCheck": "/platform/notification-check"}` in manifest.json and serve that path in the API router (POST). The body is `{"items": [{"groupKey", "resourceId"}]}`; answer `{"allowed": ["groupKey", ...]}` with the groups that still point at something this person may open. The request carries the person's verified identity with `identity.context.platform == true`, `admin == false` and no token for further platform calls; treat it as a read-only call and change no data. Answer within 3 seconds and 64 KiB; a missing or late answer only hides those notifications for that opening, a definite answer removes the denied ones.

## Side panels, home cards and search

An app may offer narrow screens that the portal shows as a side panel beside the main app frame. Declare them in manifest.json as `"panels": [{"id": "todos", "title": "할 일", "path": "/widgets/todos"}]` (at most 4; `id` is a lowercase slug, `title` 1–40 characters, `path` an app-relative screen path). Each person picks and pins panels in the portal; one panel is open at a time. The panel is a second frame of the same app with its own location: `runtime.location` starts at the declared path, `runtime.navigate` changes only the panel, and the portal address keeps following the main frame. Design the panel screen for about 400 px width, report unsaved input with `runtime.setNavigationState` as in the main screen, and keep frames independent: the platform relays nothing between them, so refetch through `runtime.api` (or a live connection) to see changes made in the other frame. On narrow screens the portal opens the panel's path in the main frame instead.

To show a summary card on the portal home, declare `"platformEndpoints": {"homeCard": "/v1/home-card"}` and serve that path (POST) in the API router. The body is `{"timeZone": "Asia/Seoul", "locale": "ko-KR"}` from the person's display settings; the request carries the person's verified identity with `identity.context.platform == true`, `admin == false` and no token for further calls, so read only. Answer within 3 seconds and 64 KiB with `{"title"?, "count"?, "items": [{"title", "subtitle"?, "at"? (RFC 3339), "path"? (app-relative)}]}`. The platform keeps at most 5 items, shortens titles (80/120/160 characters), drops anything else and shows it as text; an item's `path` opens in this app's frame. A missing or late answer shows the card as unavailable for that visit; answer 403 to calls that are not platform calls.

Platform calls (home card, search, notification check, file access) carry no token for further calls, so they cannot ask the directory. When the app is approved for `platform:directory:read`, `identity.context.groups` holds the person's current group IDs and the SDK ACL uses them for group grants on those calls; without the approval it is `None` and only direct user grants count.

To take part in the portal's integrated search, declare `"platformEndpoints": {"search": "/v1/search"}` and serve that path (POST) the same way. The body is `{"query", "limit", "timeZone", "locale"}` with a trimmed query of 1–200 characters and a limit of 1–10. Answer `{"items": [{"title", "snippet"?, "path"?, "at"?, "kind"?}]}` with only what this person may open, at most `limit` items; your app decides access exactly as for its own screens, and the platform never shows anything you leave out (no counts of hidden items). `kind` is a short label of your own (for example "일정"); titles are cut to 120 characters and snippets to 240. Escape `%`, `_` and `\` when you build a `LIKE` pattern. A late answer marks your app "가져오지 못함" for that search.

## Live connections

For updates that should arrive at once (new messages, presence), call `runtime.live({ onOpen, onMessage, onClose })` in the UI; it returns `{ send(text), close() }`. The platform relays the WebSocket to this app's `GET /api/live` with the person's verified identity, so add a `/live` route to the API router that accepts an Axum `WebSocketUpgrade` (enable the `ws` feature of `axum` in Cargo.toml) and reads `Extension<Identity>` like any other route. Messages are text, up to 64 KiB each. The runtime reconnects after drops (`onClose` with `retrying: true`); it stops when the frame session ends, access is revoked or the release changes. The platform closes a connection that carries no message for 5 minutes, so send a small heartbeat if you need longer silences. Keep reads and writes on `runtime.api`: treat a live message as a hint to refetch, and check access again on the server for every action. For authenticated application data use `runtime.liveBinary` with the same lifecycle and Uint8Array messages. A logical message (up to 16 MiB) uses consecutive binary frames, each with a big-endian u32 total length and u32 byte offset followed by up to 65528 payload bytes. Both endpoints discard partial messages on disconnect. App close codes 4410 (resource access revoked) and 4411 (resource generation changed) stop reconnection without ending the frame. Reauthorize each room on join and during use. Local preview relays `/__miy/live` to the same route.

## Frame execution

The UI runs in its own cross-origin frame: one origin per installation, separate from the portal, the console and every other app. The platform frame runtime loads this release's `./AppRoot` and passes `runtime`; it shares only React and React DOM with the app. `runtime.api`, `apiBlob`, `platformApi` and `appApi` call this frame's own origin with a short in-memory credential; there are no cookies and no CSRF value. The frame cannot read portal pages, storage or another app, and another app's API is reachable only through `runtime.appApi` with an approved connection.

To copy or share a link to a screen, use `runtime.portalUrl('/path')`: it returns the full portal address of an app-relative path (the frame cannot read the portal's address). Clipboard writing and full screen are not available in the frame unless the release requests `frame:clipboard-write` or `frame:fullscreen` in `requestedPermissions` and an administrator approves it; keep a fallback for when they are not.

Inside the frame: do not use `window.parent`, `window.top`, `history.pushState`/`replaceState`/`back` or `document.cookie` for credentials, and do not register service workers. Use `runtime.navigate` for app routes; plain links to app paths under `runtime.basePath` are routed by the portal, and external links open in a new tab. For downloads use `runtime.apiBlob(path)`, create an object URL and revoke it after use. The frame fills the portal work area at a fixed size; dialogs and overlays render inside it and the app scrolls internally. Keep local styles; the frame document has only a small baseline (font, background, link colors).

## Display settings and tokens

`runtime.settings` carries the display settings the person chose in the portal: `theme` (`light` or `dark`, already resolved), `themePreference` (`system`, `light` or `dark`), `locale` (`ko-KR` or `en-US`), `timeZone` (an IANA name) and `dateFormat` (`korean`, `iso`, `us`, `european` or `locale`). `runtime.theme` equals `settings.theme`. When a setting changes, AppRoot renders again with a new `runtime`; do not cache the old values. Settings change how things look and read. Never use them for an access decision.

The platform sets the theme on the frame document before the app renders: the `dark` class and `data-miy-theme="dark"` on `<html>`, and `lang` to the locale. Do not set these yourself. Format dates and times with `settings.timeZone`, `settings.dateFormat` and `settings.locale`, not with the browser defaults.

The platform frame runtime serves the design tokens and the Pretendard font to every app frame: CSS variables named `--ui-*` (for example `--ui-color-bg`, `--ui-color-surface`, `--ui-color-ink`, `--ui-color-border`, `--ui-color-accent`, `--ui-color-brand`, `--ui-radius-md`, `--ui-space-4`, `--ui-text-body`). Use these variables for colors, spacing, radii and type sizes so the app follows the light and dark themes; do not hard-code colors. The body baseline is 14px with a 1.45 line height. Local preview loads the same tokens from `sdk/preview/tokens.css`; it shows Pretendard only when the computer has the font installed.

Apps built with a bundle before 0.12.0 keep the light theme and Korean document language whatever the person chose.

## Delivery

`app build` requires committed clean source (at most 64 MiB) and builds the immutable Docker image on the server. `app deploy` deploys that server image to dev; production receives it only by `app promote` of the accepted release. The client needs no Docker engine. The platform is not restarted. Use `app status` and `job get ID` to check installation, release, image and terminal job state; a running old version is not evidence that an update succeeded.

After browser/API testing, `app accept --note "actual checks"` records acceptance for the exact dev release. `miy --context CONTEXT --app APP --yes app promote --environment prod --release UUID` deploys that same image to a separate prod installation/database; it does not copy dev data. Only administrators or users granted prod/deploy may promote or control prod. Runtime routes explicitly include environments: `/environments/dev/apps/ID` and `/environments/prod/apps/ID`.

## Component distribution

The SDK protocol remains in the versioned foundation bundle. UI implementations
come from the platform component registry using protocol `miy.component/v1`.
The template declares initial defaults in `miy.components.json`; the CLI installs
them after login with `component sync`. New component releases do not change
the CLI binary or any installed app. `platform-components/` is a managed source
directory with its own version/hash lock. Import `@miy/components/NAME` and keep
business extensions outside that directory. App check/build verifies both locks.

## Navigation and application lifecycle

Within one app frame or local preview session, runtime methods (including
`api`, `appApi`, and `navigate`) keep the same reference when the route, query,
hash, or display settings change. API calls use the session's current
credentials. The `runtime` object itself changes to deliver route and settings
updates. Use `[api]` for session-level reads and `[api, resourceId]` for a view
that loads one resource. Keep the shared layout mounted, show loading in the
affected view, and cancel or ignore stale responses. The generated
`web/src/AppRoot.tsx` shows one initial read and internal navigation.

Report unsaved input or in-flight work with `runtime.setNavigationState` whenever
it changes. The portal decides synchronously from the last reported state, so
report it when the state changes, not when leaving. A move you start yourself with `runtime.navigate` inside the app does not ask (you know your state and the frame stays); browser back/forward and portal links do. Example:

```tsx
useEffect(() => runtime.setNavigationState({
  dirty: dirty || saving,
  message: "저장되지 않은 작업이 있습니다. 이동하시겠습니까?",
}), [runtime.setNavigationState, dirty, saving]);
```

The platform and local preview apply this to runtime.navigate, host menu links,
back/forward, and document unload. Browsers use their own unload message and may
suppress prompts without user interaction. Do not add a second confirm around
runtime.navigate or manipulate browser history directly. Remove the guard when
work is saved/discarded by reporting `dirty: false`. Reporting is required: hosts
cannot infer application draft state. Apps on the 0.8 SDK still run; their
callback guard cannot be evaluated across the frame, so the portal asks before
every leave. When a deployed release changes, the frame blocks stale API calls
and the portal asks the user to reload.

`app dev-stop` requests shutdown of this project's runner, waits for the port and
lock to be released, and stops its owned native backend and DB tunnel (or explicitly selected containers). Database data survives.
During startup it waits for the current build/migration to finish. A timeout is
reported as pending, never successful. Old CLI runners must first be stopped with
Ctrl-C in their terminal. Deployment does not stop a local preview automatically.

## Names and acceptance records

The platform display name is administrative metadata. Deployment never renames
it from manifest.json. Administrators use `app rename --name "Display name"`;
`app show` reports platform app and installation metadata; manifest.json remains the local source name. This changes no source or release metadata.

`app accept --note "summary" --report acceptance.json` records user-attested tests
for the report's exact releaseId. See docs/ACCEPTANCE.md for the format and
platform-boundary checklist. The authenticated recorder and test actors are
separate. Failed tests cannot be submitted as approval; use not_run with a reason
for explicitly untested scope. Legacy note-only acceptance remains supported and
is marked unstructured. Neither format automatically proves business correctness.

## CLI input and runtime control

`app accept --input @FILE` accepts strict `{releaseId,note,checks}` JSON; `grant set --input @FILE` accepts `{userId,appId?,environment,permission}`. Use `-` for explicit stdin. Unknown fields and conflicting field sources are rejected. Discover exact schemas in `describe --command`.

`app start|stop|restart|remove` replaces app control. Prod changes and every app removal require explicit `--context`, `--app`, `--environment` and confirmation (`--yes` for automation). Dry-run uses the same target and returns planned changes/expected state without job creation. Admission and execution recheck state and permissions; app removal preserves the app database. Context removal only affects local configuration.

`app logs --environment dev --tail 100` returns a bounded snapshot with truncation/rotation limits. Resume a known log request with `--request ID`. Do not treat it as retained historical logging.
