## 1. 요약

- **3일간 한 일.** 11-20~21에 계정 발급(초대·재설정 링크), CLI 로그인 갱신 안정화, 재설정 복구, 릴리스 소스 보관, 오프라인 하니스를 만들어 miy.works를 0.13.0에서 0.16.0까지 올렸다. 11-22 하루에 범용 기능 계획의 거의 전부(디자인·설정·알림·실시간·패널·사용자 전환·검색·대용량 파일, 공식 앱 7개)를 약 55만 줄로 올렸다. 이 리뷰가 진행되는 동안(11-23 오전 KST) 앱 API 계약 작업이 더해져 **0.17.0·schema 34가 miy.works에 반영됐다.**
- **리뷰보다 반영이 앞섰다.** 내부 리뷰 2회는 11-22 정오(KST)까지의 코드만 봤다. 그 뒤의 대용량 전송·그룹·프레임 기능과 화이트보드·문서·드라이브 앱, 메신저·PMS 보강은 리뷰 없이 운영에 올라갔다. 이 문서의 §6.4~6.10이 그 구간의 첫 리뷰다.
- **코드의 P1은 2건이다.** 문서·화이트보드에서 편집 권한만으로 공개 범위를 바꿀 수 있다(APP-01). 메신저 대화 목록이 플랫폼의 4MiB 응답 한도를 넘어, 누구나 다른 사람의 메신저를 열리지 않게 만들 수 있다(APP-02). 둘 다 최신 코드에 그대로 있다.
- **운영 중인 코드의 주요 P2.** 비밀번호 재설정이 CLI 세션·발급 링크·전환 세션을 회수하지 않는다(ACC-01·03). 초대 완료 실패 시 로그인 서버에 고아 계정이 남는다(ACC-02). CLI 갱신이 일시 장애에도 재로그인을 요구한다(ACC-04). 실시간 채널이 일시 장애를 세션 종료로 처리한다(PLT-01). 무결성 확인이 읽지 못한 파일을 영구히 손상으로 표시한다(STO-02). 다운로드 슬롯 8개가 느린 연결에 묶인다(STO-01). 드라이브의 보기 전용 역할이 쓰기를 막지 못한다(DRV-01).
- **저장소와 운영이 어긋나 있다.** 운영 바이너리는 원격에 없는 커밋(`1588a88`)으로 빌드됐고, 저장소에는 0.17.0 배포 기록이 없으며, 문서는 운영을 0.14.0·0.16.0으로, 이번 범위를 "서버에 반영하지 않는다"로 적고 있다(OPS-11·06). `prod` 작업본에는 어느 커밋에도 없는 작업이 미커밋으로 남아 있다(OPS-04).
- **CI의 격리 회귀가 불안정하다.** 최근 5회 중 2회가 같은 자리(boundary 묶음)에서 실패했고 같은 트리의 재실행은 통과했다. 실패 원인 문구는 CI에 남지 않는다(OPS-01·02).
- **이전 리뷰의 보완은 대부분 실제로 들어갔다.** 플랫폼·공용 UI 22행 중 17행, 메신저 5행 중 4행, PMS·게시판·플래너 25행 중 24행이 고쳐졌다. 남은 것은 §7에 있다.

## 6. 상세 발견

표기: **ID · 심각도 · 확신도**.

- 심각도 — `P1`: 권한 우회, 데이터 유실, 보안 노출, 주 흐름 중단. `P2`: 현실적인 조건(경합·재시도·부분 실패·크기)에서 잘못 동작. `P3`: 경미, 유지보수, 테스트·문서 불일치.
- 확신도 — `확인`: 코드 경로를 끝까지 추적했다. `확인★`: 이 문서를 쓰면서 해당 줄을 다시 열어 확인했다. `추정`: 코드상 가능성이 높지만 실행이나 외부 동작 확인이 필요하다. 무엇이 미확인인지 항목에 적었다.

### 6.1 저장소·작업본·CI·문서 (OPS)

**OPS-01 · P2 · 확인★(불안정), 원인은 추정 — 격리 런타임 회귀가 같은 자리에서 간헐적으로 실패한다**

- 사실: `Isolated runtime regression`의 최근 결과는 `3983642` 실패, `5fd2a55`(PR) 실패, `10bc486`(같은 트리의 병합) 통과, `597bdfb` 통과, `9156e6a` 통과다. 두 실패 모두 `boundary`가 19건 중 1건만 기록하고 멈췄다(총 143건). 작성자의 로컬 기록은 같은 코드에서 158~161건 통과다.
- 정적 분석으로 원인을 확정하지 못했다. 디스크 크기, 시간대, `MIY_CONFIG_DIR`, 빌드 산출물, 포트, 실행 순서에 의존하는 단언은 boundary 묶음에서 찾지 못했다. 실행 시간(통과 336~352초, 실패 381초)으로 보면 새 검사 1~5 구간, 알림 실시간 채널 근처에서 멈춘 것으로 보인다.
- 원인 후보(추정, 가능성 순):
  1. **첫 NOTIFY 유실.** 포털 알림 채널의 PostgreSQL 리스너는 첫 `/api/v1/live` 요청 때 별도 task로 늦게 시작한다(`crates/miy/src/notifications.rs:754-775`). 처리기는 `LISTEN`이 켜지기를 기다리지 않는다(`:818-838`). 테스트는 `pg_notify`를 한 번만 보내고 15초를 기다린다(`crates/miy/src/browser_boundary_regression.rs:1092,1111-1120`). `LISTEN` 전에 커밋된 NOTIFY는 영영 오지 않는다. 이것은 제품 결함이기도 하다(PLT-07: 배지가 다음 변경까지 낡은 채 남음).
  2. 플랫폼 → 앱 호출의 예산·시간 제한(`crates/miy/src/platform_calls.rs:29-30`, PLT-03).
  3. 러너의 일시 장애. `scripts/runtime-regression/setup.py:23`은 PostgreSQL을 메모리 512MB, tmpfs 768MB로 띄우는데 tmpfs가 같은 메모리 한도에 계산된다. `MIY_APP_FRAME_PORTS=47100-47399`(`crates/miy/src/runtime_regression.rs:1012`)는 리눅스 임시 포트 범위 안이다.
- 확인하는 가장 싼 방법: 깨끗한 checkout에서 `python3 scripts/runtime-regression/run.py`를 여러 번 돌려 `evidence/integration.log`의 `boundary suite stopped:` 줄을 읽는다. `deadline has elapsed`면 후보 1이다. 후보 1의 존재는 리스너 task 첫 줄에 500ms 지연을 임시로 넣어 재현할 수 있다.
- 수정: 리스너가 `listen`에 성공할 때마다 재동기화 신호를 보내 각 연결이 미확인 수를 다시 보내게 한다(또는 재확인 주기마다 수를 보낸다). 테스트는 수가 올 때까지 `pg_notify`를 반복한다. 호출용 `reqwest::Client`를 하나로 공유한다. DB 컨테이너의 tmpfs를 메모리 한도 이하로 하고 프레임 포트 범위를 임시 포트 밖으로 옮긴다.
- 검증: 수정 뒤 같은 커밋에서 회귀를 10회 연속 통과시킨다.

**OPS-02 · P2 · 확인★ — 회귀 실패의 원인이 CI에 남지 않는다**

- 위치: `crates/miy/src/browser_boundary_regression.rs:258`(`run`이 `Result<Vec<String>>`을 끝에서 한 번에 반환), `crates/miy/src/runtime_regression.rs:45-63`(`suite`), `:2001`(`suite("boundary", …)`), `scripts/runtime-regression/run.py:115-122`, `.github/workflows/runtime-regression.yml:74-83`.
- 문제: 하위 묶음은 통과한 검사 이름을 모아 두었다가 마지막에 반환한다. boundary는 2,600줄 중 어디서든 `Err`가 나면 통과 기록 전부가 사라지고 FAIL 한 줄만 남는다. 오류 문구는 `eprintln!("{name} suite stopped: …")`로 통합 로그에만 찍히고 FAIL 행에는 없다. `run.py`는 통합 로그의 **마지막 14,000자**만 출력해 그 줄이 잘린다. workflow는 `sdk-acl-*`·`common-work-*` 증거만 올리고 `results.jsonl`은 올리지 않는다.
- 결과: 11-22 실패에서 CI 로그로 알 수 있는 것은 "boundary 19건 중 1건만 기록됨"뿐이었다.
- 수정: (1) `suite`가 오류 문구를 FAIL 행의 `evidence`에 넣고, boundary가 멈춘 지점(몇 번째 검사, 마지막으로 통과한 이름)을 오류에 싣는다. (2) `run.py`가 종료 전에 `suite stopped:` 줄과 `status != "PASS"`인 행을 그대로 출력한다. (3) workflow에 `if: failure()`로 `.local/evidence/runtime-regression/*/evidence/`(`results.jsonl`, `integration.log`)를 올리는 단계를 넣는다. 이 증거가 비밀값을 가리는지 먼저 확인한다.
- 검증: boundary 중간 검사를 일부러 실패시킨 브랜치에서 CI 로그에 실패 검사 이름과 오류 문구가 보이는지 확인한다.

### 6.5 공식 앱 공통 (APP)

앱 소스는 0.17.0과 함께 운영 서버에 올라갔고 일부가 설치돼 실행 중이다(§4). 여러 앱에서 같은 모양으로 반복되는 문제다. 앱 하나만 고치지 말고 일곱 앱을 같이 확인한다.

**APP-01 · P1 · 확인★ — "공개 대상 변경"이 편집 권한만 요구한다(문서, 화이트보드)**

- 문서 `apps/docs/src/items.rs:1018-1023`(PUT target), `:1035-1042`(DELETE target), `:915,941-956`(복제가 대상을 복사). 화이트보드 `apps/whiteboard/src/whiteboard.rs:1301-1314`, `:1361-1368`, `:341-352`.
- 문제: 사이드바 대상(target)은 그 문서·보드를 공간 전체에 여는 ACL이다. 사용자 공유는 `can_share`, 이름 변경·휴지통은 `can_manage`를 요구하는데 대상 변경은 `can_edit`만 본다. 화면은 관리 권한일 때만 버튼을 보여 주지만 서버는 강제하지 않는다. `apps/docs/docs/PORTING.md:113`은 이를 "AI-DO 규칙 그대로 둔 것"으로 적었다. 그러나 AI-DO는 모든 요청을 호출자가 속한 워크스페이스에 묶었고, 여기서는 그 전제가 없으며 공유 대상도 공간 구성원으로 한정되지 않는다.
- 시나리오: (1) "전체" 공간의 비공개 문서에 편집 공유를 받은 사람이 `PUT …/target`을 호출하면 모든 앱 사용자가 그 문서를 읽고 고칠 수 있다(전원이 전체 공간의 `member`, `apps/docs/src/spaces.rs:198-203`). (2) 임의의 사용자가 전체 공간의 공개 문서에 `DELETE …/target`을 호출하면 소유자 외 모두에게서 사라진다. (3) 읽기 공유만 받은 비구성원이 공개 문서를 복제하면 사본이 대상과 함께 그 공간에 생긴다.
- 수정: 대상 PUT·DELETE에 `can_manage`를 요구한다(같은 잠금 안에서). 복제는 호출자의 공간 역할이 `member` 이상일 때만 대상을 복사하고 아니면 비공개 사본을 만든다. PORTING의 해당 문장을 고친다. PMS·게시판·드라이브에 같은 종류의 "공개 범위 변경" 경로가 있는지 확인한다.
- 검증: 각 앱 `api_tests.rs`에 "편집 공유 사용자의 PUT·DELETE target이 403", "다른 사람 문서에 대한 구성원의 DELETE target이 403", "읽기 공유 비구성원의 복제본이 비공개"를 추가한다.

## 8. 작업 방식 개선

3일간의 흐름에서 반복된 것들이다. 코드 수정과 별개로 [AGENTS.md](../../AGENTS.md)와 [검사 지도](../CHECKS.md)에 반영할 후보다.

**PRC-01 — 리뷰한 범위와 반영한 범위를 맞춘다.** 내부 리뷰는 `f43a232`까지였고 운영에는 `1588a88`이 올라갔다. 그 사이의 대용량 전송, 그룹, 앱 세 개, 관리 콘솔 포팅은 리뷰 없이 반영됐다. 배포 기록에 "리뷰한 커밋 범위"를 필드로 두고, 범위 밖 커밋이 있으면 반영 전에 리뷰하거나 미리뷰임을 기록에 적는다.

**PRC-02 — 원격에 있는 커밋만 반영한다.** 운영 바이너리가 미push 커밋으로 빌드됐고, 같은 버전 번호 0.17.0으로 서버 바이너리가 세 번 바뀌었다(OPS-09·11). 반영 도구가 `git merge-base --is-ancestor <commit> origin/main`을 확인하게 한다.

**PRC-03 — 배포 기록과 운영 문서 갱신을 반영 절차의 한 단계로 둔다.** 0.15.0·0.16.0 기록은 이틀간 미추적 파일이었고 0.17.0은 아직 `/srv/miy-prod/evidence/`에만 있다. `SERVER-OPERATIONS.md`는 세 릴리스 뒤처져 있다. 반영 스크립트가 `deploy-result.json`에서 `docs/releases/` 기록과 `cli-published.json`을 만들고, 그 커밋이 없으면 반영을 미완료로 표시한다.

**PRC-04 — push와 커밋을 작게 한다.** 59개 커밋이 한 번에 올라가 CI가 마지막에서만 돌았고, 492개 파일이 한 커밋이 됐다. 단계(마일스톤)마다 push해 CI를 받는다. 생성 파일 재동기화, 동작 변경, 문서를 서로 다른 커밋으로 둔다.

**PRC-05 — 포팅에 점검표를 쓴다.** 이번 발견의 다수는 "AI-DO 규칙 그대로"가 새 전제에서 깨진 것이다. `templates/rust-react/docs/CONTRACT.md`나 앱 포팅 절차([범용 기능 계획 §4](../COMMON-FEATURES-PLAN.md#4-단계별-세부-작업))에 다음을 넣고 앱마다 확인한다.

1. 모든 경로가 쓰기 트랜잭션 안에서 **현재** 권한을 다시 확인하는가(BRD-01).
2. 공개 범위·ACL을 바꾸는 경로가 편집이 아니라 관리·공유 권한을 요구하는가(APP-01).
3. 역할이 낮아지거나 공간에서 빠진 사람의 기존 권한(소유, 직접 공유)이 어떻게 되는가(DRV-01, WB-01).
4. 모든 목록에 페이지가 있고 최대 크기 데이터로도 응답이 4MiB 미만인가(APP-02).
5. 행 잠금을 쥔 채 Core를 호출하지 않는가(APP-03).
6. 올리다 만 파일과 참조가 끊긴 파일을 회수하는가(APP-04).
7. Core의 거절 코드를 그대로 옮기는가(APP-05).
8. 날짜 판정이 서버 UTC나 고정 시간대가 아니라 포털 시간대를 쓰는가(PMS-02, PLN-01).
9. Enter 처리에 한글 조합 확인이 있는가(DOC-03).
10. 늦게 온 응답이 최신 상태를 덮지 않는가.
11. AI-DO에서 가져오지 않기로 한 기능의 코드가 남아 있지 않은가(WB-08, MSG-04).

**PRC-06 — 앱 테스트를 CI에서 돌리고 빠진 종류를 채운다.** `official-apps.yml`이 생겼다. 여기에 응답 크기 테스트, 권한 행렬(역할 × 경로), 잠금 대기 중 권한 회수 테스트를 앱마다 넣는다. 지금은 이런 테스트가 PMS에만 있다.

**PRC-07 — 작업본의 역할을 다시 적는다.** 상위 `/projects/miy-v2/AGENTS.md`는 `prod` 하나에 개발 변경을 직접 반영하고 `dev`는 소스만 준비된 작업본이라고 한다. 실제로는 `dev`에서 개발·빌드하고 산출물을 `/srv/miy-prod/bin`과 `prod/web/platform/dist`에 놓는다. `prod`의 소스는 11-21에 멈춰 있다(OPS-12).

**PRC-08 — 여러 에이전트가 한 작업본을 쓸 때.** 미커밋 변경이 15시간 동안 483개 경로로 쌓였고, 그동안 다른 작업자는 그 트리의 상태를 설명할 수단이 없었다. 긴 작업은 `git worktree`나 브랜치에서 하고, 작업 중인 범위를 한 줄로 남긴다.

**PRC-09 — `PLAN.md`를 현재 상태 표로 유지한다.** OPS-07 참조.

## 10. 검토하지 못한 범위

아래에 문제가 없다는 뜻이 아니다.

- **기준 커밋 이후의 커밋.** `597bdfb`, `9156e6a`, `ae52439`, `1588a88`은 전혀 보지 않았다. `2c38b35`는 구성과 플랫폼 변경을 봤고 앱 전환은 플래너·화이트보드·드라이브를 표본으로만 봤다. §5의 "현재" 열은 결정적인 줄 한두 개를 다시 찾은 것이지 전체 재검토가 아니다.
- **앱의 웹 코드.** 서버 발견에 필요한 경로와 명백한 결함만 봤다. 편집기, 가져오기·내보내기, 공유 편집 화면, PMS의 새 화면 렌더링은 보지 않았다.
- **앱 서버의 일부.** 메신저의 안전 관리 경로 16개·차단·약관·사용자 검색, PMS의 `search.rs`·`home_card.rs`·`notify.rs`, 드라이브 `archive_planner.rs`.
- **플랫폼.** 포털의 홈·설정·명령 팔레트·런처 메뉴 화면, 번역 문구, CSS, 생성된 SDK·API 타입, 공용 UI 2.0.x 컴포넌트 대부분, `mcp.rs`, Playwright 테스트의 내용, 배포 스크립트(`core-rollout.py` 등), Windows 설치기.

- **운영 데이터.** `/srv/miy-prod`에서는 배포 결과 요약만 읽었다. DB는 조회하지 않았다. STO-02의 운영 확인은 운영자가 한다.
