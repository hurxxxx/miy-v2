# 코어 안정화 계획

- 작성·수정일: 2026-11-03
- 기준: 현재 소스 CLI 0.7.0 / 개발 번들 0.8.0 (운영 0.6.3 / 0.7.1), [PLAN](PLAN.md)의 현재 작업 순서
- 상태: **1·2차 구현·단위/격리 회귀 및 SDK/CLI 검증. 실제 운영 Docker 후속 호출·서비스 계정과 3~5차는 별도다.**

이 문서는 앱 개발·원격 빌드·배포 기반의 **1) worker/오류, 2) 설치 승인 권한/호출자, 3) 용량, 4) 백업·복원/updater, 5) 새 서버·수명주기 인수** 작업 묶음을 관리한다. 번호는 기존 증거와 연결하기 위해 유지한다.

2026-11-03 사용자 결정에 따라 1·2차 다음 착수 범위는 [기본 UI/UX 이식](../UIUX_MIGRATION_PLAN.md)이다. 라이트 테마·한국어·새 설치 기준의 UI-1~4를 구현했고 UI-5 통합 검증이 진행 중이다. 조직·그룹 권한과 앱 소유 워크스페이스는 기본 UI 이후에 구현한다. 코어 3~5차 전체를 기본 UI 착수 조건으로 두지 않으며, 자원·복구·updater의 남은 구현과 종합 인수는 베타 전 운영 준비로 관리한다. 각 기능의 회귀 검사는 계속 수행하고 실제 데이터 변경 전 필요한 백업·복구 경로는 먼저 확보한다. 현재 실행 순서는 [추진 계획](PLAN.md)을 따른다.

현재 게시 서버·CLI의 artifact source `8d7d04271f9467d8bbdd16308e73715b33e4dc0c`와 main 통합 commit `a6fae065ed627bb63798cf74ea8a2c73a744c104`는 구분한다. 문서·소스 수정은 운영 반영을 뜻하지 않는다. [운영 안내](SERVER-OPERATIONS.md)의 기존 서비스·데이터 보존 경계를 유지하며, 새 인수는 격리 환경에서 수행한다. 사용자 Windows 11 실제 검증은 사용자가 추후 수행하기로 했으므로 [Windows 인수 절차](WINDOWS-0.6.3-ACCEPTANCE.md)의 `NOT_RUN`을 유지한다.

## 1차: worker 제어·빌드 실행 분리와 DB 오류 계약

**현재 상태: 구현과 아래 단위·격리 통합 회귀 통과. 운영 서버 재배포나 전체 코어 완료를 뜻하지 않는다.**

착수 시점의 [worker](../crates/miy/src/worker.rs)는 제어 순회에서 `server_build_worker::tick`을 await하고 빌드 완료까지 기다렸다. [빌드 worker](../crates/miy/src/server_build_worker.rs)의 컴파일 제한 시간은 1,800초다. 이 구조에서는 빌드 중 다음 제어·reconcile 순회가 지연될 수 있다. HTTP 관찰 task가 별도라는 사실만으로 앱 stop/start 처리 지연이 해결되지는 않는다.

빌드와 제어는 같은 워커 소유권 아래 서로 다른 future로 실행한다. 별도 감시가 소유권 연결을 1초마다 확인하며 검사 제한시간은 3초다. 연결 유실·분기 실패·종료 신호 시 다른 분기를 취소하고 기존 Docker 클라이언트 정리 경로를 사용한다. 빌드 복구 잠금을 얻지 못하면 제어를 막지 않고 복구를 재시도한다. 동기 파일 검증은 future 취소 후에도 계속될 수 있으므로 실행별 임시 경로와 Arc 수명으로 분리했다. DB 준비·이미지 import·runtime 제어 사이의 기존 처리 순서는 유지한다.

완료 기준:

1. 격리 fixture에서 빌드를 의도적으로 대기시킨 상태로 다른 앱 stop/start·상태 대조를 요청한다. **빌드 대기를 해제하기 전에** 제어 작업이 완료되고, 미리 정한 제한 시간 안에 결과가 관찰돼야 한다. API 요청 접수만으로 통과시키지 않는다.
2. 두 worker의 동시 시작, 소유 worker 종료·재시작, 대기/실행 중 작업 복구를 확인한다. 같은 작업의 중복 빌드·중복 migration·타 worker 소유 작업 회수가 없어야 한다. 종료 때 소유 자식과 DB lock이 정리되는지도 확인한다.
3. DB 준비 경로에서 원래 타입으로 분류된 오류를 보존한다. 명시적인 `DatabaseUnavailable`은 새 preflight 후 retry 대상으로 유지하고, migration 이력 불일치·SQL 실행 실패·미분류 오류는 각각 구분하여 재시도를 허용하지 않는다. 임의 오류 문자열에 포함된 단어로 재시도 권한을 부여하지 않는다.
4. 내부 DB job과 외부 runtime job에 같은 안정된 code를 기록하고 기존 API/CLI의 retry 계약으로 제공한다. SQL 원문·bind 값·DB 접속 문자열·사용자 비밀을 응답에 반영하지 않는다. DB 오류라는 이유만으로 변경 명령을 자동 재전송하지 않는다. 모든 공개 API의 일반 SQL 오류 매핑은 이번 좁은 DB 준비 수정과 구분한다.
5. 변경 관련 단위 검사와 두 feature 경계의 fmt/Clippy, 격리 동시성·오류·기존 lifecycle 회귀를 최종 소스에서 수행한다. 실제 명령·종료코드·통과/실패/ignored·source commit을 연결한 뒤 상태를 갱신한다.

1차의 완료는 scheduler 응답성과 오류 계약의 완료다. 다음 절의 설치 승인 권한, 전체 자원 제한, 백업·복원은 별도다.

## 2차: 설치 승인 권한과 원래 호출자 유지

**현재 상태: 설치/릴리스 승인, 사용자 위임, 원래 호출자와 후속 증표를 구현했다. 상세 계약·전환·실행 한계는 [코어 권한 안내](CORE-PERMISSIONS.md), 실제 결과는 [2차 검증 기록](releases/core-permissions-2026-11-03-validation.json)을 따른다.**

CLI/core 0.7.0, 번들 0.8.0, Rust SDK 0.3.0이다. 기존 설치의 외부 권한은 자동 승인하지 않는다. 부분 승인 상태로 앱을 배포할 수 있으나 미승인 기능은 호출 시 차단한다. 새 릴리스·다른 환경에는 승인을 이월하지 않는다. 사용자 위임의 앱·환경·행위·만료·철회를 작업 큐에 보존하며, 앱 후속 호출은 별도 Core 증표와 모든 호출 단계의 현재 승인을 다시 확인한다. 서비스 계정 발급과 진행 중 부작용의 강제 롤백은 구현하지 않았다.

단위·격리 검사는 현재 정책의 구현 경계를 확인한다. SDK의 loopback HTTP 검사와 Core의 서명 backend fixture 검사를 실제 운영 Docker 네트워크의 전체 인수로 합산하지 않는다. 현재 운영 서버·기존 앱과 게시 CLI는 변경하지 않았다.

[PRD](PRD.md)의 사용자 권한 ∩ 토큰 범위 ∩ 설치 승인 권한 ∩ 대상 정책을 저장 모델과 공통 집행 경로로 연결한다. manifest의 `requestedPermissions`는 앱의 요구이며 설치에 대한 실제 승인으로 자동 취급하지 않는다. 사용자 grant와 앱 설치 승인도 서로 다른 경계다.

완료 기준:

1. 설치·환경별 승인 권한, 승인한 주체·시각·대상 릴리스/범위와 변경 이력을 저장한다. 기존 설치의 migration 정책을 명시하고, 새 릴리스의 권한 증가를 묵시적으로 승인하지 않는다.
2. 읽기·쓰기·공통 directory·다른 앱 호출을 같은 교집합 정책으로 판단한다. 요청했지만 승인하지 않은 권한, 토큰 범위 부족, 사용자 철회, 타 환경/타 설치는 거부한다. 관리자가 허용할 수 있다는 것과 앱이 자동으로 관리자 권한을 갖는 것을 구분한다.
3. 앱 간 호출에 원래 사용자, 호출 앱/설치·릴리스, 환경, 유효한 권한 범위를 유지한다. 대상 앱의 더 강한 자격증명으로 자동 대체하지 않으며 브라우저가 보낸 식별 헤더를 신뢰하지 않는다.
4. 작업 접수 후 권한 회수, 새 릴리스로 권한 증가, 다단계 호출과 타 사용자/환경 위조를 격리 회귀로 확인한다. API/CLI/MCP/SDK에서 동일한 허용·거부와 감사 결과를 확인한다.

이 계약을 공통 기능이 사용할 경계로 먼저 확정한다. miy-v1의 개별 기능 API·UI를 이 단계에서 함께 옮기지는 않는다.

## 3차: 서버 자원 예산과 실행 허용 판단

**현재 상태: 개별 고정 제한은 구현, [CAPACITY](CAPACITY.md)의 전체 정책은 설계·집행 인수 미완료.**

앱 컨테이너의 CPU/RAM 제한은 Docker build와 공유 PostgreSQL의 CPU/RAM 사용을 같은 범위로 제한하지 않는다. 대기 작업 건수 제한도 호스트 RAM·디스크 예약이 아니다. 기본 정책은 OS·core·identity·DB·운영/복구 여유를 먼저 제외하고 앱·빌드·개발 작업을 허용하는 것이다.

완료 기준:

1. 지원 Linux의 cgroup/controller와 실제 집행 가능 여부를 진단한다. 앱·빌드의 메모리/CPU/PID·임시 저장/로그 한도, OOM 후 제한된 복구 정책을 적용한다. 설정값 저장만 된 환경은 정상 지원으로 표시하지 않는다.
2. 자원 예약을 원자적으로 획득하고 완료·실패·중단 후 회수한다. worker 재시작 때 실제 컨테이너·작업과 대조하며, 오래된 측정값·불확실한 호스트 상태에서 새 실행을 제한한다.
3. 업데이트에 필요한 이미지·migration·복구 디스크와 실행 예산을 기존 앱 중지 전에 확인한다. 부족하면 대기/거부하고 기존 서비스를 유지한다. 전체 RAM 상한을 넘는 병렬 입장과 예약 누수를 검사한다.
4. 디스크 바이트·inode·WAL·캐시 증가, DB 연결/쿼리/임시 파일을 측정하고 보호 조치를 정의한다. 템플릿의 작은 연결 풀만으로 DB 부하가 격리된다고 설명하지 않는다. 자동 정리는 활성·복구용 산출물과 운영 데이터를 보존한다.
5. 부하·OOM·PID 초과·디스크 부족을 격리 환경에서 주입하여 문제 작업이 제한되는 동안 코어 관리와 다른 앱이 유지되는지 확인한다. 필요량·허용량·남은 용량·실패 코드와 실제 측정 한계를 같은 API 계약으로 제공한다.

## 4차: 백업·복원과 호스트 코어 updater

**현재 상태: [STACK](STACK.md)의 설계, 수동 설치/갱신과 특정 배포용 파일 복구 이력만 존재. 제품 복구 흐름과 새 서버 복원은 미완료.**

현재의 [서버 실행 안내](RUNNING.md)는 명시적 설정 생성·core migration·서비스 배포 절차를 제공한다. [0.6.3 배포 스크립트 이력](releases/evidence/cli-0.6.3-linux/deploy.py)은 특정 경로의 바이너리·UI·index 복구를 수행한다. 이를 DB migration 복원, 범용 updater, 플랫폼 전체 백업으로 표시하지 않는다. 프로젝트 CLI 파일 transaction의 backup도 별도 기능이다.

완료 기준:

1. 실제 배포한 core/identity/app DB·역할, 설정·암호화/복구 키, artifacts·앱 이미지·소스의 백업 범위와 제외 항목을 manifest로 기록한다. DB와 파일의 정합성 지점, 외부 보관·암호화·보존 기간·필요 여유 공간을 정의한다.
2. 빈 서버·별도 DB/파일 영역에 복원하고 로그인·권한·앱 실행·동일 레코드와 파일 해시를 확인한다. 백업 생성/검증과 실제 복원 성공을 별도 상태로 남긴다. 복구 시간과 데이터 유실 가능 범위도 실제 측정값 또는 미확인으로 표시한다.
3. 코어가 내려가도 실행 가능한 작은 호스트 updater가 대상 출처/digest·앱 계약 호환성·migration·사전 백업을 확인하고, 작업 잠금·신규 작업 진입 제어·단계 journal을 관리한다. 서버 API의 정상 작동에 복구가 종속되지 않게 한다.
4. 바이너리/UI 적용 중단, migration 전/후 실패, 정상 확인 실패와 재부팅을 주입한다. 단계·실제 상태를 대조해 재개하거나 복구 필요 상태로 끝내야 한다. DB와 호환되지 않는 이전 코드의 강제 실행 및 새 쓰기를 잃는 자동 DB 복원은 하지 않는다.

현재 v2의 실제 데이터에 영향을 주는 변경 전에는 해당 범위의 최소 백업과 복구 경로를 확보한다. 이는 기본 UI 이식에 전체 백업 제품이나 updater 완성을 요구하는 조건은 아니다. 실제 저장 서비스가 추가될 때마다 backup manifest와 복원 인수 범위를 함께 확장한다.

## 5차: 새 서버·수명주기 독립 인수

**현재 상태: 앱 개발·배포·부분 복구의 기존 실증은 있으나 아래 새 전체 실행은 NOT_RUN.**

완료 기준:

1. 지원 버전의 빈 Linux 서버에 명시적 origin·TLS·서비스 계정·private 상태·검증한 이미지/바이너리로 설치한다. 설정 생성에 더해 실제 인증·앱 생성·빌드·dev 배포와 API/화면 사용까지 확인한다. 재실행 때 기존 비밀·DB·설치가 보존돼야 한다.
2. 실행 중 앱과 수동 중지 앱을 둔 상태에서 호스트 재부팅·worker 재시작·앱 업데이트·migration 실패·전진 복구를 확인한다. stopped 앱의 자동 시작, 중복 작업, 타 환경 데이터 변경이 없어야 한다.
3. 4차의 백업을 다른 빈 환경에 복원하고 같은 앱·데이터·권한을 재사용한다. 새 담당자가 기록된 절차만으로 진단·복구를 수행할 수 있는지도 확인한다.
4. [VALIDATION](VALIDATION.md)의 V7 반복 조건과 연결해 새 작업공간·세션·설치의 독립 실행을 기록한다. 같은 환경의 재시도를 독립 실행 3회로 집계하지 않으며 수동 보정·실패·NOT_RUN을 보존한다.

Windows 사용자 인수, 실제 콘솔 신호, 다른 OS 또는 Docker Desktop 항목은 수행한 환경의 결과만 인정한다. 사용자에게 미룬 Windows 실행을 Linux/Windows Server CI로 대체하지 않는다.

## 결과 기록과 다음 단계

각 구현 묶음은 다음 정보를 연결한 후 완료 상태를 갱신한다.

| 필드 | 기록 기준 |
| --- | --- |
| 대상 | 구현 묶음 번호, 실제 source commit, 버전·feature·OS·DB/Docker 환경 |
| 실행 | 명령, 시작/종료 시각, 종료코드, 테스트·관찰 개수, 실패/ignored/NOT_RUN |
| 경계 | 실제 서비스 또는 격리 fixture, 실제 Docker build 여부, 합성 오류/실제 장애 구분 |
| 보존·정리 | 소유한 임시 DB/컨테이너/프로세스 정리, 기존 서비스·앱·데이터 영향 |
| 판정 | 완료 기준별 PASS/FAIL/NOT_RUN, 남은 위험, 다음 단계의 선행 조건 |

오류 메시지 원문·토큰·쿠키·접속 문자열·복구 키를 공개 증거에 넣지 않는다. 과거 통과를 새 소스의 통과로 치환하거나, 미실행 결과 파일을 미리 만들지 않는다. 각 단계 상태는 실제 실행 증거의 범위에 맞춰 갱신한다.
