# 코어 안정화 계획

- 작성일: 2026-11-03 · 수정일: 2026-11-14
- 기준: [PLAN](PLAN.md)의 작업 순서. 실제 서버 반영은 [운영 안내](SERVER-OPERATIONS.md), CLI 소스·게시 차이는 [릴리스 안내](CLI-RELEASE.md)에서 확인한다.
- 상태: **1·2차와 구조 기반의 완료한 구현 묶음은 검증·개발 서버 반영했다. API 계약 이전의 나머지 응답, 전체 자원 예약·백업 제품·호스트 updater와 새 서버 종합 인수는 후속이다.**

이 문서는 앱 개발·원격 빌드·배포 기반의 **1) worker/오류, 2) 설치 승인 권한/호출자, 3) 용량, 4) 백업·복원/updater, 5) 새 서버·수명주기 인수** 작업 묶음을 관리한다. 번호는 기존 증거와 연결하기 위해 유지한다. 착수 순서는 [추진 계획](PLAN.md#다음-우선-작업)이 관리한다. 3·4차에는 v1의 Docker 저장소 점검·DB 연결 예산·전환/롤백·불확실한 커밋 처리·설정 스키마 규칙(V1-O1~O5)을, 5차에는 호스트 진단·공개 전 점검·검증 자원 분리(V1-O6~O8)를 함께 적용한다([v1 적용 계획](V1-ADOPTION.md) §3.2).

디스크·DB 연결 보호와 변경 범위의 최소 백업·별도 영역 복원 확인은 구현해 사용하고 있다. 실제 데이터 변경 때마다 이 보호를 수행하며, 전체 백업 제품·호스트 updater·나머지 자원 예약·빈 서버 종합 인수는 베타 전 과제로 구분한다. [사내 최소 보안](APP-BOUNDARIES.md)은 prod 포털·dev 포털·콘솔 세 출처와 목적별 세션·환경 제한·콘솔 device 승인을 구현·반영했다. 별도 IdP·전 credential 재설계·자동 CA·전 앱 전환 도구를 먼저 만들지 않는다. 다음 기능인 공통 ACL 등은 PLAN 순서를 따른다.

2026-11-03 사용자 결정에 따라 1·2차 이후 [기본 UI/UX 이식](V1-ADOPTION.md#9-플랫폼-화면과-ui-후속-계약)을 진행했다. ai-do를 원본으로 라이트 테마·한국어·새 설치 기준의 UI-1~4를 구현하고 UI-5 통합 검증을 마쳤으며, v2.dwdcc.kr에 웹 화면과 0.7.0 서버·migration 17·공개 CLI를 반영했다([배포 기록](releases/core-0.7.0-deployment.json)). 운영·권한 교훈은 공식 miy v1에서 참고하며, 현재 공통 기능·UX의 직접 이식 원본은 [AI-DO 대상 목록](AI-DO-COMMON-MIGRATION.md)을 따른다. 플랫폼의 사용자·그룹별 앱 사용 권한과 앱 내부의 선택적 데이터 공간을 유지한다. 각 기능의 회귀 검사는 계속 수행하고 현재 실행 순서는 [추진 계획](PLAN.md)을 따른다.

운영 서버·UI와 게시 CLI의 현재 배포 소스는 [운영 안내](SERVER-OPERATIONS.md)를 따른다. 문서·소스 수정만으로 후속 배포를 주장하지 않으며 기존 서비스·데이터 보존 경계를 지킨다. 새 인수는 격리 환경에서 수행하고 사용자 Windows 11 검증은 추후 사용자가 수행한다. 현재 절차·출처 검사기는 [Windows 인수](WINDOWS-ACCEPTANCE.md)에 준비했고 실행은 NOT_RUN이다. [0.6.3 인수 기록](archive/results/WINDOWS-0.6.3-ACCEPTANCE.md)은 당시 범위로 보존한다.

## 1차: worker 제어·빌드 실행 분리와 DB 오류 계약

**현재 상태: 구현과 아래 단위·격리 통합 회귀 통과, 구현분 운영 반영. 이 절의 과거 검사 결과를 전체 코어 완료나 새 범위의 인수로 확대하지 않는다.**

착수 시점의 [worker](../crates/miy/src/worker.rs)는 제어 순회에서 `server_build_worker::tick`을 await하고 빌드 완료까지 기다렸다. [빌드 worker](../crates/miy/src/server_build_worker.rs)의 컴파일 제한 시간은 1,800초다. 이 구조에서는 빌드 중 다음 제어·reconcile 순회가 지연될 수 있다. HTTP 관찰 task가 별도라는 사실만으로 앱 stop/start 처리 지연이 해결되지는 않는다.

빌드와 제어는 같은 워커 소유권 아래 서로 다른 future로 실행한다. 별도 감시가 소유권 연결을 1초마다 확인하며 검사 제한시간은 3초다. 연결 유실·분기 실패·종료 신호 시 다른 분기를 취소하고 기존 Docker 클라이언트 정리 경로를 사용한다. 빌드 복구 잠금을 얻지 못하면 제어를 막지 않고 복구를 재시도한다. 동기 파일 검증은 future 취소 후에도 계속될 수 있으므로 실행별 임시 경로와 Arc 수명으로 분리했다. DB 준비·이미지 import·runtime 제어 사이의 기존 처리 순서는 유지한다.

완료 기준:

1. 격리 fixture에서 빌드를 의도적으로 대기시킨 상태로 다른 앱 stop/start·상태 대조를 요청한다. **빌드 대기를 해제하기 전에** 제어 작업이 완료되고, 미리 정한 제한 시간 안에 결과가 관찰돼야 한다. API 요청 접수만으로 통과시키지 않는다.
2. 두 worker의 동시 시작, 소유 worker 종료·재시작, 대기/실행 중 작업 복구를 확인한다. 같은 작업의 중복 빌드·중복 migration·타 worker 소유 작업 회수가 없어야 한다. 종료 때 소유 자식과 DB lock이 정리되는지도 확인한다.
3. DB 준비 경로에서 원래 타입으로 분류된 오류를 보존한다. 명시적인 `DatabaseUnavailable`은 새 preflight 후 retry 대상으로 유지하고, migration 이력 불일치·SQL 실행 실패·미분류 오류는 각각 구분하여 재시도를 허용하지 않는다. 임의 오류 문자열에 포함된 단어로 재시도 권한을 부여하지 않는다.
4. 내부 DB job과 외부 runtime job에 같은 안정된 code를 기록하고 기존 API/CLI의 retry 계약으로 제공한다. SQL 원문·bind 값·DB 접속 문자열·사용자 비밀을 응답에 반영하지 않는다. DB 오류라는 이유만으로 변경 명령을 자동 재전송하지 않는다. 모든 공개 API의 일반 SQL 오류 매핑은 1차의 좁은 DB 준비 보완과 구분한다.
5. 변경 관련 단위 검사와 두 feature 경계의 fmt/Clippy, 격리 동시성·오류·기존 lifecycle 회귀를 최종 소스에서 수행한다. 실제 명령·종료코드·통과/실패/ignored·source commit을 연결한 뒤 상태를 갱신한다.

1차의 완료는 scheduler 응답성과 오류 계약의 완료다. 다음 절의 설치 승인 권한, 전체 자원 제한, 백업·복원은 별도다.

### 2026-11-03 실행 결과

`9967265`의 [구조화 증거](releases/core-hardening-2026-11-03-validation.json)에 구현 파일·로그 hash, 명령, 세부 관찰과 한계를 보존한다. 당시 서버 단위 152 PASS/6 ignored, 클라이언트 110 PASS, 두 feature 정적 검사와 실제 PostgreSQL·Docker 격리 58개 관찰이 PASS였다. 빌드 잠금 중 제어 진행, 소유권 상실·후속 worker 복구, SIGTERM 종료·lock 정리와 SQL 실패의 retry 금지·데이터 보존을 확인했다. 로컬 검사는 commit 전 작업본이며 기록한 구현 파일과 해당 commit의 바이트 일치를 확인한 결과다.

이 동시성 인수는 실제 worker·PostgreSQL의 잠금 대기를 사용했다. 실제 장시간 Rust Docker 컴파일 중 지연 측정과 provision DB 네트워크 장애 주입은 NOT_RUN이다. SIGKILL에는 RAII가 실행되지 않아 임시 경로가 남을 수 있으며 자동 정리는 3차 용량 정책 범위다. 설치 승인 권한·자원 예산·백업·updater·새 호스트 전체 인수를 이 실행의 완료로 합치지 않는다.

## 2차: 설치 승인 권한과 원래 호출자 유지

**현재 상태: 인증된 connections 경로의 설치/릴리스 승인·사용자 위임·원래 호출자·후속 증표를 구현·반영했다.** 최초 [2차 검증](releases/core-permissions-2026-11-03-validation.json)은 backend 경로의 증거다. 이후 업무 앱 프레임을 도입해 브라우저의 직접 API도 자기 설치로 제한하고 다른 앱은 승인된 연결로만 호출한다. 원 프레임·첫 호출자·릴리스 결합 보완은 [2026-11-12 리뷰 보완 검증](releases/app-frames-review-fixes-2026-11-12-validation.json)과 [배포 기록](releases/app-frames-review-fixes-2026-11-12-deployment.json)을 따른다. 과거 같은 페이지 MF의 한계와 새 프레임의 검증 범위를 합치지 않는다. 상세 계약은 [코어 권한](CORE-PERMISSIONS.md)이 관리한다.

최초 2차 도입은 CLI/core 0.7.0, 번들 0.8.0, Rust SDK 0.3.0 기준이었다. 기존 설치의 외부 권한은 자동 승인하지 않는다. 부분 승인 상태로 앱을 배포할 수 있으나 미승인 기능은 호출 시 차단한다. 새 릴리스·다른 환경에는 승인을 이월하지 않는다. 사용자 위임의 앱·환경·행위·만료·철회를 작업 큐에 보존하며, 앱 후속 호출은 별도 Core 증표와 모든 호출 단계의 현재 승인을 다시 확인한다. 서비스 계정 발급과 진행 중 부작용의 강제 롤백은 구현하지 않았다.

단위·격리 검사는 해당 소스의 구현 경계를 확인한다. SDK의 loopback HTTP 검사와 Core의 서명 backend fixture 검사를 실제 운영 Docker 네트워크의 전체 인수로 합산하지 않는다. 최초 2차 소스 검증 당시에는 운영 서버·기존 앱과 게시 CLI를 변경하지 않았으며, 후속 반영 여부는 위 배포 기록과 [운영 안내](SERVER-OPERATIONS.md)를 따른다.

[PRD](PRD.md)의 사용자 권한 ∩ 토큰 범위 ∩ 설치 승인 권한 ∩ 대상 정책을 저장 모델과 공통 집행 경로로 연결한다. manifest의 `requestedPermissions`는 앱의 요구이며 설치에 대한 실제 승인으로 자동 취급하지 않는다. 사용자 grant와 앱 설치 승인도 서로 다른 경계다.

완료 기준:

1. 설치·환경별 승인 권한, 승인한 주체·시각·대상 릴리스/범위와 변경 이력을 저장한다. 기존 설치의 migration 정책을 명시하고, 새 릴리스의 권한 증가를 묵시적으로 승인하지 않는다.
2. 읽기·쓰기·공통 directory·다른 앱 호출을 같은 교집합 정책으로 판단한다. 요청했지만 승인하지 않은 권한, 토큰 범위 부족, 사용자 철회, 타 환경/타 설치는 거부한다. 관리자가 허용할 수 있다는 것과 앱이 자동으로 관리자 권한을 갖는 것을 구분한다.
3. 앱 간 호출에 원래 사용자, 호출 앱/설치·릴리스, 환경, 유효한 권한 범위를 유지한다. 대상 앱의 더 강한 자격증명으로 자동 대체하지 않으며 브라우저가 보낸 식별 헤더를 신뢰하지 않는다.
4. 작업 접수 후 권한 회수, 새 릴리스로 권한 증가, 다단계 호출과 타 사용자/환경 위조를 격리 회귀로 확인한다. API/CLI/MCP/SDK에서 동일한 허용·거부와 감사 결과를 확인한다.

이 계약을 공통 기능이 사용할 경계로 먼저 확정한다. miy-v1의 개별 기능 API·UI를 이 단계에서 함께 옮기지는 않는다.

## 3차: 서버 자원 예산과 실행 허용 판단

**현재 상태: 개별 고정 제한은 구현, [CAPACITY](CAPACITY.md)의 전체 정책은 설계·집행 인수 미완료.**

앱 컨테이너의 CPU/RAM 제한은 Docker build와 공유 PostgreSQL의 CPU/RAM 사용을 같은 범위로 제한하지 않는다. 대기 작업 건수 제한도 호스트 RAM·디스크 예약이 아니다. 기본 정책은 OS·core·identity·DB·운영/복구 여유를 먼저 제외하고 앱·빌드·개발 작업을 허용하는 것이다.

완료 기준:

1. 지원 Linux의 cgroup/controller와 실제 집행 가능 여부를 진단한다. 앱·빌드의 메모리/CPU/PID·임시 저장/로그 한도, OOM 후 제한된 복구 정책을 적용한다. 설정값 저장만 된 환경은 정상 지원으로 표시하지 않는다.
2. 자원 예약을 원자적으로 획득하고 완료·실패·중단 후 회수한다. worker 재시작 때 실제 컨테이너·작업과 대조하며, 오래된 측정값·불확실한 호스트 상태에서 새 실행을 제한한다.
3. 업데이트에 필요한 이미지·migration·복구 디스크와 실행 예산을 기존 앱 중지 전에 확인한다. 부족하면 대기/거부하고 기존 서비스를 유지한다. 전체 RAM 상한을 넘는 병렬 입장과 예약 누수를 검사한다.
4. 디스크 바이트·inode·WAL·캐시 증가, DB 연결/쿼리/임시 파일을 측정하고 보호 조치를 정의한다. 템플릿의 작은 연결 풀만으로 DB 부하가 격리된다고 설명하지 않는다. 자동 정리는 활성·복구용 산출물과 운영 데이터를 보존한다.
5. 부하·OOM·PID 초과·디스크 부족을 격리 환경에서 주입하여 문제 작업이 제한되는 동안 코어 관리와 다른 앱이 유지되는지 확인한다. 필요량·허용량·남은 용량·실패 코드와 실제 측정 한계를 같은 API 계약으로 제공한다.

## 4차: 백업·복원과 호스트 코어 updater

**현재 상태: core DB의 변경 범위 백업·별도 영역 복원 확인과 core/UI 반영·복구 도구를 구현해 실제 배포에 사용했다. 전체 플랫폼·앱 DB·파일을 묶는 백업 제품, 범용 호스트 updater와 새 서버 종합 복원은 미완료다.** 현재 도구와 실제 적용 범위는 [운영 안내](SERVER-OPERATIONS.md#6-변경-전-최소-백업과-복원-확인)를 따른다.

현재의 [서버 실행 안내](RUNNING.md)는 명시적 설정 생성·core migration·서비스 배포 절차를 제공한다. [0.6.3 배포 스크립트 이력](releases/evidence/cli-0.6.3-linux/deploy.py)은 특정 경로의 바이너리·UI·index 복구를 수행한다. 이를 DB migration 복원, 범용 updater, 플랫폼 전체 백업으로 표시하지 않는다. 프로젝트 CLI 파일 transaction의 backup도 별도 기능이다.

완료 기준:

1. 실제 배포한 core/identity/app DB·역할, 설정·암호화/복구 키, artifacts·앱 이미지·소스의 백업 범위와 제외 항목을 manifest로 기록한다. DB와 파일의 정합성 지점, 외부 보관·암호화·보존 기간·필요 여유 공간을 정의한다.
2. 빈 서버·별도 DB/파일 영역에 복원하고 로그인·권한·앱 실행·동일 레코드와 파일 해시를 확인한다. 백업 생성/검증과 실제 복원 성공을 별도 상태로 남긴다. 복구 시간과 데이터 유실 가능 범위도 실제 측정값 또는 미확인으로 표시한다.
3. 코어가 내려가도 실행 가능한 작은 호스트 updater가 대상 출처/digest·앱 계약 호환성·migration·사전 백업을 확인하고, 작업 잠금·신규 작업 진입 제어·단계 journal을 관리한다. 서버 API의 정상 작동에 복구가 종속되지 않게 한다.
4. 바이너리/UI 적용 중단, migration 전/후 실패, 정상 확인 실패와 재부팅을 주입한다. 단계·실제 상태를 대조해 재개하거나 복구 필요 상태로 끝내야 한다. DB와 호환되지 않는 이전 코드의 강제 실행 및 새 쓰기를 잃는 자동 DB 복원은 하지 않는다.

현재 v2의 실제 데이터에 영향을 주는 변경 전에는 해당 범위의 최소 백업을 만들고 별도 DB·파일 영역에 복원하여 필요한 데이터와 키의 복구 가능성을 확인한다. 이 선행 보호와 베타 전 전체 백업 제품·호스트 updater·빈 서버 종합 복원 인수는 구분한다. 실제 저장 서비스가 추가될 때마다 backup manifest와 복원 인수 범위를 함께 확장한다.

## 5차: 새 서버·수명주기 독립 인수

**현재 상태: 앱 개발·배포·부분 복구의 기존 실증은 있으나 아래 새 전체 실행은 NOT_RUN.**

완료 기준:

1. 지원 버전의 빈 Linux 서버에 명시적 origin·TLS·서비스 계정·private 상태·검증한 이미지/바이너리로 설치한다. 설정 생성에 더해 실제 인증·앱 생성·빌드·dev 배포와 API/화면 사용까지 확인한다. 재실행 때 기존 비밀·DB·설치가 보존돼야 한다.
2. 실행 중 앱과 수동 중지 앱을 둔 상태에서 호스트 재부팅·worker 재시작·앱 업데이트·migration 실패·전진 복구를 확인한다. stopped 앱의 자동 시작, 중복 작업, 타 환경 데이터 변경이 없어야 한다.
3. 4차의 백업을 다른 빈 환경에 복원하고 같은 앱·데이터·권한을 재사용한다. 새 담당자가 기록된 절차만으로 진단·복구를 수행할 수 있는지도 확인한다.
4. [승계한 V7 반복 조건](APP-BOUNDARIES.md#기존-검증의-승계)과 연결해 새 작업공간·세션·설치의 독립 실행을 기록한다. 같은 환경의 재시도를 독립 실행 3회로 집계하지 않으며 수동 보정·실패·NOT_RUN을 보존한다.

Windows 사용자 인수, 실제 콘솔 신호, 다른 OS 또는 Docker Desktop 항목은 수행한 환경의 결과만 인정한다. 사용자에게 미룬 Windows 실행을 Linux/Windows Server CI로 대체하지 않는다.

## 구조 기반

회귀 상시화·권한 판정 단일화·API 계약 단일 원본이다. **완료 범위: 1의 회귀 workflow·일반 `core-rollout.py` 정확한 SHA CI gate, 2·4. 3은 첫 묶음과 리뷰 보완까지다.** 2026-11-05 후속 리뷰에서 드러난 권한·API 불일치와 CI 실패 중 배포의 구조적 원인을 정리했다. 완료분은 [PLAN의 완료 요약](PLAN.md#완료한-작업)의 "구조 기반·최소 데이터 보호"에, 나머지 API 계약은 [일부 구현된 작업](PLAN.md#일부-구현된-작업)에 연결한다. 해당 기능을 변경할 때의 착수 순서는 [통합 작업표](PLAN.md#다음-우선-작업)를 따른다.

완료 기준:

1. **회귀 상시화**
   - 격리 runtime 회귀(`scripts/runtime-regression/run.py`)를 GitHub Actions에서 main push마다 실행한다. 정해진 suite별 관찰 수와 전 관찰 PASS로 판정하고, hosted runner의 실행 시간과 Docker 저장 공간 하한 충족을 기록한다.
   - 운영 반영 도구가 대상 commit의 필수 workflow 성공을 확인하고, 실패·미완료면 반영 전에 멈춘다. 예외로 진행하면 그 이유를 보고서에 남긴다.
2. **권한 판정 단일화**
   - 주체(사용자 세션·CLI·위임·앱 후속 호출, 이후 서비스 계정)·대상·동작의 판정을 정책 모듈 하나가 제공한다. 결과는 거부 이유를 가진 타입이다. 호출부는 동작을 지정할 뿐 판정 함수를 고르지 않는다.
   - 목록 노출 SQL 조건과 응답의 가능 여부 표시값(`canManage`·`canPromote`·`canOpen`)을 같은 정의에서 만들고, 표시값의 의미를 문서화한다.
   - 쓰기는 트랜잭션 안에서 대상 잠금 후 판정한 결과로만 진행한다. 관리자 재확인과 실행 접수 재판정을 일반화한 것이다.
   - 상세 판정·목록 노출·표시값이 주체·권한·회사 사용 중지·환경·위임 동작의 모든 조합에서 일치하는지 실제 PostgreSQL 행렬 시험으로 확인한다. 동작을 바꾸지 않는 정리는 기존 격리 회귀(관찰 87개)를 그대로 통과해야 한다.
3. **API 계약 단일 원본**
   - 공개 API 응답을 Rust 구조체로 정의하고 JSON Schema를 내보낸다. 설치 목록·실행 작업·감사·그룹부터 시작한다.
   - SDK·플랫폼 TS 타입을 그 schema에서 생성하고, 생성물이 어긋나면 CI가 실패한다. CLI도 같은 구조체로 응답을 읽는다.
   - 게시된 CLI가 읽는 필드의 호환 규칙(추가만 허용, 제거는 유예 후)을 정하고 검사한다.
4. **CLI 버전 일치(V1-Q4 확장):** 게시 CLI의 source 이후 클라이언트 빌드에 들어가는 코드가 바뀌었는데 버전이 같으면 검사가 실패한다.

| 9 | 기본·페이지·실행 관리 설치 목록과 앱 상세를 같은 SQL 행/응답 타입으로 통합 | 위 3의 API 계약 첫 묶음 |

쓰기는 행위자·위임 행을 커밋까지 공유 잠금하고 권한 사실·위임 유효 상태를 한 SELECT로 읽는다. 필요한 잠금 대기 뒤 새 스냅샷으로 판정하며, 직접 트랜잭션·주체 쓰기의 우회는 `scripts/check-write-decisions.py`가 검사한다. 위임 발급 잠금 순서·HTTP/worker 동시성, API 숫자 범위·UUID/날짜 형식 검사 등의 후속 보완과 이전 실패·남은 환경 검사는 [구조 기반 리뷰 보완 기록](releases/core-foundation-review-2026-11-06-validation.json)에 보존한다.

현재 API 호환 검사기는 [게시 계약](../contracts/api-v1.published.json)의 필드 제거·필수 해제·값 확장을 검사하고, 제거 근거는 `removable`에 기록한다. 이 구현을 개발 단계 전체의 하위 호환 의무로 확대하지 않는다. 계약을 끊는 변경은 개발 단계 원칙에 따라 새 버전의 CLI·SDK·웹·문서를 함께 갱신하고 게시된 바이트는 유지한다.

보류한 것:
- core/CLI crate 분리: 클라이언트도 로컬 preview·MCP에 axum·sqlx·rmcp를 쓴다. 3의 계약 타입을 별도 모듈로 모으는 데까지만 한다.
- OS별 분기 정리: 대부분 원래 OS마다 다른 모듈이고, cfg 실수는 Windows CI가 검사한다.

## 결과 기록과 다음 단계

각 구현 묶음은 다음 정보를 연결한 후 완료 상태를 갱신한다.

| 필드 | 기록 기준 |
| --- | --- |
| 대상 | 구현 묶음 번호, 실제 source commit, 버전·feature·OS·DB/Docker 환경 |
| 실행 | 명령, 시작/종료 시각, 종료코드, 테스트·관찰 개수, 실패/ignored/NOT_RUN |
| 경계 | 실제 서비스 또는 격리 fixture, 실제 Docker build 여부, 합성 오류/실제 장애 구분 |
| 보존·정리 | 소유한 임시 DB/컨테이너/프로세스 정리, 기존 서비스·앱·데이터 영향 |
| 판정 | 완료 기준별 PASS/FAIL/NOT_RUN, 남은 위험, 다음 단계의 선행 조건 |

오류 메시지 원문·토큰·쿠키·접속 문자열·복구 키를 공개 증거에 넣지 않는다. 과거 통과를 새 소스의 통과로 치환하거나, 미실행 결과 파일을 미리 만들지 않는다. 각 단계 상태는 실제 실행 증거의 범위에 맞춰 갱신한다.
