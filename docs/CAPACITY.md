# miy 인프라 용량 관리와 효율화 계획

작성일: 2026-10-20  
수정일: 2026-10-21  
기준: PRD 0.5  
상태: 설계 기본안 · 자원 수치와 지원 규모는 파일럿에서 결정

**서버 전체의 여유를 먼저 확보하고, 앱별 한도·실행 전 용량 확인·초과 대응을 함께 적용한다.** CPU·메모리, 파일, DB는 제한하는 방법과 보장 범위가 다르다. 기업별 단일 Linux 서버·VM에서 시작하며 사내·클라우드에 같은 관리 원칙을 적용한다.

[PRD](PRD.md)의 자원 요구사항, [개발 계획](DEVELOPMENT.md)의 앱·DB 계약, [기술 스택](STACK.md)의 Rust runner·Docker·PostgreSQL 구성을 구체화한다. 현재는 문서 설계이며 실제 서버 설정을 변경하지 않는다.

## 관리 주체와 실행 흐름

Rust 코어에 용량·정책 판단 기능을 두고, 내부 runner가 호스트·컨테이너 상태 수집과 승인된 실행 제어를 담당한다. Storage API는 파일 예약·사용량을, DB 관리 기능은 DB 크기·연결·작업 상태를 제공한다. 별도 범용 오케스트레이터 도입을 초기 전제로 삼지 않는다.

```text
사용량 수집 → 서버·앱별 예산과 비교 → 새 실행의 용량 확인
                                      ├─ 충분: 자원 예약 후 실행
                                      └─ 부족: 대기 또는 거부
실행 중 감시 → 한도 집행·경보·필요한 중지 → 여유 확인 후 복구
```

앱 제작자는 필요한 자원을 선언하고, 고객사 또는 위임받은 운영자가 허용 범위를 정한다. 실제 값은 설치·앱·환경에 귀속한다. 앱 코드가 자신의 한도를 임의 변경할 수 없게 하며 변경 이력과 수행자를 기록한다.

## 자원별 제한 방식

| 자원 | 관리 기준과 집행 위치 | 한도 도달 시 동작 |
| --- | --- | --- |
| 앱 CPU | 컨테이너 CPU 시간 상한과 실행 그룹의 우선순위 | 실행 속도 조절, 신규 무거운 작업 대기 |
| 앱 메모리 | 컨테이너 메모리·swap 정책, API·작업을 합친 환경 예산 | OOM 상태 기록, 제한된 재시작·재시도와 진단 |
| 프로세스·동시 작업 | 프로세스 수, 앱·환경·서버별 실행 슬롯 | 신규 생성·실행 거부 또는 대기 |
| 업무 파일 | Storage API의 예약량·사용량·파일 수, 실제 저장 장치 여유 | 한도를 넘는 신규 업로드 거부 |
| 임시 파일·로그·빌드 캐시 | 제한된 임시 영역, 로그 회전, 캐시 보존 상한 | 정책에 따른 정리, 신규 빌드·작업 제한 |
| 앱 DB 저장량 | DB별 물리 크기·증가 추세의 관리 한도 | 경보, 배포·작업 제한, 필요 시 해당 앱의 DB 접근 중단 |
| DB 처리 부하 | 역할별 연결 수, 쿼리·트랜잭션·임시 파일 관리 | 연결 대기·거부, 오래 실행되는 작업 취소·진단 |
| 서버 전체 디스크 | 실제 여유 바이트·inode·증가 속도·복구 여유 | 신규 저장·빌드·미리보기 제한, 운영자 조치 |
| 디스크 I/O | 지연·처리량·대기 상태, 지원 호스트의 I/O 제어 | 빌드·백업·일괄 처리 동시 실행 축소 |

Docker는 기본적으로 컨테이너 자원을 제한하지 않으므로 runner가 실행 설정을 반드시 지정한다. CPU 상한은 사용할 수 있는 CPU 시간의 최대치이며 특정 물리 코어의 독점 할당이나 최소 성능 보장은 아니다. 메모리 상한 초과는 해당 컨테이너의 프로세스 종료로 이어질 수 있다. [Docker 자원 제한](https://docs.docker.com/engine/containers/resource_constraints/)

Rootless Docker의 자원 제한에는 cgroup v2·systemd와 필요한 controller 위임이 필요하다. 호스트 설치 진단에서 지원 여부와 실제 제한 동작을 확인하고, 적용되지 않는 옵션을 저장만 한 상태로 배포하지 않는다. [Docker Rootless 자원 제한](https://docs.docker.com/engine/security/rootless/tips/#limiting-resources)

## 서버 전체 예산과 실행 전 확인

앱에 사용할 수 있는 메모리는 전체 RAM에서 OS·기반 서비스와 운영·복구 여유를 제외해 산정한다. 기반 서비스에는 miy API, 인증, PostgreSQL, Gitea, Hermes 런타임과 내부 제어 기능이 포함된다.

```text
앱 실행 예산 = 호스트 용량 − 기반 서비스 예산 − 운영·복구 여유
활성 앱 + 실행 중 작업 + 빌드 + 미리보기의 예약량 ≤ 앱 실행 예산
```

초기 메모리 배정은 동시에 실행할 인스턴스의 상한을 기준으로 보수적으로 계산한다. 측정한 평균 사용량만으로 최대치를 초과 배정하지 않는다. 이 예약은 miy의 실행 허용 판단이며 Docker의 soft memory reservation을 물리 RAM 확보로 해석하지 않는다.

CPU는 앱별 상한과 전체 작업 그룹의 상한·우선순위를 함께 조정한다. 한도를 높여도 호스트 CPU가 늘어나는 것은 아니다. 지연과 CPU 제한 발생률을 관측하여 작업 동시 실행 수를 정한다.

디스크 용량이 충분해도 I/O가 포화되면 모든 앱이 느려질 수 있다. DB·백업·빌드의 동시 접근과 저장 장치 지연을 측정하고, 지원되는 호스트에서는 I/O 제어를 적용한다. 지원하지 않는 환경에서는 실행 슬롯·작업 시간 분산으로 부하를 조절한다.

새 앱, 잠든 앱의 재기동, 빌드, 미리보기, 작업, 백업·복원, 업데이트 전에 실행 예산과 현재 여유를 확인한다. 기본 업데이트는 일시 중단을 허용하여 기존 앱을 종료한 뒤 새 버전을 시작하므로 신구 앱의 동시 실행 RAM을 요구하지 않는다. 기존·새 이미지와 복구용 산출물의 디스크, migration·인덱스·백업의 임시 공간, 새 버전의 자원 한도와 복구 여유는 별도로 확보한다. 기존 실행 종료를 확인한 뒤 예약을 전환하고 그 용량을 다른 작업이 선점하지 않게 한다. 용량이 부족하면 앱을 중지하기 전에 배포를 대기·거부한다.

예약과 슬롯 획득은 원자적으로 처리하고 작업 실패·runner 재시작 후 실제 실행 상태와 대조하여 회수한다. 측정값이 오래되었거나 호스트 상태를 확인할 수 없으면 신규 실행을 보수적으로 제한한다.

API 요청, 예약 작업, 빌드, 문서 처리와 Hermes 실행은 동시 실행 한도를 구분한다. 무거운 빌드·색인·일괄 처리는 우선순위를 낮추고, 특정 앱의 작업이 다른 앱의 대기열을 계속 독점하지 않도록 한다.

## 파일과 서버 디스크

파일 업로드는 시작 시 공간을 예약하고 실제 기록 바이트를 확인한 뒤 사용량으로 확정한다. 병렬 업로드도 같은 예산에서 차감하며 실패·중단 시 예약과 불완전 파일을 정리한다. 파일 크기뿐 아니라 파일 수와 inode도 관리한다. S3 backend도 miy의 파일 API 계약과 사용량 검사를 거치게 한다.

서버 디스크에는 다음 항목을 따로 표시한다.

- 앱 업무 파일과 업로드·변환 중인 임시 파일.
- 앱 DB의 테이블·인덱스·대용량 값 저장 영역.
- PostgreSQL 공통 WAL, 임시 작업·유지관리 공간.
- Git 저장소, 배포 이미지·패키지와 빌드 캐시.
- 컨테이너 로그, 감사 기록·메트릭, 로컬 백업 준비 공간.

공유 이미지 계층 등을 앱마다 중복 합산하지 않고 공통 사용량과 앱 귀속량을 구분한다. 논리적 파일 크기와 물리 저장량의 차이를 고려하여 서버의 실제 여유도 별도로 확인한다. 설치 환경이 지원하면 업무 파일·DB·빌드 캐시의 볼륨을 분리해 한 영역의 증가가 다른 영역을 채우는 위험을 줄인다.

앱 컨테이너의 코드 영역은 읽기 전용으로 유지하고 임시 쓰기 공간만 제공한다. 메모리 기반 임시 공간도 메모리 예산에 포함한다. Docker 볼륨에 앱별 용량 제한이 자동 적용된다고 가정하지 않으며, 업무 파일은 Storage API를 통과하게 한다.

로그는 크기·보존 기간으로 회전시키고, 빌드 캐시는 크기·사용 시점에 따라 정리한다. Docker의 로그 회전과 BuildKit GC를 기반 기능으로 활용하되, 활성 릴리스·보존 대상 롤백 이미지·진행 중 빌드의 파일은 보호한다. [Docker local 로그](https://docs.docker.com/engine/logging/drivers/local/), [BuildKit GC](https://docs.docker.com/build/cache/garbage-collection/)

디스크 경보는 사용률뿐 아니라 남은 바이트·inode, 증가 추세, 예정된 작업에 필요한 공간을 함께 본다. 예측된 고갈 시점은 추정치로 표시한다. 백업은 기존 방침대로 별도 저장 위치에 보관하고, 전송 전 로컬에 만드는 임시 사본도 예산에 반영한다.

## PostgreSQL 공유 구성의 한계와 보호

### DB별 저장량

초기 구조는 한 PostgreSQL 인스턴스 안에 코어·앱·환경별 DB를 두는 방식이다. 표준 구성에서 DB마다 `5 GiB` 같은 강제 디스크 상한을 지정할 수 있다고 설계하지 않는다. `pg_database_size`로 DB의 물리 사용량을 측정하고, 별도로 WAL·임시 파일·전체 저장 장치 여유를 관측한다. 앱의 논리 DB 크기만 합산해서 서버 전체 공간으로 취급하지 않는다. [PostgreSQL 크기 측정](https://www.postgresql.org/docs/current/functions-admin.html#FUNCTIONS-ADMIN-DBSIZE), [DB 생성 설정](https://www.postgresql.org/docs/current/sql-createdatabase.html)

앱별 DB 용량에는 경보선과 접근 중단선을 둔다. 초기에는 주기적인 측정과 운영 정책을 이용하는 관리 한도이며, 감지·중단 전의 트랜잭션이나 인덱스 생성으로 한도를 초과할 수 있다. 큰 데이터 반입·마이그레이션은 실행 전 별도 용량 검사를 수행하지만 실제 증가량을 정확하게 사전 보장하지는 않는다.

중단선이나 서버 보호 기준을 넘으면 해당 앱의 신규 요청·작업·마이그레이션을 막는다. 앱 백엔드가 DB에 직접 접근하므로 SDK에서 쓰기 버튼을 막는 것만으로 충분하지 않다. 필요 시 앱 실행을 중지하고 해당 실행 역할의 신규 DB 접속 차단과 기존 세션 종료를 확인한다. 코어·복구용 접근은 유지하고, 앱 조회까지 중단될 수 있는 서비스 영향을 표시한다.

`default_transaction_read_only` 같은 기본값만으로 강제 쓰기 차단을 구현하지 않는다. 조회를 유지하는 제한 모드는 별도 역할·접근 경로의 검증 후 제공한다. 복구 시 남은 용량·역할·실행 상태를 확인하고 정책에 따라 재개한다.

### DB의 CPU와 메모리

앱 컨테이너의 CPU·메모리 제한은 공유 PostgreSQL 내부에서 수행되는 쿼리에 같은 비율로 적용되지 않는다. 따라서 다음 항목을 함께 관리한다.

- 앱·환경별 작은 연결 풀과 DB·역할의 연결 제한. 코어·관리·복구용 연결 여유 보존.
- 요청 쿼리, 긴 작업, 마이그레이션을 구분한 실행 시간·잠금 대기·유휴 트랜잭션 기준.
- 쿼리 작업 메모리, 임시 파일, 병렬 처리와 유지관리 작업의 동시 실행 수.
- 느린 쿼리·잠금·임시 파일 증가를 식별하고 취소·중지할 수 있는 운영 경로.

`work_mem`은 DB 전체나 한 연결 전체의 메모리 상한이 아니며 여러 연산·세션·병렬 작업에서 누적될 수 있다. `temp_file_limit`도 프로세스의 특정 임시 파일에 대한 제한으로, 앱 DB 저장량 전체를 제한하지 않는다. `statement_timeout` 등 앱 세션에서 바꿀 수 있는 설정은 절대적인 격리 경계로 설명하지 않는다. [PostgreSQL 자원 설정](https://www.postgresql.org/docs/current/runtime-config-resource.html), [연결 기본값](https://www.postgresql.org/docs/current/runtime-config-client.html)

앱 수가 증가하여 연결 비용이 문제가 되면 PgBouncer를 검토한다. DB·사용자별 서버 연결 상한을 설정하고, 앱이 풀을 우회하지 못하게 연결 경로를 관리한다. 트랜잭션 풀 모드의 세션 기능·ORM·마이그레이션 호환성은 별도로 확인한다. 처음부터 연결 풀 하나를 추가하는 것만으로 DB 부하가 해결된다고 가정하지 않는다. [PgBouncer 설정](https://www.pgbouncer.org/config.html)

### 강한 격리가 필요한 경우

공유 PostgreSQL에서는 앱별 접근을 분리해도 DB 처리 자원과 장애 영향이 남는다. 문제가 반복되거나 엄격한 용량·성능 경계가 필요한 앱은 별도 PostgreSQL 인스턴스와 저장 볼륨·자원 한도를 갖는 프로필 또는 외부 DB로 이동하는 방안을 후속 검토한다. 동일 호스트의 별도 인스턴스도 물리 디스크·호스트 장애까지 분리하지는 않는다.

DB 파일에 임의 파일시스템 한도를 걸어 오류가 발생하게 하는 방법을 정상적인 앱 용량 관리로 대체하지 않는다. 디스크 부족은 PostgreSQL의 정상 작업을 막을 수 있으므로 고갈 전에 제한·증설·복구 조치를 수행한다. [PostgreSQL 디스크 관리](https://www.postgresql.org/docs/current/diskusage.html)

## 효율화 순서

| 순서 | 적용할 방법 | 확인할 효과와 조건 |
| --- | --- | --- |
| 1 | 기본 서비스 예산, 앱·빌드·작업 한도, 작은 DB 연결 풀 | 폭주·동시 실행 과다로 인한 중단 방지 |
| 2 | 만료 미리보기 종료, 로그·캐시·불완전 업로드 정리 | 사용하지 않는 메모리·디스크 회수 |
| 3 | 동일 기반 이미지·의존성 캐시 재사용, 검증한 이미지의 운영 승격 | 반복 빌드·저장·전송 비용 감소 |
| 4 | 페이지 조회, 필요한 컬럼만 조회, 쿼리·인덱스 개선, 배치 처리 | 쿼리 시간·전송량·잠금·임시 공간 감소 |
| 5 | 변경된 문서만 색인·임베딩 생성, 중복 작업 방지, 예약 작업 시간 분산 | AI·CPU·DB 작업량 감소 |
| 6 | 지원 앱의 유휴 중지·요청 시 재기동, 필요 시 PgBouncer | 상시 메모리·연결 비용 감소와 초기 응답 지연의 균형 |
| 7 | 측정에 따른 VM 증설·저장 장치 확장·무거운 기능 분리 | 단일 서버의 지속적인 병목 해소 |

첫 출시에서는 한도와 정리를 먼저 구현한다. 빌드 동시 실행 `1` 같은 보수적인 시작값을 후보로 검증하고, 실제 CPU·메모리·I/O 여유에 따라 늘린다. 앱 API와 작업의 실행 프로세스는 분리하며, 효율화를 위해 서로 다른 앱의 코드·비밀값을 하나의 공유 프로세스에 넣지 않는다.

유휴 중지는 개발 미리보기부터 적용을 검토한다. 운영 앱은 적합한 프로필에서 선택적으로 제공하고, 첫 요청 대기·시작 실패·동시 재기동 방지·작업 종료를 검증한다. WebSocket·장시간 연결·상시 서비스가 필요한 앱은 상시 실행한다. DB·파일은 앱 프로세스 중지 후에도 유지한다. 유휴 대기와 운영자의 명시적 중지는 구분하며 수동 중지 앱은 요청·예약 실행으로 재기동하지 않는다. 목표 상태가 실행인 앱의 작업만 스케줄러가 기동한다.

기본 템플릿에는 제한된 DB 연결 풀, 페이지 조회, 스트리밍 파일 처리, 종료 신호 처리와 재개 가능한 작업 예제를 제공한다. CLI의 로컬 검사와 플랫폼 개발 영역에서 메모리 상한·동시 작업·대량 데이터 상황을 확인한다. 사용량을 줄이는 변경도 앱의 권한·격리 계약을 유지해야 한다.

DB는 autovacuum·통계 갱신을 유지하고 데이터 보존 정책을 적용한다. 일반 `VACUUM`은 주로 공간을 재사용 가능하게 만들며 항상 디스크 여유를 반환하는 것은 아니다. `VACUUM FULL`은 추가 공간·잠금을 요구하므로 디스크가 찬 상태의 자동 정리 수단으로 삼지 않는다. [PostgreSQL VACUUM](https://www.postgresql.org/docs/current/routine-vacuuming.html)

내부 AI는 관리자가 설정한 공통 Codex·Claude Code 연결과 사용자별 독립 세션을 사용하며 API LLM도 선택 지원한다. 서버에서 사용하는 Hermes·공식 클라이언트 프로세스·작업 파일의 CPU·메모리·디스크와 공급자의 사용량 한도를 따로 관리한다. 구독 사용을 무제한 실행이나 비용 0원으로 표시하지 않으며, 제공사가 반환하지 않는 잔여량·요금은 미확인으로 둔다. 연결 방식과 지원 조건은 [내부 AI 계획](AI.md)을 따른다.

Hermes 실행과 문서 처리의 동시 실행·시간·관측 가능한 토큰 예산을 제한한다. 전체 호출은 공통 연결의 한도를 함께 소비하고, miy는 별도로 사용자별 예산·동시 실행 수와 공정한 대기열을 관리한다. 같은 대화는 순서대로, 다른 대화는 검증한 공통 연결·서버 한도 안에서 실행한다. 구독 한도 초과·인증 만료는 해당 연결 전체의 대기·재인증·실패로 처리하며 다른 계정이나 API 과금으로 자동 전환하지 않는다.

사용자 한 명의 취소는 해당 turn만 중지하며 공통 프로세스·인증을 종료하지 않는다. 영속 세션과 프로세스 수명을 분리하여 유휴 실행기를 종료하고, 재개 시 저장된 소유 관계로 각 대화를 복구한다. 공통 실행기 재시작이 여러 대화에 영향을 주는 경우 실행 상태를 확인한 뒤 복구하며 새 요청을 중복 생성하지 않는다.

로컬 모델 서버가 있다면 모델의 RAM·VRAM·GPU 사용량을 별도 계산한다. 구독 연결에도 외부 데이터 전달 정책을 적용하고 자원 부족을 이유로 내부 전용 데이터를 외부 모델로 자동 전달하지 않는다.

## 운영 화면과 용량 부족 대응

관리 화면은 서버 총량·현재 사용·예약량·운영 여유, 앱별 컨테이너 자원·파일·DB 크기, 대기 작업·최근 한도 초과와 담당자를 표시한다. 앱 컨테이너 CPU와 공유 DB 서버 CPU를 구분하고, 쿼리 통계로 추정한 앱 부하는 정확한 CPU 귀속량처럼 표시하지 않는다.

일상 관리에는 작은 앱·일반 업무 앱·무거운 작업 등 검증된 자원 프로필을 제공하고, 실제 사용량에 따른 한도 조정 권고와 예상 영향을 표시한다. 프로필별 수치는 파일럿에서 정하며, 코어 운영 여유를 침범하는 변경은 적용하지 않는다.

| 상태 | 조치 |
| --- | --- |
| 정상 | 승인된 한도 안에서 실행·저장 |
| 주의 | 담당자에게 원인·증가 추세·관련 앱 표시, 보존 정책에 따른 정리 |
| 제한 | 신규 빌드·미리보기·대량 작업 대기, 파일 한도 초과 업로드 거부, DB 초과 앱 접근 제한 |
| 보호·복구 | 문제가 있는 앱·작업 중지, 안전한 정리·증설·복구 후 여유와 상태 재검증 |

경계값에는 사용률과 절대 여유, 지속 시간, 회복 기준을 함께 둬 상태가 반복 전환되지 않게 한다. CPU 과부하·메모리 압박·디스크 증가에 동일한 백분율 하나를 적용하지 않는다. 자동 정리는 만료·보존 정책에 따른 대상만 처리하며 운영 데이터·DB WAL 파일을 직접 지우지 않는다.

자원 부족은 작업 ID와 원인 코드·필요량·허용량·현재 여유를 포함해 반환한다. 메모리 초과 앱을 무한 재시작하거나 실패한 작업을 제한 없이 재시도하지 않는다. 관리 API·CLI·MCP는 같은 정보를 제공하고, 앱 제작자는 허용된 앱의 사용량·한도만 확인한다.

증설은 먼저 병목을 확인한 뒤 판단한다. 메모리 부족, CPU 처리량, DB I/O, 파일 증가의 원인을 구분하여 VM 크기·디스크·DB 또는 작업 실행 위치를 조정한다. 다중 서버·Kubernetes는 실제 요구가 확인된 뒤 검토하며 첫 출시의 필수 구성으로 추가하지 않는다.

## 확정 전 검증

- 지원 호스트에서 실제 CPU 제한·메모리 OOM·프로세스 제한이 동작하고 제한되지 않는 설정을 탐지하는지 확인.
- 동시에 시작하는 앱·빌드·작업이 예산을 중복 예약하지 않으며 runner 재시작 후 예약이 복구되는지 확인.
- 기존 앱 종료 후 자원 예약을 새 버전으로 전환하고 중복 실행 RAM 없이 업데이트하는지 확인. 신구 이미지·마이그레이션·복구 공간 부족은 중지 전에 대기·거부하며 중지 이후 실패는 명시적 복구 상태로 처리.
- 병렬 업로드·중단·재시도·inode 부족에서 파일 한도와 예약 회수가 동작하는지 확인.
- 공유 PostgreSQL의 연결 폭주·느린 쿼리·임시 파일·DB 성장·WAL 증가를 관측하고 원인 앱 차단과 복구 경로를 검증.
- DB 관리 한도의 초과 폭·감지 지연과 기존 세션 종료를 측정하고 실제 보장 범위를 운영 화면에 표시.
- 만료 미리보기·로그·캐시 정리가 운영 데이터와 활성·롤백용 이미지를 삭제하지 않는지 확인.
- 앱 수·활성 사용자·동시 작업·DB 데이터·파일 규모별 응답 지연과 자원 사용을 측정하여 지원 규모를 산정.
- 공통 AI 연결의 총한도·프로세스 자원·사용자별 대기 공정성, 개별 취소, 공통 연결 장애와 유휴 종료 후 소유 대화의 재개를 확인.

최소 하드웨어와 최대 앱 수는 구성 요소의 기본 사용량·업무 부하를 측정한 뒤 정한다. 설치 가능한 앱 수와 동시에 실행 가능한 앱 수를 구분하고 단순 앱 개수만으로 수용량을 보장하지 않는다.
