## 제품 정의

**miy는 전담 IT 운영팀이 없는 중소기업이 자체 업무 앱과 데이터를 운영할 수 있도록, 개발 지침부터 소스 관리·배포·인증·DB·파일 저장소·AI 활용까지 제공하는 플랫폼이다.**

고객사는 필요한 역량에 따라 직접 개발·운영하거나, miy 개발사와 유지관리가 가능한 파트너사에 이를 맡길 수 있다. 앱을 직접 구현할 수 있는 도메인 전문가도 고객사의 업무 앱 제작에 참여한다. 고객사 내부에 개발자나 서버 운영 인력이 있어야만 사용할 수 있는 제품으로 한정하지 않는다.

앱 제작자는 CLI로 앱의 기본 구조를 만들고 자신의 Codex, Claude Code, Hermes, Pi 등의 개발 에이전트를 MCP로 연결한다. 개발자는 miy가 제공하는 앱 규격, UI 컴포넌트, API와 데이터 소스 계약을 지키면서 업무 로직과 화면을 자유롭게 구현한다. 개발 중인 앱은 로컬 또는 플랫폼 개발 영역에서 실행·평가한다. 완성된 앱은 독립 패키지로 배포되며, miy 코드를 수정하거나 플랫폼 전체를 다시 배포할 필요가 없어야 한다.

기존 `../miy`는 미출시 상태다. 후속 프로젝트의 내부 이름은 `miy-v2`, 대외 서비스명은 `miy`다. 현재 범위는 계획 문서 작성과 정리이며 구현과 배포는 후속 작업이다.

이 문서는 제품 요구사항의 기준이다. 추진 순서는 [PLAN.md](PLAN.md), 개발 경험과 CLI 기본안은 [DEVELOPMENT.md](DEVELOPMENT.md), 유사 프로젝트와 차용 근거는 [RESEARCH.md](RESEARCH.md), 프론트엔드 기술 비교는 [FRONTEND.md](FRONTEND.md)에서 관리한다.

본격적인 제품 구현에 앞서 최소 플랫폼·API/MCP·DB, CLI·개발 하네스, Codex 앱 개발, 단일 이미지 배포와 라우터 기반 UI 실행을 연결해 집중 검증한다. 단계·증거·통과 조건은 [핵심 흐름 검증 계획](VALIDATION.md)을 따른다. 통합형 UI의 구체적인 로더와 버전은 이 검증에서 결정한다.

## 사용자와 해결할 문제

현업에서 AI로 업무 앱을 만들 수 있어도 인증, 데이터 연결, 소스 보관, 배포와 장애 복구를 각각 준비해야 하면 기업이 지속적으로 운영하기 어렵다. miy는 이러한 공통 기능과 운영 책임을 앱별로 확인할 수 있게 한다.

| 사용자 | 필요한 경험 |
| --- | --- |
| 고객사 책임자·업무 담당자 | 업무 요구 정의, 앱 평가, 수행자·운영 방식 선택, 접근 권한 위임과 회수 |
| 고객사 관리자·운영 담당자 | 직접 운영하는 경우 설치, 계정·권한·연결 관리와 장애 대응 |
| miy 개발사 | 플랫폼 코어 개발·업데이트 제공, 고객사 구축·유지관리와 앱 개발 대행 |
| 유지관리 파트너사 | 위임 범위에서 구축, 코어 업데이트 적용, 서버·앱 운영과 유지보수, 앱 개발 대행 |
| 앱 제작자·도메인 전문가 | 고객사 내부 또는 외부에서 업무 지식을 앱으로 구현하고 미리보기·검증·유지보수 수행 |
| 일반 직원 | 한 번 로그인하여 허용된 업무 앱 사용, 내부 데이터 기반 챗봇 이용 |

이 구분은 업무 역할이며, 한 조직이나 사람이 여러 역할을 맡을 수 있다. 도메인 전문가의 앱 개발 참여가 서버 운영이나 코어 유지관리 권한까지 포함하지는 않는다.

제품의 차별점은 기업의 앱·데이터·운영 권한을 통합하고, 외부 개발 에이전트와 내부 챗봇이 같은 권한 체계에서 협업하도록 만드는 데 둔다.

## 설치와 서비스 제공 방식

**설치 위치와 운영 주체를 독립적으로 선택한다.** 사내 설치도 개발사·파트너가 대행할 수 있고, 클라우드 설치도 고객사가 직접 운영할 수 있다. 기업별 독립 설치와 기존 앱·데이터 격리 구조는 두 위치에서 동일하게 적용한다.

| 선택 항목 | 제공할 방식 |
| --- | --- |
| 설치 위치 | 고객사 내부의 서버·VM 또는 클라우드 서버·VM |
| 운영 방식 | 고객사 직접 운영 / 개발사·파트너 대행 / 업무별 공동 운영 |
| 앱 개발 방식 | 고객사 자체 개발 / 개발사·파트너 개발 대행 / 개발 가능한 도메인 전문가 참여 |

클라우드 설치도 고객사별 독립 환경을 기본으로 한다. 여러 고객사를 하나의 설치에서 함께 운영하는 공유형 SaaS와 다중 서버 구성은 기존 후속 범위를 유지한다. 클라우드 제공자, 계정·비용 부담 주체, 원격 접속과 네트워크 구성은 도입 시 정하며 특정 제공자에 고정하지 않는다.

고객사는 업무 요구, 평가와 데이터 이용 범위를 결정한다. 실제 설치·업데이트·백업·장애 대응은 지정한 수행자가 맡는다. 인프라 운영, 플랫폼 코어 유지관리, 개별 앱 유지보수의 담당자와 인계 범위를 각각 기록한다.

## 핵심 사용자 흐름

### 기업 환경 준비

고객사와 구축 담당자가 사내·클라우드 설치 위치와 직접·대행·공동 운영 방식을 정한다. 고객사 또는 위임받은 개발사·파트너가 miy를 설치하고 관리자 계정을 만든다. 사용자·그룹을 등록하고, 데이터 소스와 AI 모델 연결을 설정한다. 코어·서버·앱별 담당자, 수행자의 접근 범위, 배포 권한, 자원 한도와 백업 대상을 지정한다.

### 로컬 개발과 배포

고객사 개발자, 개발사·파트너 또는 개발 가능한 도메인 전문가가 앱 제작자로 참여한다. 외부 제작자는 해당 고객사가 위임한 앱·환경에 접속한다. CLI로 생성한 프로젝트에는 앱 manifest, SDK·UI 자산, 인증·데이터 이용 예제, 테스트 데이터와 에이전트용 지침이 포함된다. 개발 에이전트는 MCP에서 허용된 규격·데이터 스키마와 앱 기능 정보를 보완하여 로컬 저장소에서 개발한다.

제작자는 로컬 실행으로 화면과 업무 로직을 반복 확인하고, 고객사 업무 담당자의 평가나 실제 플랫폼 연동 검증이 필요하면 중간 작업본을 개발 영역에 올린다. 플랫폼은 격리된 미리보기 URL과 로그·검증 결과를 제공한다. 고객사 또는 대행사의 운영 배포 권한을 가진 담당자는 소스 커밋에 연결된 검증 완료 산출물을 운영으로 승격한다.

### 코어 업데이트와 유지관리

개발사는 플랫폼 코어의 업데이트와 호환성·변경 안내를 제공한다. 설치별 유지관리 담당자는 고객사와 정한 작업 범위·시점에 따라 앱 계약과 데이터 변경의 호환성을 확인하고, 필요한 백업과 복구 수단을 준비해 업데이트를 적용한다. 이후 플랫폼과 앱의 정상 동작을 확인하고 결과를 기록한다. 개별 앱 개발·배포와 코어 업데이트는 별도의 버전·권한·작업 이력으로 관리한다.

### 앱 이용과 기능 조합

직원은 miy에 로그인하여 허용된 앱을 실행한다. 앱은 사용자에게 부여된 범위에서 플랫폼 데이터·파일을 사용하고, 다른 앱이 공개한 API와 업무 기능을 호출한다. 새로운 앱을 추가할 때 기존 플랫폼 코드를 수정하지 않는다.

### 내부 데이터 기반 업무 지원

직원은 miy 웹사이트의 내장 챗봇에 질문한다. 내부 Hermes 엔진은 현재 사용자가 접근할 수 있는 자료와 앱 기능을 도구로 활용하고, 모델 호출과 도구 결과 반영을 반복하여 출처가 있는 답변을 제공한다. 업무 변경이 필요하면 대상과 변경 내용을 제시하고, 사용자 확인과 실행 시점의 권한 검사를 거쳐 수행한다.

## 기능 요구사항

### 개발 에이전트 연결

MCP를 개발 에이전트의 표준 진입점으로 제공한다. 코어가 앱에 공개한 API 전체의 명세·필요 권한·사용 예제·오류·지원 버전을 MCP에서 목록·검색·상세 조회할 수 있어야 한다. 앱과 일반 프로그램에는 HTTP API와 SDK를 제공하며, 모든 경로에 동일한 서버 권한 정책을 적용한다. MCP 연결 없이도 CLI로 기본 개발·검사·배포를 완료할 수 있어야 한다.

| 제공 항목 | 내용 |
| --- | --- |
| 앱 규격 | 패키지 구조, 실행 방식, manifest, 지원 API 버전, 배포 조건 |
| 디자인 자산 | 디자인 토큰, 공통 컴포넌트, 화면 템플릿, 접근성·다국어 지침 |
| 개발 지침 | 인증, 데이터 접근, 오류 처리, 테스트와 배포 예제 |
| 코어 공개 API | 모든 공개 API의 경로·입출력·권한·오류·버전, SDK 호출 예제와 관련 컴포넌트 |
| 데이터 설명 | 접근 가능한 데이터 소스의 스키마, 허용 작업과 사용 예제 |
| 앱 기능 목록 | 다른 앱이 공개한 API·업무 기능과 필요한 권한 |
| 실행 도구 | 앱 등록, 검증, 빌드·미리보기 요청, 배포, 상태·로그 조회와 복구 |

문서는 MCP Resources로, 선택 가능한 작업 안내는 Prompts로, 검색·조회와 실행 기능은 Tools로 제공한다. 앱 프로젝트·SDK·UI 패키지는 버전이 있는 개발 번들로 CLI가 준비하고 MCP에서는 이를 찾고 사용법을 조회하게 한다. 클라이언트별 기능 차이를 고려하여 핵심 개발 문서는 도구 호출과 로컬 파일로도 제공한다. 전체 API 정보를 조회할 수 있게 하되 모든 문서를 매번 모델 문맥에 넣거나 모든 API를 개별 실행 도구로 등록할 필요는 없다.

문서·SDK·실제 서버의 계약이 일치하도록 같은 버전의 명세와 예제를 관리한다. 공개 API 사용법의 조회와 API 실행 권한을 구분하며, 고객사 데이터 스키마·비공개 앱 기능 등은 조회 권한과 외부 AI 정책을 적용한다.

개발에는 스키마와 합성 샘플을 기본 제공한다. 실제 기업 데이터의 전달은 사용자 권한과 외부 AI 이용 정책을 모두 만족해야 한다. 에이전트에 이미 전달된 데이터는 miy가 회수할 수 없으므로 전달 시점에 정책을 집행한다.

지원 클라이언트의 인증 방식과 MCP 기능을 실제로 검증하고 지원 버전을 기록한다. 표준을 지원한다는 사실만으로 모든 클라이언트와의 호환을 완료한 것으로 보지 않는다.

### CLI와 앱 개발 계약

CLI는 프로젝트 생성, 플랫폼 연결, 개발 맥락 갱신, 로컬 실행, 계약 검사, 개발 영역 업로드, 상태·로그 조회와 운영 승격을 제공한다. MCP는 개발 에이전트에 맥락과 실행 도구를 제공하며, CLI·MCP·관리 화면은 같은 서버 API와 권한 정책을 사용한다.

- CLI는 기본 개발 지침·SDK·UI·타입·예제를 포함한 호환 개발 번들을 제공하고 템플릿에서 앱 구조를 생성한다. 별도로 자료를 수집하지 않아도 기본 앱을 개발·실행할 수 있게 한다.
- manifest에는 계약·실행 프로필 버전, 진입점, 공개 기능, 필요한 자원과 권한을 선언한다.
- 개발자는 화면 구성, 업무 로직, 내부 모듈과 호환되는 라이브러리를 선택한다. 필수 UI 연동·접근성 규칙은 지키되 업무별 컴포넌트를 추가할 수 있다.
- 데이터 소스는 논리적인 연결 이름으로 참조하고, 실제 연결·비밀값은 환경별 설정에서 바인딩한다. 앱 소스에 기업별 자격증명을 넣지 않는다.
- 공개 기능의 입력·출력·오류·필요 권한·변경 효과를 선언하여 앱 간 호출과 Hermes 도구에 같은 계약을 사용한다.
- CLI는 타입·manifest·의존성·공개 기능·데이터 바인딩을 검사하고 수정 가능한 오류를 반환한다. 서버도 배포 시 계약을 다시 검증하며, 실행 시 권한은 서버가 집행한다.
- 템플릿·SDK·UI 자산·계약 버전과 의존성을 고정하고 호환 범위를 검사한다. 지침·생성 타입 갱신은 개발자가 작성한 코드를 무조건 덮어쓰지 않는다.
- 일반 맥락 동기화와 SDK·UI·템플릿 업그레이드를 구분한다. 대상 고객사의 코어 버전에 맞는 자산을 선택하고, 사내 배포·오프라인 개발 번들의 제공 범위를 명시한다.

CLI는 개발 에이전트와 CI에서 사용할 수 있는 구조화된 결과, 명확한 종료 코드와 비대화형 실행을 제공한다. 명령 이름과 생성 파일 구성은 [개발 흐름 기본안](DEVELOPMENT.md)에서 구체화한다.

### 로컬 실행과 플랫폼 개발 영역

| 실행 위치 | 필요한 경험 | 검증 범위 |
| --- | --- | --- |
| 개발자 로컬 | 화면의 빠른 갱신, 앱 백엔드·작업의 로컬 실행, 테스트용 DB·파일과 샘플 데이터 | 화면, 업무 로직, 데이터 처리와 계약 검사 |
| 플랫폼 개발 영역 | 개인 또는 팀별 미리보기, 평가자 접근, 실제 플랫폼 인증·데이터 연결·앱 간 호출, 로그 | 플랫폼과의 통합, 현재 권한, 실행 격리와 운영 호환성 |

필요한 도구·의존성을 준비한 뒤에는 플랫폼에 연결하지 않아도 기본 템플릿의 로컬 실행이 가능해야 한다. 로컬 테스트용 사용자·데이터·서비스 대체 구현을 제공하되, 로컬 통과를 실제 서버 권한·격리 검증 완료로 취급하지 않는다. 지원 실행 프로필의 로컬 실행과 플랫폼 실행에서 계약·런타임·의존성을 맞추고 차이가 있는 기능은 표시한다.

개발 영역은 운영과 별도 데이터·비밀값·권한·자원 한도를 가진다. 미리보기 URL에도 접근 정책을 적용하며, 외부 연결은 테스트 대상을 기본으로 사용한다. 예약 실행과 외부 시스템에 영향을 주는 작업은 개발 환경에서 별도로 활성화하도록 한다.

커밋 전 작업본도 불변 소스 스냅샷과 해시를 기록하여 개발 영역에 올릴 수 있다. 이 미리보기는 운영 릴리스와 구분한다. 운영 승격에는 기준 Git 커밋에 연결되고 검증을 통과한 릴리스가 필요하다. 소스가 달라지면 새 산출물을 검증한다.

미리보기의 소유자, 평가자, 버전, 만료와 삭제 상태를 관리한다. 빌드·사전 검사 실패는 기존 실행에 영향을 주지 않는다. 교체 중 해당 미리보기의 일시 중단은 허용하고 실행 실패 시 이전 버전 복구 또는 복구 필요 상태를 표시한다. 운영 앱에는 영향을 주지 않아야 한다.

### 독립 앱과 격리 실행

앱은 자체 소스 저장소, manifest, 배포 산출물, 버전과 데이터 수명주기를 갖는다. 여기서 플러그인은 별도 배포 패키지를 뜻하며, 앱 백엔드 코드를 플랫폼 코어의 서버 프로세스에 직접 로드하는 구조로 만들지 않는다.

- 신뢰한 앱의 React UI 모듈을 플랫폼 라우터에서 런타임에 로드하는 통합형 실행을 우선 검증한다. 새 앱 설치에 플랫폼 프런트엔드 재빌드를 요구하지 않는다.
- 통합 UI는 플랫폼과 브라우저 실행 공간을 공유한다. 별도 UI 격리가 필요한 앱은 다른 출처의 iframe·독립 화면 실행을 검토하며 두 방식의 신뢰 경계를 구분한다.
- 앱 백엔드와 작업은 플랫폼 프로세스와 분리된 컨테이너 등 지원 실행 프로필의 격리 환경에서 운영한다.
- 앱별 CPU·메모리·저장 공간·작업 동시 실행 한도를 적용한다.
- 앱에 호스트 관리자 권한, 컨테이너 관리 소켓, 플랫폼 DB 자격증명을 제공하지 않는다.
- 앱 간 직접 네트워크·저장소 접근을 제한하고 허용된 API와 자원 연결을 사용하게 한다.
- 개발·미리보기와 운영의 데이터, 비밀값, 권한을 분리한다.
- 새 앱의 등록·설치·업데이트는 메타데이터와 배포 산출물로 처리한다.

Windmill의 CLI·개발 자산·작업 관리 경험을 참고한다. 현재 첫 앱 프로필의 기본안은 Rust 백엔드와 빌드된 React 정적 화면을 같은 OCI 이미지로 배포하는 독립 서비스다. 정적 파일의 바이너리 내장은 선택안이다. 앱별 컨테이너와 필요 시 별도 작업 컨테이너를 miy가 관리한다. 공유 함수·Worker 실행은 후속 비교 대상으로 두며 첫 출시의 필수 엔진으로 추가하지 않는다.

첫 출시는 기업이 승인한 앱을 실행하는 컨테이너 격리를 기본안으로 삼는다. Rust로 작성한 앱도 코어 프로세스에 직접 로드하지 않는다. UI·SDK·실행 프로필의 세부 도구는 기술 검증 후 고정한다. 공개 마켓플레이스의 임의 코드를 강한 VM 경계에서 실행하는 기능은 후속 범위다.

### 인프라 용량과 자원 관리

서버 전체의 가용 용량, 기반 서비스의 운영 여유와 앱·환경별 한도를 함께 관리한다. 앱이 manifest에 요청한 자원과 운영자가 실제 허용한 한도를 구분하고, 새 앱·미리보기·빌드·작업·업데이트를 시작하기 전에 필요한 자원을 확인한다. 용량이 부족하면 대기 또는 구체적인 거부 사유를 반환한다.

- CPU 시간·메모리·프로세스 수는 실행 환경에서 제한한다. 설치 진단으로 제한이 실제 집행되는지 확인하고 지원되지 않는 설정을 정상 적용으로 표시하지 않는다.
- 운영 앱, 개발 미리보기, 빌드·백그라운드 작업의 자원 예산과 동시 실행 수를 구분한다. 코어·인증·DB와 복구 작업의 운영 여유를 남긴다.
- 파일 저장소는 업로드 중 예약량을 포함한 앱·환경별 용량 한도를 적용하고, 서버 전체의 디스크·inode 여유도 확인한다.
- DB별 크기·증가 추세·연결 수·쿼리 부하와 PostgreSQL 전체의 WAL·임시 파일·디스크 여유를 함께 관측한다. 공유 PostgreSQL에서 앱별 DB 분리는 CPU·메모리·디스크의 물리적 격리를 의미하지 않는다.
- DB 용량은 초기 공유 구성에서 측정·경보·접근 차단을 이용한 관리 한도로 제공한다. 초과 감지 전 증가분이 생길 수 있으므로 정확한 바이트 단위의 강제 제한으로 표시하지 않는다. 엄격한 자원 격리가 필요한 앱의 별도 DB 실행 프로필은 후속 검토한다.
- 로그·빌드 캐시·미리보기의 보존과 정리 규칙을 제공한다. 운영 데이터·복구에 필요한 릴리스·백업을 용량 부족만으로 임의 삭제하지 않는다.
- 자원 부족의 대상·원인·조치·복구 결과를 관리 화면·API·CLI에 제공하고, MCP에서도 동일 권한 범위로 조회할 수 있게 한다. 증설과 한도 변경은 권한 있는 운영자가 수행한다.

초기에는 보수적인 동시 실행 수와 자원 한도부터 적용한다. 운영 앱의 유휴 중지·자동 재기동, 연결 풀 공유와 실행 자원 최적화는 실제 부하·지연·복구 검증 후 확장한다. 상세 관리 경계·효율화 순서·검증 조건은 [용량 관리 계획](CAPACITY.md)에 정의한다.

### 빌드와 배포

운영 릴리스의 배포 흐름은 **소스 커밋 → 격리 빌드 → 검증 → 개발 영역 미리보기 → 배포 권한 확인 → 운영 활성화 → 상태 확인**으로 구성한다. 중간 평가용 작업본 업로드는 이 흐름에 진입하기 전에도 가능하다.

운영에는 검증한 산출물을 그대로 승격한다. 소스 커밋, 산출물 digest, 설정 버전, 수행자와 결과를 연결하여 기록한다. 실패한 빌드나 상태 확인이 정상 운영 버전을 대체해서는 안 된다. 배포 요청과 실제 활성화 결과는 구분하여 표시한다.

기본 교체 절차는 **이미지 확보·사전 검사 → 대상 앱 점검 상태 → 신규 요청·예약 작업 차단 → 기존 실행 종료 → DB 변경 → 새 버전 시작 → 정상 확인 → 서비스 재개**다. 대상 앱의 일시 중단을 허용하며 블루·그린 배포나 두 버전의 동시 실행을 첫 출시 조건으로 요구하지 않는다. 코어와 다른 앱은 계속 관리할 수 있어야 한다. 새 버전 실패 시 DB 호환성이 확인된 이전 버전을 재실행하거나 복구 필요 상태로 남긴다. 중지된 앱의 업데이트는 중지 상태를 유지하고 별도 시작 요청으로 서비스를 연다.

화면·백엔드·작업을 같은 릴리스로 묶어 호환되는 조합을 활성화한다. 데이터 연결·비밀값·실제 부여 권한은 운영 환경에서 별도로 설정하고 확인하며, 개발 DB와 비밀값을 승격 시 자동 복사하지 않는다.

개인 개발 권한이 운영 배포 권한을 자동으로 부여하지 않는다. 권한을 위임받은 담당자는 허용된 앱·환경에 배포할 수 있으며, 모든 운영 배포에 별도 관리자 승인을 반복 요구하는 것을 기본 정책으로 삼지 않는다.

앱 코드 롤백과 데이터 복원은 구분한다. DB 변경은 이전 앱 버전과의 호환성을 확인하며, 파괴적인 변경을 코드 롤백만으로 복구할 수 있다고 표시하지 않는다. 호환되지 않는 변경에는 별도 복구 절차와 필요한 백업을 연결한다.

### 인증과 권한

실행 주체는 사용자, 개발 에이전트, 앱 서비스 계정으로 구분한다. 개발 에이전트의 위임 관계와 앱 서비스 계정의 소유자를 기록한다. 토큰에는 대상 앱·환경·허용 작업·유효기간을 연결하고 철회할 수 있어야 한다.

외부 개발사·파트너·도메인 전문가도 해당 고객사 설치에서 식별 가능한 계정과 위임 범위를 사용한다. 앱 개발·미리보기, 운영 배포, 플랫폼 관리, 코어·서버 유지관리의 권한을 구분한다. 고객사는 수행자를 교체하거나 접근을 회수할 수 있어야 하며, 여러 고객사를 담당하는 수행자의 접속 대상과 자격증명은 설치별로 구분한다. 위임 범위·유효기간·수행 이력을 확인할 수 있게 한다.

사용자를 대신하는 요청의 유효 권한은 다음 조건의 교집합이다.

> 현재 사용자 권한 ∩ 토큰 범위 ∩ 설치된 앱에 부여된 권한 ∩ 대상 리소스의 접근 정책

- 브라우저에는 해당 앱에서 사용할 제한된 사용자 토큰만 전달한다.
- 예약 작업은 명시적으로 부여된 서비스 계정 권한으로 실행한다.
- 앱 manifest의 요청 권한과 실제 설치에 부여된 권한을 구분한다.
- 계정 중지, 앱 비활성화, 권한 회수는 이후 요청과 대기 작업에 반영한다.
- 인증과 권한은 서버가 집행하며 UI 표시, 모델 판단, 문서의 지침을 권한 부여로 사용하지 않는다.
- 비밀값은 브라우저·소스·에이전트 응답·일반 로그에 포함하지 않는다.

‘플랫폼의 모든 데이터에 접근’은 API로 공개된 기능과 데이터에 권한 범위 내에서 접근할 수 있음을 뜻한다. 신규 플랫폼 기능도 API와 권한 계약을 함께 제공한다.

### 앱 간 접근

다른 사람이 만든 앱에도 그 앱이 공개한 API와 업무 기능을 통해 접근할 수 있어야 한다.

앱 간 호출에서는 원래 사용자와 호출 앱을 식별한다. 플랫폼은 호출 권한을 확인하고 대상 앱은 자신의 리소스 권한을 확인한다. 대상 앱의 권한 검사를 생략하거나 더 강한 서비스 계정 권한으로 조용히 대체하지 않는다.

앱은 다른 앱의 DB를 직접 공유하거나 플랫폼 관리자 자격증명을 전달하지 않는다. 업무 데이터의 세부 권한은 앱이 정의하되, 플랫폼의 공통 인증·권한 확인 계약과 검증 도구를 사용하도록 한다.

### DB와 파일 저장소

- 관리형 PostgreSQL을 제공하고 앱·환경별 DB와 역할을 분리한다.
- 초기에는 하나의 PostgreSQL 서버 안에 코어용 DB와 앱·환경별 DB를 생성한다. 앱마다 별도의 PostgreSQL 서버를 실행하는 방식은 기본 구성에 포함하지 않는다.
- 앱 전용 DB 연결 정보는 해당 서버 실행 환경에만 제공한다.
- 앱 제작자는 테이블·관계·인덱스와 변경 이력을 소스에 정의하고, miy가 설치·업데이트 시 검증한 릴리스의 마이그레이션을 대상 앱 DB에 적용한다.
- 앱 실행 계정과 스키마 변경 계정을 분리한다. 변경의 동시 실행·이력 변조를 방지하고, 실패 시 새 버전 활성화를 중단하여 기존 버전 유지 또는 명시적 복구 절차를 수행한다.
- 브라우저에서 사용하는 데이터 기능은 인증된 API를 통해 제공한다.
- 공통 파일 저장소는 앱·사용자·그룹별 권한, 용량 제한, 업로드·다운로드 API를 제공한다.
- MinIO는 도입하지 않는다. 파일 API와 저장 backend를 분리하고 초기 로컬 영속 볼륨·선택적 S3 연결을 기본안으로 검토한다.
- 데이터 보존, 앱 제거 시 처리, 백업과 복원을 앱 수명주기에 연결한다.

앱 전용 DB 운영과 다른 앱·기업 공통 데이터 이용은 구분한다. 기업 공통 데이터와 앱 간 데이터 이용에는 해당 소유자가 공개한 API와 접근 정책을 적용한다.

앱 DB는 컨테이너·릴리스 교체 후에도 유지한다. 개발용 DB·샘플 데이터는 운영으로 복사하지 않으며, 스키마 적용·권한·기존 데이터 변경 절차는 [앱 전용 DB 개발 계획](DEVELOPMENT.md#앱-전용-db와-스키마-적용)을 따른다.

### 외부 데이터 소스

첫 연결 대상은 업로드 파일, 외부 PostgreSQL, 사내 HTTP API다.

외부 PostgreSQL은 허용된 뷰·쿼리 중심의 조회부터 지원한다. HTTP 연결은 관리자가 등록한 대상과 작업만 호출할 수 있게 한다. 데이터 소스 자격증명은 서버가 보관하며 개발 에이전트나 브라우저에 반환하지 않는다.

각 연결에는 소유자, 허용 사용자·앱, 작업 범위와 외부 AI 전달 정책을 연결한다. 검색·요약·인용에도 원본 접근 정책을 적용한다.

### 소스 관리

miy 설치만으로 비공개 저장소 생성, Git clone/push, 코드·변경 이력 조회, 접근 권한 관리와 변경 검토가 가능해야 한다.

외부 GitHub·GitLab 저장소도 연결하며 앱마다 하나의 기준 저장소를 지정한다. 배포 이력에서 실제 사용한 커밋과 산출물을 확인할 수 있어야 한다. 내장 Git 구현에는 Gitea를 활용하는 방향을 기본 제안으로 삼으며, 구성 요소의 최종 선택은 기술 설계에서 결정한다.

### 일상 운영과 복구

**miy 관리 화면에서 설치된 앱의 수명주기를 직접 제어한다.** Docker·Kubernetes처럼 상태를 보고 실행을 제어하는 경험을 제공하되, 초기 구현은 Docker Engine과 내부 runner를 사용하며 Kubernetes 설치를 전제로 하지 않는다.

| 관리 기능 | 요구사항 |
| --- | --- |
| 시작 | 지정 릴리스·환경·권한·자원으로 실행하고 정상 확인 후 접근 허용 |
| 중지 | 신규 요청·예약 및 대기 작업의 실행을 차단하고 앱 서버·실행 중 작업을 종료 정책에 따라 중지. DB·파일·설정은 보존 |
| 재시작 | 같은 릴리스·설정으로 중지 후 시작. 일시 중단 표시 |
| 업데이트·이전 버전 복구 | 릴리스와 DB 호환성을 확인하고 중지 후 교체. 데이터 복원과 코드 버전 복구를 구분 |
| 앱 삭제 | 대상 환경의 실행·라우트·예약·앱 자격증명을 정리. 업무 데이터는 기본 보존하며 영구 삭제는 별도 권한·명시적 요청으로 처리 |
| 상태·로그·자원 | 원하는 실행 상태와 실제 상태, 활성·대상 릴리스, 오류, CPU·메모리·저장량, 최근 작업의 수행자·결과 표시 |

운영자가 중지한 앱은 요청·예약 실행·서버 재시작으로 자동 시작하지 않는다. 장애 후 재시작 정책은 실행을 원하는 앱에만 적용하며 반복 실패에는 횟수 제한과 대기를 둔다. 앱 삭제가 다른 환경의 설치, 기준 Git 저장소, 공유 DB 서버·스토리지를 삭제해서는 안 된다. 앱을 호출하는 다른 앱·Hermes에도 중지·점검·제거 상태를 반환한다.

관리 화면·CLI·API·허용된 MCP 관리 도구는 같은 앱·환경 권한과 작업 기록을 사용한다. 실행 제어는 내부 runner를 거치며 앱이나 브라우저에 Docker 소켓을 제공하지 않는다. 중복·상충하는 시작·중지·업데이트·삭제는 앱·환경별로 직렬화하고, 코어·runner 재시작 후 저장된 목표 상태와 실제 컨테이너 상태를 대조해 복구한다.

관리 화면은 다음 정보를 함께 제공한다.

- 고객사 책임자, 코어·서버·앱 유지관리 담당자와 대행 범위.
- 앱 담당자, 사용자 범위, 소스와 현재 배포 버전.
- 실행 상태, 최근 장애, 로그, 자원 사용량.
- DB·파일 용량, 백업 상태와 복원 결과.
- 만료·실패한 연결, 인증서 상태와 업데이트 상태.
- AI 사용량과 설정한 예산 한도.

백업은 플랫폼 설정뿐 아니라 Git 저장소, 앱 DB, 파일과 필요한 복구 키까지 포함한다. 별도 서버 또는 외부 저장소로 복사하고 새 환경에서 복원하는 절차를 제공한다. 백업 파일 생성과 복원 검증의 상태를 구분한다.

기반 서버·네트워크 준비는 고객사 또는 위임받은 구축·운영 담당자의 책임으로 두고, miy는 사내·클라우드 설치에 공통으로 사용할 설치 진단과 운영 절차를 제공한다. 접속 경로, 인증서, 백업 위치와 장애 연락 담당자를 설치별로 정한다.

코어 버전과 앱 릴리스는 독립적으로 관리한다. 코어 업데이트에는 대상 버전, 앱 API·SDK·실행 프로필의 호환 범위, 데이터 변경과 예상 영향, 사전 검사·백업, 적용 결과와 복구 절차를 연결한다. 데이터 변경을 포함한 업데이트는 이전 코어 바이너리로 되돌리는 것만으로 복구된다고 간주하지 않는다.

운영 대행자는 위임받은 범위에서 진단·업데이트·백업·복원을 수행하며 작업자·대상·결과를 기록한다. 호스트·클라우드 관리 권한은 앱 API 토큰과 구분하여 관리한다. 앱 개발 계약만으로 호스트 관리자 권한이 생기지 않으며, 서버 관리자 권한은 업무 데이터에 영향을 줄 수 있는 별도의 신뢰 경계로 다룬다.

수행자 변경 시 기준 소스 저장소, 릴리스·설정 정보, 백업·복구 절차와 작업 이력을 인계하고 기존 접근을 회수할 수 있게 한다. 소스 이용 권리와 인계 조건은 고객사와 수행자가 사전에 정한다.

### Hermes 업무 챗봇

Hermes는 miy 웹사이트에 내장된 챗봇의 백엔드 실행 엔진이다. 직원은 miy에 로그인하여 사이트 안에서 챗봇을 사용한다. Hermes를 따로 설치하거나 별도 서비스에 접속하는 절차는 없다. 내부 런타임을 별도 프로세스·컨테이너로 운영하더라도 제품과 운영의 경계는 miy 설치 안에 둔다.

Hermes와 내부 생성형 기능은 **공통 AI 연결 + 사용자별 독립 세션**으로 설계한다. 관리자가 Codex·Claude Code 공통 연결을 설정하고 직원은 miy에만 로그인한다. 각 직원이 자신의 구독 계정을 연결하는 방식은 요구하지 않는다. 구독 이용 경로를 우선 검토하고 API 기반 LLM은 별도 설정·선택하는 추가 경로로 지원한다. 연결의 만료·한도 초과·실패가 API 과금이나 다른 계정 이용으로 자동 전환되어서는 안 된다.

구독 인증과 일반 모델 API는 같은 인터페이스가 아니다. 공급자별 공식 인증·실행 조건과 Hermes의 모델·도구 루프 호환성을 선행 검증한다. 특히 Claude Code 원본 실행과 구독 토큰을 이용한 일반 모델 중계는 구분하며, 검증되지 않은 경로를 지원 완료로 표시하지 않는다. 상세 연결 후보·제약·세션 계약은 [내부 AI 계획](AI.md)을 기준으로 한다.

기본 실행 흐름은 다음과 같다.

1. 웹 챗봇이 miy의 대화·실행 API에 질문을 전달한다.
2. miy가 사용자·대화·실행 상태와 모델 정책을 관리하고 공통 AI 연결로 실행을 디스패치한다. 공급자 실행 세션은 사용자·대화별로 배정한다.
3. Hermes가 모델을 호출하고, 필요한 miy 도구를 요청한 뒤 그 결과를 반영한다. 답변이 완료되거나 중지 조건에 도달할 때까지 이 실행 루프를 반복한다.
4. 도구 호출은 miy의 서버 정책을 거쳐 앱의 공개 업무 기능과 허용된 데이터 연결을 이용한다.
5. miy가 진행 이벤트, 실행 확인 요청과 답변을 웹 챗봇에 스트리밍한다. 사용자의 확인·거부·중지도 같은 대화·실행 경로로 처리한다.

Hermes는 모델 호출·추론·도구 반복 실행·대화 실행을 담당하고, miy는 사용자 식별·권한·데이터 전달 정책·실행 상태·실행 확인·감사를 담당한다. 앱의 예약·백그라운드 작업 큐와 Hermes의 에이전트 루프는 책임이 다른 실행 경로다. 실행 디스패치 방식과 서비스 간 API의 세부 규격은 후속 설계에서 정한다.

외부 개발자가 MCP에 연결하여 사용하는 개발 도구로서의 Hermes와, 플랫폼이 운영하는 내장 챗봇 엔진으로서의 Hermes를 구분한다.

- 파일, 연결된 데이터 소스, 앱이 공개한 데이터를 검색하고 출처와 함께 답변한다.
- 모델에 전달하기 전에 현재 접근 권한을 확인한다. 검색 결과의 제목·요약·인용도 같은 정책을 따른다.
- 공통 공급자 인증과 miy 사용자 인증을 구분한다. 공통 연결 아래에서도 업무 대화·Hermes 세션·공급자 thread·메모리·파일의 소유 관계와 접근 범위를 유지한다.
- 한 사용자도 여러 대화를 가질 수 있으며 대화끼리 실행 세션을 섞지 않는다. 조회·재개·중지·재접속마다 소유권을 확인한다.
- 한 사용자의 로그아웃·실행 취소·권한 회수는 해당 사용자의 접근과 실행만 처리한다. 공통 인증 만료·회수·한도 초과는 전체 연결의 장애로 처리하고 대기·복구 상태를 표시한다.
- 데이터 변경은 대상과 변경 내용을 보여주고 사용자 확인 후 실행한다.
- 확인 이후에도 실제 실행 직전에 권한과 대상 상태를 재검사한다.
- 앱이 공개한 업무 기능을 호출한다. 첫 출시에서는 챗봇의 임의 서버 관리·무제한 셸 실행을 제공하지 않는다.
- 관리자가 공통 AI 연결·연결 방식·데이터 전달 범위를 설정한다. 구독 모델도 외부 전달 정책을 적용하며, 내부 전용 데이터는 승인된 사내 모델을 사용하거나 실행을 거부한다.
- 실행 취소, 시간·비용 제한, 실패 사유와 작업 결과를 제공한다.
- 화면 연결과 실행 수명을 분리한다. 대화 화면에 다시 접속하면 기존 실행의 상태·결과를 복구하며, 단순 화면 이탈로 새 실행을 만들거나 진행 중 작업을 중복 실행하지 않는다.

## 공개 인터페이스의 기본 단위

다음은 제품이 제공해야 할 계약의 책임 구분이다. 구체적인 필드, API 경로와 인증 흐름은 후속 기술 설계에서 정한다.

| 계약 | 책임 |
| --- | --- |
| App Manifest | 앱 식별자, 계약·실행 프로필 호환 버전, 진입점, 필요한 자원·권한, 공개 API·업무 기능 |
| App Release | 정확한 소스 커밋, 불변 산출물, 검증 결과 |
| App Installation | 설치 환경, 활성 버전, 사용자 범위, 실제 부여 권한 |
| Development Preview | 소스 스냅샷·해시, 빌드 결과, 개발 환경, 평가자, 만료와 정리 상태 |
| Data Binding | 앱의 논리적 연결 이름과 환경별 데이터 소스·허용 작업의 대응 |
| Platform API와 SDK | 인증, 사용자·그룹 조회, 데이터·파일·앱 기능 접근 |
| CLI와 개발 자산 | 프로젝트 생성, 계약 검사, 로컬 실행, 미리보기·승격과 버전이 있는 UI·지침 제공 |
| MCP | 개발 맥락 조회와 권한 있는 개발·운영 작업 |
| Operation | 빌드·배포·복원·업무 실행의 상태, 결과, 오류, 취소 가능 여부 |

장시간 작업은 작업 ID를 반환하고 상태를 조회하게 한다. 재시도로 배포나 업무 변경이 중복 발생하지 않도록 멱등성을 보장한다. API 버전, 오류와 권한 거부 결과는 클라이언트가 처리할 수 있는 계약으로 제공한다.

## 대표 검증 시나리오

자산 관리 앱과 구매 요청 앱을 기본 검증 예제로 삼는다. 두 앱은 독립적으로 배포되며, 구매 요청 앱은 허용된 자산 정보를 조회하고 Hermes는 두 앱의 정보를 종합하여 답변한다. 이들은 플랫폼 기능을 검증하는 예제이며 완성형 자산·구매 업무 제품 전체를 첫 출시 범위에 추가하는 의미는 아니다.

| 인수 항목 | 통과 조건 |
| --- | --- |
| 설치 선택 | 사내 서버·VM과 클라우드 서버·VM 각각에서 기업별 독립 설치·초기 설정·앱 실행·백업 복원을 확인 |
| 개발·운영 대행 | 외부 앱 제작자가 지정된 앱·개발 환경에서 개발·평가하고, 별도 위임받은 담당자만 운영 배포·유지관리 가능 |
| 대행 종료·인계 | 수행자 접근을 회수한 뒤 신규·대기 작업이 거부되고, 인계받은 담당자가 소스·릴리스·운영 절차로 작업을 이어갈 수 있음 |
| 코어 업데이트 | 호환성·백업·데이터 변경을 확인해 코어를 갱신하고 기존 앱 동작을 검증하며, 실패 시 정의된 복구 절차를 수행 |
| 프로젝트 생성 | CLI로 생성한 기본 앱에 SDK·UI 자산·지침·테스트 데이터가 포함되며 의존성 준비 후 실행 가능 |
| 개발 자산 제공 | MCP 없이 CLI로 프로젝트 생성·검사·미리보기·배포 가능. 대상 코어와 SDK·UI·지침 버전이 맞고 동기화가 사용자 코드나 패키지 버전을 임의 변경하지 않음 |
| API 정보 완전성 | 모든 코어 공개 API의 명세·권한·예제·오류·지원 버전을 검색·조회 가능. 고객사 고유 정보는 권한·외부 AI 정책에 따라 제공 |
| 개발 자유와 계약 | 사용자 정의 화면·업무 로직을 추가할 수 있고, 잘못된 manifest·공개 기능·바인딩은 CLI와 서버에서 구체적인 오류로 거부 |
| 로컬 실행 | 플랫폼 연결 없이 샘플 데이터로 화면·앱 백엔드·작업을 실행하고, 플랫폼에서만 검증 가능한 항목을 구분 |
| 중간 평가 | 커밋 전 작업본을 해시로 추적하여 개발 영역에 올리고, 허용된 평가자만 미리보기와 로그에 접근 |
| 개발과 운영 분리 | 미리보기에서 운영 비밀값·DB를 자동 사용하지 않으며, 만료·삭제가 운영 앱과 데이터를 변경하지 않음 |
| 릴리스 승격 | 커밋에 연결된 검증 완료 산출물만 운영으로 승격하며, 화면·백엔드 버전과 환경별 연결·권한을 확인 |
| 개발 에이전트 호환 | Codex·Claude Code·Hermes·Pi 각각에서 연결, 지침 조회, 앱 검증, 배포 요청과 결과 조회를 검증하고 지원 버전을 기록 |
| 코어 독립성 | 앱 설치·업데이트·삭제 중 플랫폼 소스 수정과 전체 재배포가 발생하지 않음 |
| 통합 UI 런타임 | 플랫폼 빌드 후 새 앱을 설치하고 iframe 없이 앱 모듈을 라우터에서 실행. 직접 링크·뒤로 가기·UI/API 버전 일치와 로드 실패 처리를 실제 브라우저에서 검증 |
| Codex 개발 하네스 | 생성 지침·SDK·MCP와 검사 진단으로 앱 개발·변경을 완료. 플랫폼 소스 접근·사람의 앱 코드 패치 없이 독립 인수 검사와 서버 배포 증거 확보 |
| 앱 운영 제어 | 허용된 관리자가 화면에서 시작·중지·재시작·삭제하며 CLI·API와 같은 상태·권한·이력을 확인. 중지 앱이 요청·예약·호스트 재시작으로 자동 기동되지 않음 |
| 중단 허용 교체 | 기존 컨테이너 종료 후 새 버전 실행·정상 확인·접근 재개. 대상 앱만 점검 상태로 표시하고 실패 시 호환되는 이전 버전을 재실행하거나 복구 필요 상태 표시 |
| 앱 삭제와 데이터 | 앱 실행 환경 제거 후 DB·업무 파일 기본 보존. 별도 데이터 삭제가 다른 앱·환경·소스 저장소에 영향을 주지 않음 |
| 사용자 격리 | 사용자 A의 파일·레코드·대화가 권한 없는 B에게 API·MCP·검색·챗봇을 통해 노출되지 않음 |
| 권한 회수 | 토큰 철회나 앱 접근 해제 후 신규 호출과 대기 중 실행이 거부됨 |
| 앱 조합 | 구매 요청 앱이 자산 앱의 허용된 API를 호출하고 부여되지 않은 작업과 직접 DB 접근은 차단됨 |
| 앱 스키마 | 빈 DB 설치와 이전 버전 업그레이드 모두 검증하며 기존 업무 데이터를 보존. 실행 계정의 DDL·다른 앱 DB 접근을 차단하고 중복 적용·변경 이력 불일치를 검출 |
| 배포 실패 | 빌드·상태 확인·마이그레이션 실패 시 기존 운영 상태를 보존하거나 명시적인 복구 상태로 전환 |
| 자원 제한 | 지원 실행 프로필에서 CPU·메모리·프로세스 한도를 집행하고, 앱 OOM·작업 폭주 상황에서 플랫폼 관리·복구 기능 확인 |
| 용량 부족 | 신규 빌드·미리보기·배포의 자원 부족을 대기·거부하며 업로드 예약량·신구 이미지·DB 변경 임시 공간을 반영. 기본 교체에 신구 앱 동시 실행 RAM을 요구하지 않음 |
| DB 자원 관리 | 공유 DB 서버의 앱별 연결·임시 파일·용량을 관측하고 초과 차단·기존 세션 종료·복구를 검증. 관리 한도와 강제 제한의 차이를 표시 |
| 자동 정리 | 만료 미리보기·로그·미사용 캐시만 정해진 정책에 따라 정리하며 활성·복구용 릴리스와 운영 데이터를 보존 |
| 내장 챗봇 | miy 사이트에서 질문하면 내부 Hermes가 도구 호출·결과 반영을 반복하고 진행·답변을 화면에 전달함. 재접속과 명시적 중지를 구분하고 중복 실행 없이 상태를 복구함 |
| 공통 AI 연결 | 관리자 설정 한 번으로 두 사용자가 개인 공급자 로그인 없이 챗봇을 사용. 공식 지원 경로·Hermes 호환성·공통 인증 만료·갱신·한도 초과를 검증하고 API 연결은 명시적으로 선택 |
| 사용자별 AI 세션 | 같은 공통 연결 아래 두 사용자와 한 사용자의 여러 대화에 별도 thread를 배정. 문맥·파일·이벤트·도구 권한이 섞이지 않고 다른 사용자 세션의 조회·재개·중지를 거부 |
| AI 실행 | 확인 전 데이터 변경이 없고, 확인 후 권한이 회수된 작업도 실행되지 않음 |
| 외부 전달 정책 | 내부 전용 데이터가 외부 개발 에이전트 응답이나 외부 모델 입력에 포함되지 않음 |
| 복원 | 별도 환경에서 소스·배포 정보·DB·파일을 복원하고 실제 앱 동작까지 확인 |

파일럿에서는 첫 앱 운영까지 걸린 시간, 관리자 개입 횟수, 배포 성공률, 장애 복구 시간과 AI 실행 비용을 측정한다. 성능 목표는 기준 하드웨어와 데이터 규모를 정한 후 확정한다.

## 기술 기본안과 가정

| 항목 | 현재 기본안 또는 가정 |
| --- | --- |
| 관리 웹 | TypeScript·React·Vite·TanStack Router·TanStack Query. 상세 근거는 [프론트엔드 검토](FRONTEND.md) 참조 |
| Rust 적용 범위 | 플랫폼 코어와 개별 앱 백엔드의 합의된 구현 언어. Hermes·Git·DB 등 통합 구성 요소까지 Rust로 재작성하지 않음 |
| 앱 구현 언어 | Rust 백엔드 + TypeScript·React 화면. 서버와 정적 화면을 같은 이미지로 묶으며 바이너리 내장은 선택안. 추가 언어는 후속 검토 |
| 개발 도구 | miy CLI, 버전이 있는 SDK·UI 자산·템플릿과 MCP를 함께 제공 |
| 내부 AI | Hermes + 공통 Codex·Claude Code 연결 + 사용자별 독립 세션, 선택형 API·사내 모델. 실제 연결 방식과 검증 조건은 [내부 AI 계획](AI.md) 참조 |
| 앱 실행 모델 | Rust 서버와 정적 화면을 OCI 이미지로 배포하고 앱·환경별 컨테이너로 실행. 중지 후 교체와 플랫폼의 수명주기 제어는 [개발 계획](DEVELOPMENT.md#rust-풀스택-앱의-플러그인-구조) 참조 |
| 운영 환경 | 사내 또는 클라우드의 Linux 단일 서버·VM, 고객사 사용자와 위임받은 외부 수행자 중심 |
| 저장소 | PostgreSQL + miy Storage API. 초기 로컬 영속 볼륨과 선택적 S3 backend를 검토하며 MinIO는 제외 |
| 기존 miy 활용 | 독립 앱 manifest, 별도 출처 인증, 권한 확인, 배포 이력의 설계와 검증 사례 활용 |
| 데이터 이전 | 미출시 상태를 전제로 기존 개발 데이터 이전은 기본 범위에서 제외 |

기존 코드와 모든 내장 업무 앱의 일괄 이전은 포함하지 않는다. 참조할 기존 계약과 실제 도입할 외부 구성 요소는 [조사 문서](RESEARCH.md)에 연결한다.
