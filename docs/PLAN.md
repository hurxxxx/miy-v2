## 다음 우선 작업

**이 표가 작업 순서의 유일한 기준이다.** 각 작업의 세부 완료 기준은 담당 문서가 관리한다. UI는 [UI 이식 계획](UIUX-MIGRATION.md), 코어는 [코어 안정화 계획](CORE-HARDENING.md), v1에서 가져올 항목(ID `V1-*`)과 근거는 [v1 적용 계획](V1-ADOPTION.md)이다. 후속 UI·기능·권한 설계는 miy v1을 기준으로 한다. 플랫폼은 사용자·그룹별 앱 사용 권한을 관리하고, 필요한 앱이 내부 데이터 분리와 멤버·리소스 권한을 소유한다. 구체적인 계약은 [PRD](PRD.md)를 따른다.

앞선 리뷰를 반영해 **변경 범위의 최소 백업·복원 확인과 디스크·DB 보호를 먼저 확보하되, 전체 백업 제품·호스트 updater 완성을 기능 개발의 선행 조건으로 두지 않는다.** 전체 코어 3~5차의 남은 구현과 종합 인수는 베타 전 단계에서 완료한다. 이미 수행한 ai-do 기반 기본 UI의 구현·검증 이력은 보존한다.

### 결정이 필요한 사항

선택지와 권고는 [v1 적용 계획 §5](V1-ADOPTION.md#5-결정이-필요한-사항)에 있다.

1. 최소 보호의 대상·완료 기준과 첫 업무 앱. 전체 호스트 updater는 기능 개발의 선행 조건으로 두지 않는다.
2. 그룹 정본·동기화: v1의 단일 그룹·주 소속 정확 일치·수동 사용자 배정을 기본안으로 두고 코어 DB·Keycloak·인사 연동의 책임을 정한다. 하위 부서 자동 권한 상속·중첩 그룹은 초기 기본안에서 제외한다.
3. 대표 앱의 내부 공간·역할·공유·회수 계약. 플랫폼 공통 워크스페이스는 도입하지 않으며 공간이 필요 없는 앱은 그대로 동작한다.
4. 대외 소개 자료의 제품 요구(V1-R1~R5, 비용 집계 V1-A3는 R2에 포함)와 v1 보류 앱(Mail·Community·Whiteboard·Video-chat)의 채택 범위. 상세 범위는 v1 적용 계획 §3.6·3.8에서 관리한다.
5. Hermes 채택 유지: PRD 합의 사항이다. 다만 v1은 upstream 공백 9건을 자체 어댑터로 메웠고, 그중 일부는 비공개 API를 썼다. 4-1 실험에서 이 비용을 확인한다.

현재 v2의 실제 데이터에 영향을 주는 변경 전에는 해당 범위의 백업·복구 경로를 먼저 확보한다. 권한 계약·기존 설치 전환은 [코어 권한 안내](CORE-PERMISSIONS.md)를 따른다. 기본 회귀 검사는 각 단계에서 수행한다. 다른 단계의 PASS를 이월하지 않는다.

### 보류 중인 사용성 개선

0.6.3 사용자 테스트와 독립 AI 인수에서 나온 항목이다. 이전 `docs/TODO.md`에서 옮겼다. 해당 화면을 고칠 때 함께 처리한다.

- `get_contract` 응답이 Claude 클라이언트 한도를 넘는다(119,525자). 짧은 개요와 섹션별 조회 경로를 추가하고, 파일로 저장될 때 경로와 읽는 방법을 안내한다.
- HTTP IP 접속에서는 클립보드 API가 제한될 수 있다. 설치 명령을 직접 선택·복사하는 안내와 복사 상태 표시를 개선한다.
- 설치 안내에서 기존 활성 연결과 이번 명령의 대상 서버가 다르면 두 주소와 추가·선택 명령을 쉽게 비교하도록 배치한다. context 이름 `default`를 미리 정해진 서버로 오해하지 않게 한다.
- 개발 세션이 충돌하거나 만료됐을 때 세션 소유자, 남은 시간, 중지 후 재실행 절차를 보여 준다.
- 개발자 등록 요청, 관리자 승인, 운영 배포 권한 부여의 진행 상태를 이어서 보여 준다.
- 배포 작업이 앱 상태 확인 뒤 후처리에서 실패할 수 있다. 실제 앱 상태와 실패 위치를 구분해 표시하고, job ID로 진단 기록을 찾도록 안내한다.
- 실제 IdP의 로그인 만료·중복 콜백 재현과 복구 화면 인수가 남아 있다. 2026-10-28 사용자 테스트에서 Keycloak `expired_code`·`already_logged_in`이 관찰됐다(요청 ID `00cb6859-9481-47ac-8341-78b653627a96`).
- Windows 설치 파일의 코드 서명과 조직별 배포 정책 적용은 후속으로 검토한다.

## 문서의 역할

문서별 담당 범위와 보관 문서는 [문서 지도](README.md)가 관리한다. 요구사항을 바꿀 때에는 PRD를 먼저 갱신하고 관련 계획과 검토 문서를 연결한다. 외부 프로젝트와 v1의 기능 설명은 miy에 적용할 설계 제안과 구분한다.

## 최초 설계 단계와 제품 로드맵

PRD 0.5에는 Rust 앱 서버·정적 화면의 한 이미지 배포, 중지 후 교체와 플랫폼의 앱 제어에 더해 라우터 기반 UI 모듈 실행·Codex 개발 하네스의 집중 검증을 반영했다. 사내·클라우드 설치, 직접·대행·공동 운영, 권한·데이터·Hermes의 기본 구조는 유지한다. 최초 계획은 제품 전체 구현에 앞서 최소 구성으로 핵심 개발·배포 경로를 확인하는 것이었다. 아래 목록은 제품 전체에서 계속 검토할 설계 범위다.

| 순서 | 기획 작업 | 산출물과 완료 기준 |
| --- | --- | --- |
| 1 | 개발 흐름과 CLI 설계 | 지침·SDK·UI 개발 번들, 대상 코어와의 버전 호환, 프로젝트 생성·환경 연결·맥락 갱신, 로컬 실행·미리보기·승격 |
| 2 | 앱과 UI·데이터 계약 설계 | manifest·release·installation·preview 구분, SDK·공개 기능·데이터 바인딩, 필수 UI 규칙과 자유로운 확장 범위 |

기술 선택에서는 구현 난이도뿐 아니라 전담 IT 운영팀이 없는 고객사가 개발사·파트너의 지원을 받아 설치·진단·복구하고 유지관리를 이어갈 수 있는지를 평가한다. Gitea 등 외부 구성 요소를 직접 통합하는 경우에는 지원 버전, 연동 계약, 라이선스와 업데이트·복원 범위를 함께 검토한다.

## 먼저 수행할 집중 검증

세부 계획의 기준은 [핵심 개발·배포 흐름 검증](VALIDATION.md)이다. 최초 예제는 자산 관리 앱과 작은 기준정보 앱으로 좁히고, 플랫폼·DB·MCP·Docker·실제 브라우저를 연결한다. iframe 표시를 라우터 기반 UI 통합의 통과로 대신하지 않는다.

| 순서 | 검증 대상 | 다음 단계로 넘어갈 조건 |
| --- | --- | --- |
| V0 | 최소 계약, 인증·MCP 연결, UI 모듈 로딩 | 플랫폼 빌드 후 새 모듈 등록·실행과 실제 인증 확인 |
| V1–V2 | Rust 코어·DB·API, CLI·SDK·UI·지침·하네스 | 앱별 DB·권한·migration, 로컬 실행, CLI·서버의 계약 검사 일치 |
| V3–V5 | Codex 앱 개발, 단일 이미지 배포, UI 라우터 실행 | 코어 수정 없이 독립 인수 검사 통과, 서버 digest 일치, 실제 업무 동작과 같은 산출물 승격 |
| V6 | v2 DB 변경·업데이트·운영 실패 | 기존 데이터 보존, UI/API 일치, 중지 상태 유지와 복구 |
| V7 | 새 작업공간·세션·설치에서 3회 반복 | 필수 조건 모두 충족, 수동 앱 코드·호스트 보정 없이 재현 |

검증을 위해 필요한 최소 구현부터 만들고, 통과한 구성은 다음 제품 단계에서 확장한다. 실패를 수동 조치로 가리지 않고 계약·SDK·하네스·실행기 중 원인을 수정해 관련 단계를 다시 확인한다. 이미 수행한 검증과 미검증 범위는 [구현 결과](IMPLEMENTATION-RESULTS.md)에서 구분한다.

## 최초 제품 확장 순서와 후속 범위

아래는 최초 제품 전체의 기능 확장 지도다. 현재 실행 순서는 위 **다음 우선 작업** 표만 따른다. 이 표의 모든 기능을 동시에 착수한다는 의미가 아니다.

| 단계 | 작업 | 완료 기준 |
| --- | --- | --- |
| 1. 계약과 기반 | 재현 가능한 빌드·검사 기반, 기업·사용자·외부 수행자 위임, 앱·UI·데이터 계약, API·개발 자산 목록·MCP 계약, 사내·클라우드 설치 구성 | 공개 API 명세·예제·권한을 공통 기준으로 정의하고 주요 계약과 설치 경로 검증 |
| 2. 로컬 개발 | 지침·SDK·UI를 포함한 CLI 개발 번들, 버전 고정·계약 검사, 로컬 앱 실행기·테스트 데이터, 같은 API·자료를 제공하는 MCP 어댑터 | CLI만으로 기본 앱을 생성·실행·수정·검사하며 MCP에서 API·예제·허용된 스키마를 조회 가능 |
| 3. 개발 영역과 배포 | 내장 Git, 작업본 스냅샷, Rust·정적 화면 이미지 빌드, 미리보기, 운영 승격, 관리 화면의 앱 제어 | 검증한 릴리스를 중지 후 교체하고 시작·중지·재시작·삭제·실패 복구를 플랫폼 코드 변경 없이 수행 |
| 4. 데이터와 앱 조합 | DB, 파일, 외부 연결·환경별 바인딩, 앱 간 API | 두 독립 앱이 허용된 기능을 공유하고 권한 밖 접근은 거부됨 |
| 5. 내장 챗봇과 Hermes 통합 | 사이트 챗봇 UI, 대화·실행 API, 공통 AI 연결·API 선택 지원, 사용자별 독립 세션, Hermes 루프, 답변 스트림 | 직원별 공급자 로그인 없이 공통 연결로 사용하고, 대화·이벤트·도구 권한을 분리한 상태에서 질문·확인·개별 중지·재접속·공통 연결 장애를 처리 |
| 6. 운영 검증 | 코어 업데이트·앱 호환성, 백업·복원, 장애 복구, 대행 종료·인계 | 코어 갱신 후 앱 동작과 실패 복구를 확인하고, 새 서버·새 담당자가 앱·데이터·인증을 이어서 운영 |

집중 검증에서 자산 관리 앱과 기준정보 앱으로 CLI 생성·로컬 실행·앱 간 연결·개발 배포·검증용 운영 승격을 확인한다. 이후 구매 요청 앱과 외부 연결을 추가하여 업무 조합과 Hermes 통합을 확장한다. 예제 앱의 업무 범위를 늘리기보다 플랫폼 계약과 운영 흐름을 검증하는 데 집중한다.

공통 AI 연결과 독립 세션은 5단계까지 미루지 않고 설계 단계에서 최소 실험으로 먼저 확인한다. 기존 Workbench의 1인용 Codex 연결·thread 재개와 기존 Hermes의 사용자별 소유 관계를 참고하되, 두 경로가 이미 연결되어 있다고 가정하지 않는다. 같은 공통 연결로 두 miy 사용자의 대화·이벤트·도구 실행이 분리되는지 확인하며 세부 기준은 [내부 AI 계획](AI.md#구현-전-확인할-사항과-인수-조건)을 따른다.

초기 실행 프로필은 Rust 서버와 정적 화면을 같은 OCI 이미지로 배포하는 독립 서비스로 구체화한다. 정적 파일의 바이너리 내장은 선택안으로 비교한다. 기존 앱 중지 후 새 버전을 실행하는 방식으로 검증하며, Kubernetes·무중단 배포·공유 함수 엔진·범용 시각적 워크플로 편집기를 첫 출시 범위에 추가하지 않는다.

## 제품 확장 단계의 검증

제품의 필수 인수 조건은 [PRD의 대표 검증 시나리오](PRD.md#대표-검증-시나리오)를 기준으로 한다. 아래는 제품 전체의 검증 범위이며, 집중 검증의 순서·최소 범위·실행 판정은 [VALIDATION.md](VALIDATION.md)를 따른다.

- Rust 정적 검사와 인증·권한·배포 상태 전이의 핵심 도메인 검사.
- 앱 관리 화면·CLI·API의 시작·중지·재시작·업데이트·삭제 권한과 상태 일치, 중복 명령·runner 재시작 후 복구 확인.
- 수동 중지 앱의 요청·예약·호스트 재시작에 의한 자동 기동 차단, 삭제 후 DB·파일 보존과 다른 환경 영향 검사.
- 기존 앱 종료 후 새 버전 시작·정상 확인, 실패 시 호환되는 이전 버전 재실행 또는 복구 필요 상태, 중지된 앱의 업데이트 후 중지 유지 확인.
- 프론트엔드 타입 검사와 API 스키마·생성 타입의 일치 확인.
- API·CLI·MCP·SDK에서 동일 권한 정책과 오류 계약을 적용하는지 확인.
- CLI로 기본 앱 생성 후 로컬에서 화면·백엔드·작업을 실행하고, 수정한 업무 기능과 계약 오류를 확인.
- UI·SDK·지침 갱신 시 사용자 코드 보존과 버전 불일치 진단 확인.
- MCP 미연결 상태의 CLI 개발·배포, 공개 API 문서 누락·SDK 버전 불일치, 맥락 동기화와 패키지 업그레이드 분리 확인.
- 고객사별 코어 버전에 맞는 개발 번들 선택, 내부 패키지 읽기 권한과 오프라인 제공 범위 확인.
- 커밋 전 작업본의 소스 해시 추적, 평가자 접근, 로그 확인, 만료·삭제와 실패한 미리보기 갱신 확인.
- 로컬·개발·운영의 데이터 바인딩과 권한 분리, 커밋 릴리스의 불변 산출물 승격 확인.
- 실제 브라우저에서 통합 UI의 런타임 등록·라우팅·직접 링크·버전 갱신을 확인하고, 분리형 UI의 출처·로그인·접근 회수·오류 처리도 해당 프로필에서 별도 검증.
- 빌드·배포·업무 실행의 재시도, 중복 요청, 중단 후 상태 복구 확인.
- 실제 CPU·메모리·프로세스 제한, 동시 실행 자원 예약과 부족 시 배포·미리보기 대기·거부 확인.
- 병렬 파일 업로드의 예약량, 공유 DB 연결·쿼리·용량 초과와 기존 세션 차단, 디스크·inode·WAL 여유 확인.
- 로그·캐시·만료 미리보기 정리가 활성·롤백용 산출물과 운영 데이터를 보존하는지 확인.
- Codex·Claude Code·Hermes·Pi의 지원 버전을 정하여 연결부터 배포 결과 조회까지 확인.
- 권한이 다른 사용자, 비활성화된 앱, 철회된 토큰을 이용한 접근 거부 검사.
- 외부 제작자의 지정 앱·환경 접근, 개발·배포·유지관리 권한 분리, 대행 종료 시 접근 회수와 후속 담당자 인계 확인.
- 사내·클라우드 설치 각각의 초기 진단, 접속·인증서·데이터 연결과 백업 복원 확인.
- 코어 업데이트의 앱 계약 호환성, 사전 백업, 데이터 변경, 갱신 후 앱 동작과 실패 복구 확인.
- 사이트 챗봇에서 내부 Hermes 실행, 도구 결과 반영, 답변 스트리밍, 사용자 확인과 중지를 확인하고, 재접속 시 기존 실행 상태가 복구되는지 검증.
- 하나의 공통 AI 연결로 두 사용자와 한 사용자의 여러 대화를 실행하고 thread·메모리·파일·이벤트·도구 권한이 섞이지 않는지 확인.
- 사용자 A의 로그아웃·취소·권한 회수가 B의 대화나 공통 인증을 종료하지 않는지 확인하고, 공통 인증 만료·프로세스 재시작의 전체 영향과 중복 실행 없는 복구를 별도로 검증.
- 구독 만료·한도 초과 시 원인과 복구 방법을 표시하고 API 과금·다른 계정 전환이 자동 발생하지 않는지 확인.
- 별도 환경에서 백업 복원 후 앱과 데이터의 실제 사용 가능 여부 확인.

기존 miy의 검증 사례는 새 계약에 맞춰 선택적으로 활용한다. 기존 테스트 통과나 외부 프로젝트의 기능 설명을 miy-v2의 검증 결과로 대신하지 않는다.

## 파일럿 평가

파일럿은 기업별 단일 서버·VM 구성을 기준으로 한다. 사내·클라우드 설치와 직접·대행 운영을 구분하고 실제 하드웨어, 네트워크 조건, 사용자 수, 앱 수와 데이터 규모를 기록한다. 고객사에 내부 개발자가 없는 경우 외부 제작자와 업무 담당자가 함께 앱을 완성·운영하는 흐름도 확인한다.

| 지표 | 확인할 내용 |
| --- | --- |
| 첫 앱 운영까지 걸린 시간 | 설치·연결·개발·검증·배포 중 막히는 구간 |
| 개발 피드백 시간 | CLI 생성부터 로컬 첫 실행, 수정 반영, 개발 영역 미리보기 준비까지 걸린 시간 |
| 관리자 개입 횟수 | 현업 사용자가 스스로 완료할 수 없는 작업 |
| 운영 대행·인계 | 고객사와 수행자 간 역할 분담, 위임·회수와 후속 담당자의 작업 재개 |
| 코어 업데이트 결과 | 호환성 문제, 서비스 영향, 적용·검증·복구 소요 시간 |
| 배포 성공률 | 실패 유형, 진단 정보와 재시도·복구 결과 |
| 장애 복구 시간 | 장애 인지부터 서비스와 데이터 복구까지의 시간 |
| AI 실행과 사용량 | 공통 연결의 총사용량·한도, 사용자·앱·업무별 관측 사용량·공정한 대기·개별 중단, API 예산과 프로세스 자원. 관측 불가 요금은 미확인으로 표시 |

성능·복구 시간의 수치 목표와 일정·작업량은 상세 설계와 기준 환경을 정한 뒤 산정한다.

## 기획 완료 기준

- PRD의 합의 사항, 기본안, 후속 범위와 미결정 사항이 구분되어 있다.
- 핵심 흐름마다 대상 사용자, 실패 처리, 권한과 확인 가능한 인수 조건이 있다.
- 앱 추가·업데이트에 플랫폼 코드 수정이 필요하지 않은 계약이 정의되어 있다.
- CLI 생성·검사·로컬 실행·개발 영역 평가·운영 승격의 입력과 결과, 실패 시 동작이 설명되어 있다.
- 필수 UI·데이터·실행 계약과 개발자의 자유로운 구현 범위가 구분되어 있다.
- 로컬과 플랫폼의 검증 범위, 개발 데이터·권한 분리와 작업본·운영 릴리스의 차이가 정의되어 있다.
- API·MCP·챗봇·앱 간 호출의 실행 주체와 권한 경계가 설명되어 있다.
- 사내·클라우드의 단일 서버에서 설치·코어 업데이트·백업·복원하는 책임과 절차가 정해져 있다.
- 고객사·개발사·파트너·도메인 전문가의 역할과 위임·회수·인계 범위가 설명되어 있다.
- 구현 작업을 나눌 수 있을 만큼 기술 선택과 공개 계약이 구체화되어 있다.
