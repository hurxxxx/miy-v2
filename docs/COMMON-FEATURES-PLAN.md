디자인은 AI-DO의 인상을 최대한 유지하고 최신 UI/UX 관행을 더한다.

## 1. 원칙

- 코어에는 인증, 사용자·그룹, 앱 접근, 개인 설정, 알림함, Storage처럼 범위를 제한한 공통 계약만 둔다. 메신저·플래너·PMS·문서는 [PRD](PRD.md#업무-앱의-공급과-설치)의 기본 제공 앱 또는 공식 업무 앱으로 만든다.
- 화면 표시나 선택값으로 권한을 판정하지 않는다. 공유·알림·검색 결과는 서버가 현재 권한을 다시 확인한다.
- **AI-DO 구현을 그대로 포팅한다(§7).** AI-DO는 업무에 쓰이며 다듬어진 구현이다. 화면·상호작용·API 형태·데이터 모델·업무 규칙을 새로 설계하지 않고 옮긴다. 바꾸는 것은 언어 차이(Python 서버 → Rust)와 miy의 경계(인증, 권한, 저장, 앱 프레임, 앱별 DB) 때문에 그대로 둘 수 없는 부분뿐이다. 절차는 §4의 앱 포팅 절차를 따른다.
- 그룹웨어·ERP·근태 같은 회사 전용 연동은 옮기지 않는다.
- 게시된 UI·SDK 번들은 수정하지 않고 새 버전으로 추가한다. 개발 단계이므로 하위 호환 계층을 두지 않는다.
- AI-DO에서 버튼만 있거나 미운영인 기능은 구현된 기능으로 세지 않는다. DM 반응, Docs의 "AI에게 묻기", 알림 설정 저장, Mail·Meeting·Recording이 여기에 해당한다.
- **기반 계약은 그것을 처음 쓰는 앱과 묶어 만든다.** 쓰는 앱이 없는 공통 서비스를 먼저 만들지 않는다.
- **경계를 넓히는 기능은 정본 문서를 먼저 고친다.** 플랫폼 → 앱 호출, 업무 실시간 전송, 보조 프레임, 사용자 전환, 새 플랫폼 권한이 여기에 해당한다(§8).

## 2. 대상 범위와 소유자

### 2.0 구분 기준: 플랫폼 기능과 앱

miy는 기능을 다음 네 가지로 나눈다. 앱의 세 분류는 [PRD](PRD.md#업무-앱의-공급과-설치)와 포털 표시(`web/platform/src/data/installations.tsx`의 `default_official`·`optional_official`·`organization`)에 이미 구현되어 있다.

| 구분 | 개발·공급 주체 | 배포 단위 | 이 계획의 대상 |
| --- | --- | --- | --- |
| 플랫폼 기능 | miy(프로젝트 오너). 코어·포털·콘솔·SDK·공용 UI | 코어·웹·SDK·UI 릴리스 | §2.1 전체 |
| 기본 제공 앱 | miy(프로젝트 오너) | 카탈로그 공식 릴리스. 새 서버의 기본 설치 대상으로 제안 | 플래너, 메신저 |
| 공식 업무 앱 | miy(프로젝트 오너) | 카탈로그 공식 릴리스. 회사가 선택 설치 | PMS, 게시판, 문서, 드라이브, 화이트보드. PLM은 카탈로그에 있지만 이 계획의 범위 밖이다 |
| 조직 제작 앱 | 직원·조직·위임받은 파트너 | 조직 앱 릴리스 | 범위 밖. AI-DO의 특수 업무 앱(근태·특허·급식·클레임 등)을 옮긴다면 여기에 해당하고, 공식 앱을 고친 사본도 새 ID의 조직 앱이 된다 |

다음 중 하나에 해당하면 앱이 아니라 **플랫폼 기능**으로 만든다.

1. **보안·권한 경계 자체인 기능:** 인증, 앱 접근, 사용자 전환, Storage 집행, 감사처럼 앱이 맡으면 경계가 무너지는 기능
2. **여러 앱의 결과를 한곳에 모으는 기능:** 알림함, 통합 검색, 홈·위젯 틀. 틀과 수신·표시는 플랫폼이 맡고, 내용은 각 앱이 제공한다.
3. **모든 앱이 똑같이 따라야 하는 기능:** 개인 설정(테마·언어·시간대), 런처, 디자인 토큰·글꼴·공용 UI
4. **앱이 멈춰도 동작해야 하는 기능:** 관리 콘솔, 사용자·그룹 관리

이 네 조건에 해당하지 않는 업무 데이터와 규칙은 앱이 소유한다. 대화·일정·업무·문서·파일이 여기에 해당한다.

miy가 직접 만드는 기본 제공·공식 앱도 조직 제작 앱과 **같은 SDK와 플랫폼 계약만** 쓴다. 공식 앱만 쓸 수 있는 내부 API를 만들지 않는다. 알림 발행, 플랫폼 → 앱 호출, 보조 프레임 패널은 모두 조직 제작 앱도 같은 선언·승인 절차로 쓸 수 있어야 한다. 공식 앱도 일반 앱과 같은 CLI·서버 빌드·릴리스 권한 승인을 거친다.

**카탈로그 등록.** `docs`·`drive`·`whiteboard`·`board`를 공식 업무 앱(`defaultInstall: false`)으로 [기본 제품 목록](../registry/apps/catalog.json)에 추가했다. 출시 버전은 없다.

- 카탈로그는 코어 실행 파일에 포함된다. 이 변경이 들어간 코어가 배포되면 그때부터 네 ID로 조직 앱을 새로 등록할 수 없다.
- 서버 DB의 제품 목록에는 자동으로 들어가지 않는다. schema 25 이상인 서버는 배포 도구에 `--official-app-catalog`와 승인한 SHA-256을 줘야 동기화한다.
- 같은 ID의 조직 앱·등록 요청·권한이 서버에 이미 있으면 동기화가 `catalog_app_id_conflict`로 거부된다. dwdcc.kr의 코어 DB에는 겹치는 ID가 없다(2026-11-21 읽기 전용 확인). miy.works는 확인하지 않았으므로 코어 배포 전에 확인한다.

**메신저의 메시지 수정·삭제 기준.**

- 작성자 본인만 수정·삭제할 수 있다.
- 수정한 메시지에는 "수정됨"을 표시한다.
- 삭제한 메시지는 대화 흐름에 "삭제된 메시지" 자리표시만 남기고, 첨부의 연결을 해제한다. Storage에서 연결을 해제하면 파일 바이트가 지워진다.
- 신고가 접수된 메시지는 삭제해도 신고 처리가 끝날 때까지 본문 사본과 첨부를 보존한다. 이 동안 첨부 연결 해제를 미룬다.
- 수정·삭제 이력은 메신저 앱 DB에 남긴다. 플랫폼 감사 로그에는 업무 본문을 넣지 않는다.
- 신고 처리 화면은 메신저 앱 안에 두고, 앱이 선언한 관리 역할을 가진 사용자만 쓴다. 관리 콘솔은 앱 화면을 실행하지 않는다.
- 수정·삭제하면 플랫폼 알림함에 남은 해당 알림도 회수한다(§4 M2).

### 2.3 파일 저장

**MinIO 없이 코어 Storage API와 로컬 영속 볼륨을 쓴다.** 이 방식은 [STACK](STACK.md)의 결정이고 지금도 그렇게 구현되어 있다. 앱은 파일시스템 경로를 받지 않고 SDK·Storage API로만 파일을 다룬다.

- **현재 구조**
  - 바이트는 `artifacts/.files/<설치 UUID>/<파일 UUID>.blob`에 저장한다. 쓰는 중에는 `.part`로 두고, 끝나면 rename으로 확정한다.
  - 메타데이터는 코어 DB, 업무 연결과 ACL은 앱 DB가 소유한다. 파일의 SHA-256은 이미 기록한다.
- **현재 한도** (`crates/miy/src/storage_contract.rs`)

  | 범위 | 한도 |
  | --- | --- |
  | 파일 하나 | 10MiB |
  | 설치 하나 | 256MiB, 1,000개 |
  | 코어 전체 | 1GiB, 10,000개 |
  | 전송 | 동시 4개, 전송당 20초 |

  코어 전체 1GiB 상한 때문에 지금 한도로는 드라이브 앱이 성립하지 않는다.
- **드라이브 전에 필요한 보강(M10)**
  - 분할·이어 올리기 업로드 계약. 10MiB 첨부 계약과는 분리한다.
  - 큰 파일 다운로드 수단. 지금 프레임은 파일 전체를 메모리 Blob으로 받는다. 짧게 유효한 다운로드 증표(V1-F2) 같은 새 계약이 필요하다.
  - 한도 재설계. 설치별 한도는 관리자가 정하고, 코어 전체 한도는 디스크 여유에 맞춘다.
  - 파일 수가 많을 때를 대비해 파일 UUID 앞자리로 하위 디렉터리를 나눈다. 기존 `.blob` 파일의 이전 절차를 함께 정한다.
  - 저장된 SHA-256으로 주기적 무결성 확인.
- **드라이브 앱이 소유하는 것:** 폴더, 버전(새 파일 UUID를 가리키는 행), 휴지통
- **운영**
  - 파일 볼륨은 PostgreSQL·Docker와 다른 마운트에 두는 것을 권장한다.
  - 백업·복원은 DB와 파일 볼륨을 함께 하고 별도 영역에서 복원을 확인한다.
- **S3 backend로 넘어갈 시점:** 서버가 여러 대가 되거나 고객사 객체 저장소를 써야 할 때다. 이때 S3 호환 저장소 어댑터를 추가하며, 앱 파일 API는 바뀌지 않는다.

**순서를 이렇게 잡은 이유**

- **D0가 먼저인 이유:** 이후 모든 앱이 같은 토큰·글꼴·설정 전달 경로 위에서 만들어진다.
- **플래너(M1)가 첫 앱인 이유:** 개인 범위라 ACL이 단순하고, §2.4의 기반 중 D0만 있으면 된다. PLAN의 "베타 사용자가 쓸 첫 업무 앱"의 후보가 된다.
- **연결·알림(M2)을 메신저 바로 앞에 둔 이유:** 알림 계약은 메신저가 첫 사용처다. 쓰는 앱과 함께 만들어야 계약을 실제로 검증할 수 있다.
- **메신저를 주기 조회로 먼저 내는 이유:** 실시간 전송(M4)은 경계 계약을 새로 여는 일이라 시간이 걸린다. 메신저의 나머지 기능은 그 전에 인수할 수 있다.
- **게시판이 문서보다 앞인 이유:** 필요한 기반이 적고, 홈의 공지 카드를 일찍 채운다.
- **검색(M12)이 뒤인 이유:** 검색할 내용이 있는 앱이 둘 이상 있어야 여러 앱을 모으는 계약을 검증할 수 있다.

**함께 진행할 수 있는 것**

- P1과 M1은 D0 뒤에 병행할 수 있다. 저장된 개인 설정이 없는 동안 프레임은 기본값(시스템 테마, 한국어, 브라우저 시간대)을 받는다.

- M6는 P1 뒤 언제든 착수할 수 있다. 다만 정본 개정이 먼저다.
- M7~M11은 M2 뒤에 순서를 바꿀 수 있다.

## 4. 단계별 세부 작업

### D0 디자인·설정 전달 기반

1. **AI-DO의 토큰을 원본으로 삼는다.** `../ai-do/prod`의 `packages/ui/styles.css`(`--ui-*` 토큰, 라이트·다크)를 그대로 가져와 토큰 원본 하나(`packages/tokens/tokens.css`)로 둔다. 여기서 네 곳을 만든다: 프레임 런타임(`web/frame-runtime/src/frame.css`), 포털·dev 포털·콘솔, 로컬 미리보기 호스트(`templates/rust-react/sdk/preview`), 공용 UI.
   - 이름 공간은 `--ui-*` 하나다. 포털의 `--shell-*` 중복 토큰과 프레임 런타임의 기존 변수 5개(`--miy-background`·`--miy-text`·`--miy-accent`·`--miy-border`·`--miy-app-font`)는 없앤다.
   - AI-DO의 Tailwind 테마 매핑(`bg-app-*`·`text-app-*` 등)도 같은 이름으로 둔다. 옮겨 온 화면 코드를 고치지 않고 쓰기 위해서다.
   - 링크·선택·포커스의 브랜드 파랑(§5.2)만 AI-DO 토큰에 더한다.
2. **Pretendard를 제공한다.** Pretendard Variable(OFL)을 한글 범위별로 나눈 woff2로 프레임 런타임 경로(`/_miy/runtime/`)와 미리보기 호스트에 넣는다. 포털·콘솔은 이미 같은 글꼴 패키지를 쓴다.
   - 프레임 런타임은 각 앱 출처에서 제공되므로 프레임 CSP의 `font-src 'self'`를 충족한다.
   - 라이선스 고지 파일을 배포물에 포함한다.
   - 런타임 파일은 지금 `no-cache`로 응답한다. 해시가 붙은 글꼴 파일에는 긴 캐시를 허용할지 함께 정한다.
3. **설정 전달 경로를 만든다.** AI-DO의 개인 설정과 같은 네 값(테마 선택, 언어, 시간대, 날짜 형식)을 초기값과 변경 이벤트로 프레임에 전달한다. 함께 바꾸는 곳은 다음과 같다.
   - 브리지 프로토콜(`packages/frame-protocol`), 코어의 프레임 부트스트랩
   - 포털의 송신(`web/platform/src/app/AppFrame.tsx`), 프레임 런타임의 적용(문서에 테마 표시와 `lang` 설정)
   - SDK의 값·구독 API, 템플릿의 SDK 사본, 미리보기 호스트
   - 결과로 새 SDK 번들과 CLI 버전을 게시한다.
4. **Tailwind CSS 4를 넣는다.** 앱 템플릿과 포털에 AI-DO와 같은 `@tailwindcss/vite` 방식으로 넣는다. 설정 파일 없이 CSS에서 설정하므로 서버 빌드의 소스 허용 목록을 바꾸지 않아도 된다.
5. **공용 UI 2.0.0은 AI-DO의 `packages/ui`를 옮긴다.** 원본은 파일 62개, 약 130KB로 컴포넌트 패키지 한도(128개, 2MiB) 안이다.
   - Radix UI·lucide-react 같은 npm 의존성은 지금 컴포넌트 패키지가 선언할 수 없다. 컴포넌트 프로토콜에 의존성 선언을 추가하고, `miy component sync`와 `miy app check`가 앱의 `package.json`에 빠진 의존성을 알리게 한다.
   - miy 전용 계약인 DirectoryPicker·ShareEditor·FileTransferPanel·FileImagePreview는 유지하고 새 토큰과 스타일 방식으로 맞춘다.
   - 2.0.0은 새 SDK 번들에만 호환으로 지정한다. `miy component update`는 버전을 생략하면 호환되는 가장 높은 버전을 고르므로, 기존 번들에 호환으로 게시하면 기존 앱이 의도치 않게 올라간다.
6. **기존 앱을 구분한다.** 포털은 앱이 다크·언어를 지원하는지 알 수 없다. 프레임 런타임은 릴리스의 번들 버전을 보고, 설정 전달을 지원하는 번들로 빌드한 앱에만 다크·언어를 적용한다. 그 이전 앱은 라이트·한국어로 유지한다.
   - 글꼴은 모든 프레임에서 Pretendard로 바꾼다.
   - 기존 변수 5개를 읽던 앱은 새 UI로 다시 빌드한다. 이 서버의 기존 설치 8개는 QA·파일럿 앱이다.
7. **포털·dev 포털·콘솔의 스타일을 같은 토큰으로 교체하고 다크 모드를 넣는다.**
8. **템플릿과 예제를 갱신한다.** 대표 앱(`examples/common-work`)에서 디렉터리 선택·공유·첨부의 전체 경로를 2.0.0으로 인수한다. UI 1.1.0에서 대기 중인 같은 인수와의 관계는 PLAN에서 정리한다.
9. **검사를 만든다.** 토큰 대비 자동 검사, 하드코딩 색 lint, 라이트·다크 × 데스크톱·모바일 시각 회귀 기준 이미지.

### P1 셸·설정·콘솔

사용자 전환은 [M6](#m6-사용자-전환)로 분리했다. 포털 셸·개인 설정 화면은 AI-DO의 해당 화면(`apps/web/src/components/layout`, `apps/web/src/platform/auth`의 설정 화면)을 옮긴다.

- **개인 설정**(포털·dev 포털)
  - 프로필: 표시 이름, 직함
  - 화면: 테마(시스템·라이트·다크), 언어, 시간대, 날짜 형식
  - 보안: 비밀번호 변경은 기존 Keycloak 경로를 쓴다. 브라우저 세션 목록·개별 종료를 새로 만든다. CLI 세션 관리는 기존 화면을 유지한다.
  - "기본 공간"은 두지 않는다. 플랫폼 전역 공간은 없고(PLAN 결정 1·3), 공간 선호는 각 앱이 소유한다.
  - 알림 수신 설정은 M2에서 만든다.
- **다국어(한국어·영어)**
  - 대상: 포털·dev 포털·콘솔, 프레임 런타임의 안내 문구, 공용 UI의 기본 문구. 공식 앱은 AI-DO의 해당 문구를 가져온다. 로그인 화면은 이미 한국어·영어를 지원하므로 포털에서 고른 언어를 넘겨 주기만 한다.
  - 대상 아님: CLI, 개발 문서, 에이전트 지침, 조직 제작 앱
  - 구조: AI-DO와 같은 i18next·react-i18next를 쓰고, 문구는 AI-DO의 한국어·영어 리소스(`platform/i18n/resources.ts`)에서 해당 부분을 가져온다. 키가 빠지면 빌드를 실패시키고, 화면 코드의 한글 리터럴을 lint로 거부한다.
  - 날짜·숫자·상대 시간은 사용자의 언어와 시간대로 표시한다. 서버 오류는 코드로 받고 화면에서 번역한다.
  - 한국어가 기본 언어이자 번역이 없을 때의 대체 언어다.
- **런처**
  - 즐겨찾기 고정, 순서 편집·초기화, 현재 앱 강조
  - 관리자가 편집하는 카테고리. 기존 공급 분류(기본 제공·공식 업무·조직 제작)는 앱에 붙는 표시로 유지하고, 카테고리는 그 위의 묶음이다.
- **앱 셸 레이아웃**: 서브 사이드바(240px, 180~480px 조절·접기·고정), 페이지 헤더와 브레드크럼브, 모바일 전역 메뉴와 앱 메뉴 분리. 공용 UI로 제공하고 앱 템플릿의 기본 레이아웃에 넣는다(§5.5).
- **명령 팔레트(Ctrl/⌘+K)**: 프레임에 포커스가 있으면 키 입력이 포털에 닿지 않는다. 프레임 런타임이 이 단축키를 포털에 알리는 브리지 메시지를 추가한다. 첫 버전은 앱 이동과 설정 이동만 지원한다.
- **콘솔**
  - 릴리스 권한 승인 화면: 릴리스가 요청한 권한과 승인된 권한의 차이를 보여 주고 승인한다. 배포 직후 승인이 필요하면 알린다([사용자 검증](releases/user-test-20261121-131334/report.md)의 개선 후보 3).
  - 사용자 화면: 검색·필터, CSV 내보내기
  - 런처 카테고리 편집

### 앱 포팅 절차 (M1·M3·M7~M11 공통)

공식 앱은 AI-DO의 해당 구현을 그대로 옮겨 만든다.

1. **기준 고정:** 원본은 `../ai-do/prod` main의 고정 커밋이다(현재 `0002af062`). 앱마다 기준 커밋을 앱 문서에 적는다.
2. **화면:** `apps/web/src/app-modules/<앱>`과 그 화면이 쓰는 공용 요소(`apps/web/src/components`, `platform`의 날짜·포맷·선택기 모델)를 그대로 가져온다. 바꾸는 것은 네 가지다.
   - API 호출은 miy SDK로 바꾼다.
   - 로그인·워크스페이스 문맥은 SDK가 주는 신원과 앱이 소유한 공간으로 바꾼다.
   - 다른 앱 화면을 직접 가져다 쓰던 곳은 앱 간 링크나 앱 간 호출로 바꾼다.
   - 포털 전역 이벤트에 기대던 곳은 프레임 브리지로 바꾼다.
3. **서버:** `apps/api/src/ai_do_api/domains/<도메인>`의 라우터·서비스·모델·스키마를 Rust(Axum·SQLx)로 옮긴다. REST 경로, 요청·응답 형태, 검증과 업무 규칙을 유지해 화면 쪽 API 코드를 거의 그대로 쓴다.
4. **데이터 모델:** 테이블과 컬럼을 그대로 옮긴다. 사용자·워크스페이스 참조는 miy 사용자 ID와 앱 소유 공간으로 바꾼다. 다른 도메인의 테이블을 가리키던 외래키는 ID만 보관하고 앱 간 호출로 확인한다.
5. **권한:** AI-DO의 접근 규칙을 그대로 옮긴다. 판정은 앱 서버가 앱 ACL(G5·G6)로 한다.
6. **테스트:** AI-DO의 서버 테스트(`apps/api/tests`)와 화면 테스트(`*.spec`)의 사례를 옮겨, 같은 입력에 같은 결과가 나오는지 확인한다.
7. **문구:** AI-DO의 한국어·영어 문구를 그대로 가져온다.
8. **차이 기록:** miy의 경계 때문에 원본과 달라진 점을 앱 문서에 적는다.
9. **출시:** 카탈로그 공식 릴리스를 만들고 릴리스 권한을 승인한 뒤, AI-DO 기준 화면(가상 계정·가상 데이터)과 비교하고 권한을 인수한다. 무거운 라이브러리는 로컬 미리보기가 아니라 실제 프레임에서 확인한다. 미리보기에서는 프레임 CSP 적용이 확인되지 않았다.
10. **보강:** §2.2의 보강 항목은 포팅을 인수한 뒤 더한다. 원본이 없으므로 §5의 디자인 기준으로 검사한다.

### M1 플래너

- 범위는 §2.2를 따른다. AI-DO의 `planner`와 `personal_widgets`(할 일·메모) 도메인, 달력 화면(`UnifiedCalendar`, FullCalendar 6)을 옮긴다. 첫 출시에서 빼는 기능(타임라인, 통합 캘린더, Google 구독)은 화면과 API를 가져오지 않는다.
- 일정 시각은 전달받은 사용자 시간대로 표시한다.
- 공휴일 데이터는 앱에 포함한다. 데이터가 없는 연도는 "휴일 없음"이 아니라 "휴일 정보 없음"으로 구분한다.
- 할 일·메모는 본인 전용이다. M5에서 보조 프레임에 띄울 수 있게 좁은 폭의 패널 화면을 따로 둔다.
- 공식 앱의 공급 절차를 처음 끝까지 수행한다: 소스 고정(`miy app source-pin`) → 카탈로그 `releases` 기록 → 서버 빌드 → dev 설치 → 인수 → prod 승격.

### M2 플랫폼–앱 연결과 알림

**먼저 고칠 정본:** CORE-PERMISSIONS(알림 권한, 플랫폼 → 앱 호출), APP-BOUNDARIES(자격증명 표), APP-FRAMES(§8).

**새 권한을 추가한다.** `platform:notifications:write`를 코어 허용 목록(`crates/miy/src/contract.rs`)에 넣고, 새 API 경로를 브라우저 경계와 앱 호출 허용 경로에 분류한다. Rust SDK에 메서드를 추가하고 로컬 미리보기 경로도 맞춘다. 게시된 번들은 불변이므로 새 번들 버전이 필요하다.

**알림 계약(첫 버전).** 메신저의 DM 알림은 메신저 앱이 발행하고, 플랫폼 알림함이 받아서 보여 준다.

| 단계 | 담당 | 내용 |
| --- | --- | --- |
| 1. 발행 | 앱 서버 | 사용자 요청을 처리하는 동안 Rust SDK로 코어 알림 API를 호출한다. 프레임(브라우저)에서는 발행할 수 없다. 요청이 끝난 뒤의 발행·재전송은 서비스 주체가 생긴 뒤로 미룬다 |
| 2. 실패 처리 | 앱 서버 | 발행이 실패해도 업무 저장을 되돌리지 않는다. 같은 요청 ID로 결과를 조회할 수 있다. 유실된 알림은 다시 보내지 않으며, 앱 안의 안 읽은 표시는 앱 데이터라 그대로 남는다 |
| 3. 승인 | 코어 | 그 릴리스에 `platform:notifications:write` 승인이 있는지 확인한다. 수신자는 활성 사용자이면서 같은 환경에서 그 앱의 사용 권한이 있어야 한다. 조건에 맞지 않는 수신자는 제외하고, 응답에는 접수 건수만 준다 |
| 4. 내용 | 앱 서버 | 수신자 목록, 종류(예: `message`, `mention`), 묶음 키(대화 ID: 같은 대화의 알림을 한 줄로 덮어씀), 짧은 표시 문구, 앱 내부 목적지 경로, 원본 자원 ID, 중복 방지용 요청 ID. 메신저의 기본 문구는 본문 없이 "보낸 사람 · 새 메시지 N개"다 |
| 5. 저장·표시 | 코어·포털 | 환경별 알림함에 저장한다. 포털 헤더의 알림 패널과 미읽음 배지, 런처의 앱 배지를 보여 준다. 클릭하면 해당 앱 프레임을 목적지 경로로 연다. 앱의 React 코드는 실행하지 않는다 |
| 6. 회수 | 앱 서버 | 원본이 수정·삭제되거나 수신자가 접근을 잃으면(대화에서 내보냄 등) 그 요청 안에서 묶음 키 단위로 알림을 회수하거나 교체한다 |
| 7. 재확인 | 코어 → 앱 | 패널을 열거나 알림으로 이동할 때 플랫폼 → 앱 호출로 원본 접근을 묶어서 확인한다. 거부되거나 응답이 없으면 숨기고 배지를 보정한다 |
| 8. 읽음 동기화 | 앱 서버 | 사용자가 앱에서 대화를 읽으면 그 묶음 키의 알림을 읽음 처리한다. 포털에서 알림을 읽어도 메신저의 읽음 표시는 바꾸지 않는다 |
| 9. 수신 설정 | 포털 | 앱별·종류별로 끌 수 있다. 앱은 이 설정을 읽지 않고, 코어가 저장 단계에서 거른다 |
| 10. 보존 | 코어 | 정한 기간이 지난 알림을 지운다(기간은 §7 남은 결정) |

- **배지 수 계산:** 저장된 미읽음에서 코어가 아는 사실(앱 사용 권한, 계정·앱 사용 중지)로 걸러 센다. 매번 앱을 부르지 않는다. V1-F3는 "건수는 거른 뒤 계산"이라고 적고 있으므로, 6·7단계로 이를 보완하는 이 방식을 정본 개정 때 확정한다.
- **갱신:** 포털은 주기 조회와 화면 복귀 시 조회로 시작한다. M4에서 실시간 채널로 바꾼다.
- **브라우저(OS) 알림:** 포털이 표시한다. 앱 프레임은 다른 출처라 알림 권한을 요청할 수 없다.
- **후속 채널:** 모바일 푸시와 이메일은 이번 범위에 넣지 않는다.

**플랫폼 → 앱 호출 계약.** 알림 재확인(위 7단계), 홈 요약 카드(M5), 통합 검색(M12)이 함께 쓰는 하나의 계약이다.

- 앱이 manifest에 고정된 엔드포인트를 선언하고, 릴리스 승인 대상에 넣는다. manifest 계약이 바뀌므로 새 번들이 필요하다.
- 포털에 로그인한 사용자의 요청에서만 호출한다. 코어가 그 사용자의 서명된 신원 문맥을 만들어 전달한다. 관리자 표시는 넣지 않고, 호출한 쪽이 플랫폼임을 나타내는 필드를 더한다.
- 그 사용자가 포털의 환경(업무 포털은 prod, dev 포털은 dev)에서 해당 설치의 사용 권한을 가질 때만 호출한다.
- **읽기 전용이다.** 앱 데이터를 바꾸는 일은 앱 프레임 안에서만 한다. 포털이 업무 쓰기를 대행하지 않는다.
- 응답은 표시 전용 데이터(제목, 보조 문구, 경로, 시각, 건수)다. 포털은 텍스트로만 그린다.
- 응답 크기·시간·사용자당 동시 호출 수의 한도를 두고, 기존 앱 응답 슬롯과 분리된 예산을 쓴다.
- 앱이 멈췄거나 한도를 넘으면 해당 항목만 숨기고 "가져오지 못함"을 표시한다. 포털의 다른 기능은 계속 동작한다.

**DB 연결 한도를 올린다(§7 결정).** [CAPACITY](CAPACITY.md)의 최악 연결 수는 `24 + 10 + 8N + 16D`다(N은 설치 수, D는 활성 개발 세션 수).

- 이 서버는 설치 8개, `max_connections` 200(사용 가능 197)이다(2026-11-21 읽기 전용 확인).
- 공식 앱 7개(플래너·메신저·PMS·게시판·문서·드라이브·화이트보드)를 dev·prod에 깔면 N은 22, 최악 연결 수는 210으로 197을 넘는다. 개발 세션이 없을 때 최대 N은 20이다.
- `max_connections`를 400으로 올리는 것을 제안한다(사용 가능 397). 개발 세션 2개와 설치 40개를 수용한다(24 + 10 + 320 + 32 = 386).
- 바꿀 곳은 `compose.yaml`의 PostgreSQL 설정, 배포 도구의 기대값(`scripts/core-rollout.py`의 `--max-connections` 기본값과 그 시험), CAPACITY·SERVER-OPERATIONS의 설명이다. 서버마다 메모리 여유를 확인한다.
- 운영 DB에 반영하려면 PostgreSQL을 다시 시작해야 한다. 운영 반영은 사용자가 요청할 때 한다.

### M3 메신저

- 범위와 수정·삭제 기준은 §2.2를 따른다.
- 대화 참여자만 읽고 쓴다. 나중에 들어온 사람은 들어온 뒤의 메시지만 본다.
- 알림은 M2 계약으로 발행하고, 대화를 읽으면 읽음 처리, 수정·삭제·내보내기 때 회수한다.
- 화면 갱신은 주기 조회로 시작한다. 즉시 갱신과 입력 중 표시는 M4 뒤에 넣는다.

### M4 업무 실시간 전송

**먼저 고칠 정본:** APP-BOUNDARIES(업무 WebSocket 기본 거부 항목, 자격증명 표), APP-FRAMES(프레임 listener 경로).

- 프레임 listener에 실시간 연결 경로를 추가하고 앱 서버로 중계한다.
- 인증은 프레임 토큰으로 한다. 주소에 토큰을 넣지 않는다(V1-F7). Origin을 확인한다.
- 프레임 세션이 끝나거나 권한이 회수되면 연결을 끊는다. 화면은 종료 코드를 받으면 내용을 가리고 신원을 다시 확인한다.
- 사용자·설치·서버 전체의 연결 예산, 유휴 종료, 메시지 크기 한도를 둔다.
- 브라우저 SDK와 Rust SDK에 넣고, 로컬 미리보기에서도 같게 동작하게 한다.
- 방식(WebSocket 또는 스트리밍 응답)은 이 단계의 정본 개정에서 정한다(§7 남은 결정).
- 포털 알림 채널(포털과 코어 사이의 실시간 연결)도 이 단계에서 만든다.
- 메신저를 주기 조회에서 실시간으로 바꾸고 입력 중 표시를 넣는다.

### M5 보조 프레임과 홈·개인 위젯

**먼저 고칠 정본:** APP-FRAMES(동시 프레임, 프레임 유지 정책 D5, 인수 항목).

**보조 프레임 계약.** 포털이 주 프레임 옆에 두 번째 앱 화면을 패널로 띄운다.

- 앱이 manifest에 패널 진입 경로를 선언한다. 사용자가 원하는 패널을 고정한다.
- 보조 프레임은 한 번에 하나만 띄운다. 열 때 만들고 닫으면 제거한다.
- 포털 주소는 주 프레임의 경로와만 맞춘다. 보조 프레임의 경로는 주소에 넣지 않는다.
- 미저장 입력 보호는 두 프레임 모두에 적용한다.
- 프레임끼리 메시지를 중계하지 않는다(AF-06 유지).
- 사용자당 동시 프레임 세션 수에 한도를 둔다. 지금은 한도가 없다.
- 좁은 화면에서는 패널 대신 해당 앱으로 이동한다.
- **메모리:** [APP-FRAMES](APP-FRAMES.md)의 실증(D5)에서 프레임을 하나 더 유지하면 탭당 약 130~200MiB(Chromium·Firefox), 330~470MiB(WebKit)가 늘었다. 이 단계에서 다시 측정해 기록한다.

**위젯은 두 종류로 나눈다.**

| 종류 | 방식 | 내용 |
| --- | --- | --- |
| 패널 | 보조 프레임에 앱의 패널 화면을 띄움. 쓰기는 앱 프레임 안에서 일어남 | 플래너의 할 일·메모, 메신저 대화 |
| 홈 요약 카드 | 플랫폼 → 앱 호출(읽기 전용) | 오늘 일정, 안 읽은 대화. 이후 앱이 나오면 내 업무(M7), 공지(M8), 최근 문서(M9) |

- 홈 화면의 틀은 포털이 소유한다. 설치되지 않았거나 권한이 없는 앱의 카드는 보이지 않는다.
- 할 일을 PMS 업무로 바꾸는 기능은 M7 뒤에 연결한다.

### M6 사용자 전환

관리자가 **그 사용자로 로그인하는 기능**이다. 로그인한 뒤는 그 사용자가 직접 로그인한 것과 똑같다. 그 사용자의 권한으로 모든 앱을 열고 읽고 쓸 수 있다. 읽기 전용, 앱별 차단, 전환 중 표시 같은 별도 장치는 두지 않는다(§7).

- **누가:** 플랫폼 관리자가 콘솔의 사용자 화면에서 "이 사용자로 로그인"을 누른다.
- **결과:** 업무 포털에 그 사용자의 일반 로그인 세션이 생긴다. 세션 수명과 로그아웃도 일반 로그인과 같다.
- **기록:** 누가 언제 누구로 로그인했는지를 관리 감사에 한 줄 남긴다. 그 뒤의 활동은 그 사용자의 활동으로 기록되며, 관리자가 한 것인지 구분되지 않는다.
- **원칙과의 관계:** "관리자에게 업무 데이터 권한을 자동으로 주지 않는다"는 원칙의 명시적 예외다. [V1-ADOPTION](V1-ADOPTION.md)은 대리 로그인을 "v1이 폐기한 구조, 다시 들이지 않는다"로 분류하고 있으므로 그 분류를 바꾼다.

**구현 방식.** Keycloak에 들어 있는 사용자 가장(impersonation) 기능을 쓴다. 코어의 세션 구조는 바꾸지 않는다.

1. 콘솔에서 버튼을 누르면 코어가 Keycloak 관리 API로 그 브라우저에 대상 사용자의 로그인 상태를 만든다.
2. 브라우저가 업무 포털의 일반 로그인 절차를 거친다. Keycloak에 이미 로그인된 상태이므로 바로 그 사용자로 들어간다.
3. 포털에 관리자 본인으로 로그인돼 있었다면 그 세션을 끝내고 다시 로그인한다.

착수할 때 먼저 확인할 것은 다음과 같다.

- Keycloak 26.8.1의 사용자 가장 기능이 이 구성에서 동작하는지 확인한다. Keycloak 관리 화면은 외부에 열려 있지 않으므로(`/identity/realms/miy/`와 `/identity/resources/`만 공개) 코어가 관리 API를 대신 호출해야 한다.
- 코어의 Keycloak 서비스 계정에는 지금 사용자 관리 권한(`manage-users`)만 있다. 가장 권한을 더해야 하고, 이는 `scripts/configure-identity.py` 변경과 운영 반영이 필요하다.
- 같은 브라우저에서 Keycloak 로그인 상태가 대상 사용자로 바뀐다. 관리자의 콘솔 세션이 그대로 유지되는지 확인한다.

**대안: 마스터 비밀번호 로그인.** 로그인 화면에서 사용자 ID와 마스터 비밀번호를 넣으면 그 사용자로 로그인하는 방식이다. 위 방식이 이 구성에서 동작하지 않을 때 다시 검토한다. 먼저 고르지 않은 이유는 다음과 같다.

- 누가 로그인했는지 기록이 남지 않는다.
- 비밀번호 하나가 새면 모든 계정이 열린다.
- Keycloak 로그인 절차에 확장 모듈을 만들어 넣어야 한다.

**먼저 고칠 정본:** V1-ADOPTION, CORE-PERMISSIONS(관리자와 업무 데이터 분리 원칙의 예외), APP-BOUNDARIES(관리·업무 분리 AB-05, 자격증명 표, 인수 항목), PRD, ACCOUNTS(§8).

### M7~M11 공식 업무 앱

## 5. 통일 디자인 기준

### 5.1 현재 v2의 불일치

- **토큰이 세 계열로 나뉘어 있고 서로 복사한 값이다.**

  | 이름 | 선언 위치 | 특징 |
  | --- | --- | --- |
  | `--miy-*` | `web/frame-runtime/src/frame.css`(앱에 실제로 전달되는 곳), `web/platform/src/styles/tokens.css`, `packages/ui/src/tokens.css` | 변수 4개와 앱 글꼴. 강조색 `#244bff`, 앱 글꼴 Inter. 공용 UI 컴포넌트는 이 변수를 읽지 않는다 |
  | `--ui-*` | `packages/ui/src/styles.css` | AI-DO 토큰 일부를 복사했다. 다크 토큰이 있지만 켜 주는 코드가 없다 |
  | `--shell-*` | `web/platform/src/styles/tokens.css` | AI-DO 라이트 토큰을 다시 선언했다. 다크 모드 없음 |

- **글꼴:** 포털·콘솔은 `pretendard` 패키지의 가변 글꼴을 포함한다. 공용 UI와 앱 프레임은 글꼴 파일 없이 이름만 지정해 PC마다 다르게 보이고, 앱 프레임의 기본 글꼴은 Inter라서 포털과 다르다.
- **테마·언어:** SDK가 `theme: "light"`로 고정돼 있고, 포털에는 다크 모드와 번역 구조가 없다.
- **스타일 방식:** 지금 공용 UI와 앱 템플릿은 Tailwind 없이 일반 CSS를 쓴다. AI-DO는 Tailwind CSS 4와 Radix UI를 쓴다.

### 5.2 유지할 AI-DO 디자인 요소

| 요소 | 기준 |
| --- | --- |
| 색 | 중립 회색 팔레트. 주요 버튼은 라이트에서 거의 검정(`#0f172a`), 다크에서 거의 흰색(`#f1f5f9`). 링크·선택·포커스에는 브랜드 파랑(`#244bff` 계열, 다크에서는 밝힌 값) 한 가지를 쓴다(§7). 의미 색(info·success·warning·danger)은 상태 표시에만 쓴다 |
| 밀도 | 행·컨트롤 높이 30px(조밀)·34px(기본). 본문 14px, 보조 13px, 캡션 12px |

### 5.4 적용 방식

**무엇을 어디서 제공하는가**

| 대상 | 제공하는 곳 | 바꾸면 반영되는 범위 |
| --- | --- | --- |
| 토큰(`--ui-*` CSS 변수), 글꼴, 테마·언어 적용 | 프레임 런타임(모든 앱 출처에 같은 파일). 포털·콘솔과 미리보기 호스트는 같은 원본에서 빌드 | 모든 앱에 즉시. 앱을 다시 빌드하지 않는다 |
| 컴포넌트(코드) | 공용 UI 패키지. 앱이 버전을 고정해 소스로 받는다 | 앱이 새 버전으로 올리고 다시 빌드할 때 |
| 라이브러리(Tailwind, Radix, 달력·편집기 등) | 각 앱의 `package.json`과 lockfile. 템플릿이 기본 구성을 준다 | 그 앱만 |

- 토큰 이름 공간은 AI-DO의 `--ui-*` 하나로 통일한다. 공용 UI 1.1.0도 이미 이 이름을 쓴다.
- 포털·콘솔도 같은 토큰과 Tailwind 매핑을 쓰고, 셸·설정·알림 화면은 AI-DO의 해당 화면을 옮긴다(P1·M2).

**의존성(§7 작성자 결정)**

AI-DO 코드를 그대로 옮기기 위해 AI-DO와 같은 라이브러리를 쓴다. 버전은 AI-DO의 lockfile을 기준으로 고정한다.

| 용도 | 라이브러리 |
| --- | --- |
| 스타일 | Tailwind CSS 4(`@tailwindcss/vite`), clsx, tailwind-merge, class-variance-authority |
| 기본 요소·아이콘 | Radix UI, lucide-react |
| 문구 | i18next, react-i18next |
| 표·달력·차트 | TanStack Table, FullCalendar 6, Recharts |
| 편집기·화이트보드 | BlockNote, Excalidraw. 공동편집의 Yjs는 후속 |

- 화면 이동은 AI-DO 화면이 쓰는 react-router 방식을 앱 안에서 유지하고 SDK의 경로 동기화에 연결한다. 연결 방식은 M1에서 정한다.
- 공용 UI가 요구하는 npm 의존성은 컴포넌트 프로토콜의 의존성 선언으로 알린다(§4 D0).
- 지원 브라우저는 Chrome·Edge·Firefox·Safari의 최근 두 주 버전이다. 자동 검사는 Chromium·Firefox를 기본으로 돌리고 WebKit을 선택으로 둔다.
- 프레임 CSP(`script-src 'self'`, eval·Wasm 실행 불가, `worker-src 'none'`, 외부 글꼴·이미지 차단)에서 각 라이브러리가 동작하는지 그 라이브러리를 처음 쓰는 단계에서 확인한다. 동작하지 않으면 CSP 계약을 조정할지 그때 정한다.

**자동 검사**

- 색·크기를 하드코딩하면 lint로 거부한다.
- 토큰 대비를 자동으로 검사한다.
- Playwright 시각 회귀를 라이트·다크 × 데스크톱·모바일로 돌린다.
- 화면 코드의 한글 리터럴과 빠진 번역 키를 검사한다(P1).
- AI-DO 기준 화면과 같은 가상 데이터로 비교한다.

## 6. 완료 판단

- **공통:** [AI-DO-COMMON-MIGRATION §7](AI-DO-COMMON-MIGRATION.md#7-ux와-권한-인수-기준)의 UX·권한 인수 기준을 적용한다.
- **디자인:**
  - 포털·dev 포털·콘솔과 앱 프레임이 같은 토큰 원본과 글꼴을 쓴다.
  - 하드코딩한 색이 하나도 없다.
  - 라이트·다크 모두 대비 AA를 충족한다.
  - 시각 회귀 기준 이미지가 승인돼 있다.
- **다국어:** 언어를 영어로 바꾸면 포털·콘솔·공식 앱에 한국어 고정 문구가 남지 않는다. 자동 검사와 화면 순회로 확인한다.
- **기반 계약:** 새 계약마다 해당 정본 문서가 먼저 개정돼 있고, 그 문서의 인수 항목으로 확인한다.
- **앱:**
  - 카탈로그 공식 릴리스로 설치·갱신된다.
  - 앱 ACL과 공유 회수가 동작한다.
  - 알림·검색·홈 카드에 권한 없는 항목이 나오지 않는다.
- **보고:** 검증 결과는 AGENTS 규칙에 따라 PASS·FAIL·NOT_RUN으로 기록한다.
