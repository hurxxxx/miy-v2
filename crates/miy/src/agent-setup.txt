# MIY coding agent setup

You are setting up or developing an independent MIY app in the user's workspace. Run the commands yourself. Reuse the user's installation, account and project when they match this platform. A connection request finishes after the live MCP check in section 3. For app development or publication, continue only through the environment the user requested. Hand browser sign-in, project trust and administrator decisions to the appropriate person, then resume the same task.

- Human setup page with install commands and copyable agent requests: @MIY_ORIGIN@/cli/install
- Platform and CLI context origin: @MIY_ORIGIN@
- Published CLI versions, target archives, hashes and installer commands: @MIY_ORIGIN@/api/v1/cli/install
- Report development feedback with `miy report send --message-file feedback.txt` (32,000 Unicode characters). Use `--thread-id FIRST_ID` for follow-ups and `miy report result REPORT_ID` from the submitting outbox to read the action taken. Include the CLI and SDK version when describing a compatibility issue.
- Run `miy app status --environment dev` to compare local source history. Review the exact release with `miy app accept --dry-run --note ...`, then supply `--release ID` or evidence containing releaseId. An app that requests platform:stewards:claim requires CLI 0.22.0 or newer. SDK 0.7 provides transaction-bound audit and a disposable rehearsal in sdk/testing/stewards.py.
- Read changes and upgrade actions at @MIY_ORIGIN@/api/v1/cli/release-notes or use `miy --output json describe --topic updates` offline. Compare the project's CLI and bundle versions before applying the actions for each intervening release.
- Server features: @MIY_ORIGIN@/api/v1/capabilities
- Portal, test portal and console addresses: @MIY_ORIGIN@/auth/options

## 1. Install the CLI and select the platform

Read the installer metadata and compare its cliVersion to `miy --version`. Install or update if needed. Use the matching installer for Linux or macOS x64/arm64, or Windows x64. The platform installer verifies the published archive and executable.

Linux or macOS

```bash
curl -fsSL @MIY_UNIX_URL@ | bash -s -- --no-modify-path
```

Use the executable path printed by the installer, normally `$HOME/.local/bin/miy`, or add that directory to the current shell PATH.

Windows PowerShell

```powershell
& ([scriptblock]::Create((Invoke-RestMethod -Uri @MIY_WINDOWS_URL@)))
```

Check `miy context list --output json`. In data.contexts, select the name whose origin is @MIY_ORIGIN@. If several contexts match, use the one for the intended account. If one is missing, choose an unused name and run:

```text
miy context add CONTEXT --url @MIY_ORIGIN@
```

Replace CONTEXT with the selected name in the remaining commands. Use that explicit context to avoid acting on a different server. Preserve other contexts and TLS verification.

## 2. Authenticate and hand off browser approval

Run `miy --context CONTEXT --output json --no-input auth status`. If `data.authenticated` is true and the context and account match, keep the session. For `error.code = login_required` or a CLI error explicitly requiring sign-in, start device login:

```text
miy --context CONTEXT --output json --no-input auth login --device-code --no-open --no-wait
```

When `data.status = pending`, keep `data.loginId` and the selected context. Make your next action a user-visible assistant message containing the actual `data.verificationUrl`, `data.userCode` and time remaining from `data.expiresIn`. Tool results and terminal output can be hidden from the user. For example, in the user's language: “Open {verificationUrl}, sign in to your MIY account and approve code {userCode}. It expires in {expiresIn} seconds. Tell me when you have approved so I can continue.” A new user can request an account at @MIY_ORIGIN@/signup; an administrator approves the request. Passwords and tokens belong in the browser and the CLI's protected store. Never request them or read credential files.

In a print-mode client, or whenever you cannot confirm the user can see an intermediate assistant message, **end this turn with the approval instructions**. Keep the context and loginId for the next turn; resume when the user confirms approval. If the client supports immediate user-visible messages, send the instructions first, then start the wait. The user must have the URL and code before a blocking wait starts.

On resuming, wait on that same login and inspect its JSON result:

```text
miy --context CONTEXT --output json --no-input auth wait LOGIN_ID
```

- On `data.status = authenticated`, verify `auth status` again in the same context and run `miy --context CONTEXT --output json --no-input doctor --for operate`.
- On `login_wait_interrupted`, resume `auth wait` with the original loginId. On `login_context_mismatch`, use the context that started the request.
- On `login_expired`, issue a fresh request if sign-in is still wanted and send the new URL and code. On `login_not_approved`, the request may have been denied, expired or consumed. Recheck `auth status`; if sign-in is still needed, ask whether to try again. Stop on an explicit refusal.
- On `credential_storage_unavailable` or `login_credential_not_saved`, report the safe diagnostic and resolve local credential storage before starting another login. For other failures, inspect the CLI's error code and recovery instructions.

## 3. Prepare the app and prove the MCP connection

For an existing MIY app, open its root and run `miy context show --output json` there. Check that its selected origin matches this runbook. Ask before changing a context binding. Run `miy --context CONTEXT --no-input app setup` with the installed global CLI. If it reports a bundle or managed-file conflict, inspect the error and `miy describe --topic updates` before changing files.

For a new app, use the requested path, app ID and display name. For a setup-only workspace, for example:

```text
miy --context CONTEXT --no-input app init ./miy-agent-workspace --id miy-agent-workspace --name "MIY agent workspace"
cd miy-agent-workspace
```

From the app root, use the project executable for app commands. Below, `miy` stands for `.miy-tools/miy` (PowerShell: `.\.miy-tools\miy.exe`). Use the pinned Rust toolchain and the project's Node and pnpm requirements.

```text
miy --context CONTEXT --no-input component sync
miy --context CONTEXT --no-input app check --harness-only
miy --context CONTEXT --no-input doctor --for develop
```

Open or restart the agent in this app root as the same OS user. Codex reads `.codex/config.toml`; Claude Code reads `.mcp.json`. The user approves project trust or the MCP prompt when required. Both configurations start the project's `miy_app` server over stdio. Call its tools in the actual agent session:

```text
get_cli_help({"topic":"api"})
get_contract({})
```

The first call reads local CLI guidance and works offline. The second verifies the installed bundle and reads the live platform. Report the project path, selected context and returned `platformBundleVersion` when it succeeds. If tools are unavailable, tell the user which folder to reopen and which call to make there. Use `miy describe --topic api` for offline help and leave the live MCP check pending until it succeeds. Direct HTTP MCP at @MIY_ORIGIN@/mcp uses its own OAuth session.

## 4. Implement and check the app

Read the generated AGENTS.md (Codex) or CLAUDE.md (Claude Code), the referenced project skills and docs/CLI-REFERENCE.md for the installed version. Inspect CLI inputs, permissions and effects with `miy describe --command "app build"`. Discover platform APIs with `search_api({"query":"KEYWORD"})` and then `get_api({"id":"OPERATION_ID"})` using an ID from the results. Use `list_components` and `get_component` to find shared UI components.

Implement business code in src/ and web/src/ and add new numbered SQL files under migrations/. Use the app's database, verified SDK identity and permitted platform APIs. Follow docs/API.md for app endpoints. After changing an app API, run `pnpm api:generate` and include the generated OpenAPI document and TypeScript types. Run `miy app fmt` and the full `miy app check`. The earlier harness-only check covers setup.

Apps with their own administrators can opt into installation stewards (bundle 0.16.0+). Follow "Installation stewards" in docs/CONTRACT.md. A console administrator nominates one person per installation. The nominee accepts in their own deployed app session. The app manages handovers and business roles. Never request or embed the platform administrator's account ID, password or token.

## 5. Publish and verify the requested environment

1. **Registration and preview.** Run the project executable with `--version` first. For a new app submit `miy app register` once. If it returns `official_app_id_reserved`, choose an organization-specific ID (for example `mfg-plm` instead of `plm`). Have the admin approve registration and grant dev access. CLI device approval, registration, user access and installation permission approvals are separate.
   - **0.21.1 and later.** Read `get_cli_help({"command":"app dev"})`. When harness-only reports `guidance.setupRequired: true`, use the current global `miy app setup` and reconnect the project MCP before preview. Close an older Windows MCP holding the project executable once for migration. New Windows project MCP configurations use a versioned executable. A file lock may report its path, holder PID and application name. Start `miy app dev`; it prepares the preview and validates its project inputs. Run full `miy app check` before publication. Record the safe failing path in `error.details.path` and the request ID when returned.
   - **0.21.x browser identity.** After registration approval the CLI owns the development run and DB tunnel. Give the user the loopback URL actually printed by their CLI. The browser returns through its existing dev portal session or asks the user to sign in at the standard dev portal login. Use the verified browser user's SDK Identity. Test two users with separate browser profiles. Before the first deployment each browser account needs develop access; after deployment it needs dev app access. A 403 on `/preview/apps/{app}/browser/context` is a CLI startup access check. A feature's `/platform/directory` denial needs the manifest request and the current dev release's permission checked.
   - **0.21.0 and 0.20.x diagnostics.** A response may contain just HTTP status and request ID. Report those and the command; leave the path unknown when absent. On 0.20.0 a directory call during startup could itself return 403 before first installation. Do not repeat registration or request `platform:directory:read` just to start preview. Current servers require a browser-login-capable project CLI; upgrade from 0.20.x and run global `miy app setup`. Deploy only with the user's authorization.
2. **Server build.** For updates, increment the manifest version and preserve applied migrations. Commit the checked source in the app repository and confirm a clean worktree. Run `miy app source-pin` to record the commit and archive hash, then `miy app build` for the server build receipt. On a lost response or pending asynchronous build, retain the build/request ID. Inspect `job get` or `job watch`; recover the receipt with `miy job resume BUILD_ID --environment dev`. Inspect `job logs` on build failure. A worker with automatic storage recovery reports `reclaiming_build_cache` or `waiting_for_storage`. Keep the same build ID; the server reclaims unused build cache and checks space every 30 seconds for up to 15 minutes from build start. Continue observing even if the CLI disconnected. For a terminal `docker_storage_low` (immediate on 0.20.0), read `miy job logs BUILD_ID`, report the build ID and any remaining shortfall to the platform operator. After capacity is available, start a new build of the same clean commit. Local Docker cleanup cannot free space on the build server.
3. **Dev delivery.** Review `miy app deploy --environment dev --dry-run`, then execute `miy app deploy --environment dev` for a requested deployment. Use `miy app status` to match the intended source commit and release and verify installation health. Open the dev app as an intended user and test its main workflow. If a requested capability is missing, compare release requests and approvals with `miy permissions get --installation INSTALLATION_ID --release RELEASE_ID` and report only the missing permission. Approval persists across releases of the same installation while the permission stays requested. Newly requested or reintroduced permissions require approval. Revocations survive rollback. Dev and prod installations are independent.
4. **Acceptance and production.** Follow docs/ACCEPTANCE.md and record observed dev results for the exact release with `miy app accept --input @acceptance.json`. Mark untested checks `not_run` with a reason. Only on the user's request to publish to production, with prod deploy permission, preview `miy --context CONTEXT --app APP_ID app promote --environment prod --release RELEASE_ID --dry-run`. Promote that same accepted release with `miy --context CONTEXT --app APP_ID --yes app promote --environment prod --release RELEASE_ID`. Verify the prod installation, release, health and requested workflow in its own portal.

Report the environment, app ID, source commit, build/job and release IDs, verified app URL, and checks actually performed. For a pending approval, give the responsible person the concrete action and keep the ID needed to resume.
